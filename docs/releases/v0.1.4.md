# v0.1.4 — Rate-limit recovery and local supervision controls

v0.1.4 includes rate-limit recovery, owned headless cancellation, private goals, explicit BB transfers and local client controls. CLI archives contain the executable, README and license; the optional menu preview and BB plugin are distributed separately.

## Changes since v0.1.3

- Headless cancellation now reaches a private per-turn wrapper, which stops its own Unix process group or Windows job. Saved PIDs never authorize signals; legacy turns without a stop key are refused. Native macOS, Linux and Windows fixtures cover stale records, changed PIDs, stale acknowledgements, descendants and Unicode paths.

- Known rate-limit cooldowns now wait even when automatic failover is disabled. Ordinary checks continue observing the target without spending error retries or creating a retry-cap hold before the structured reset. Earlier availability can be observed on a later check. Explicit holds and configured work bounds still win. This adds no reset-time scheduler or model/account polling API.
- `goal create|revise|show` stores a private goal ID, specification and revision history. Edits require the expected ID/revision; ordinary status withholds goal text. Optional `loop.prompt_goal` appends only the latest private goal revision to automatic prompts and handoff briefs; missing or invalid goals refuse those sends. This is opt-in transport, not reference verification, planning or revision-bound completion. Review the private text before sharing it with a provider.
- `transfer preview|apply|recover` supports explicit same-environment, same-provider moves of a single BB primary. Preview checks structured identity evidence. Apply preserves goals, holds and allowances, resets target observations, advances ownership, and leaves supervision awaiting user input. A durable pending record and target binding fence interrupted moves and stale config copies; recovery rolls forward. Account/model validation and live transfer verification remain incomplete.
- Setup explicitly labels task input as a snapshot imported once into the saved `prompt.md`. Editing the original source file does not change future prompts; editing the saved prompt does. Structured setup output adds `taskBinding: "snapshot"` without including private task text or the source filename.
- Incident history retains narrowly recognized development commit-hash and numeric release-candidate version labels. Private/arbitrary suffixes remain redacted, and previously unavailable labels cannot be recovered. Labels are historical metadata, not verified binary fingerprints.
- `registry add|list|remove` registers private local loop references without starting supervision. Versioned `client status` provides bound, timestamped status for those registrations, including optional private goal display. Unavailable or stale evidence remains visible.
- Registered `client pause|stop` uses the existing control path. `client prepare-resume` returns a five-minute, single-use ticket bound to the reviewed state, sources, owner and goal evidence. Changed evidence rejects resume. Resume preserves disabled state and allowances; consuming the ticket before saving prevents automatic replay after a lost response or crash. These are local cooperative controls, not a security boundary against someone who can edit private files.

## Separately distributed integrations

The BB plugin adds a held "Move supervision here" flow for plugin-created loops and more explicit status evidence. Failed refreshes hide controls until refreshed. It uses registered host commands; it does not move sessions between providers or automatically resume a transferred loop. Plugin fixture/typecheck/bundle verification is separate from live deployment.

A read-only native macOS menu preview is available in source under `integrations/macos/`. It displays explicitly registered loops, goals, holds and freshness without starting a supervisor or timer. It is a developer preview, with no packaged installer, signing/notarization, native controls or live UI certification. Neither the menu app nor the BB plugin is included in the CLI archives or Homebrew formula.

## Verification and remaining limits

The rate-limit rule, goal storage, transfer fencing and client controls have offline regression coverage. Native setup/recovery smoke checks use local stand-in BB/process/Claude/Codex providers; they do not call real models. Held-daemon SIGKILL/restart checks verify preserved holds, ownership, allowances and no notification replay after a recorded check; crashes during sends, writes or delivery remain outside that check. Cross-compiled archives are not evidence of native installation on every platform. Publication, package and native verification evidence is tracked separately in [release verification](../release-verification.md).

A naturally occurring BB rate-limit incident and an explicit recovery informed the cooldown fix. The corrected future-cooldown behavior remains fixture-tested; a new live cooldown, unattended recovery and full fresh-setup/two-turn/hold/restart/completion walkthrough are still outstanding. Packaging does not establish readiness to migrate other threads. Live headless resume/cancellation, separate-account handoff, installed-service lifecycle, and Cursor/Antigravity adapters remain unverified or unimplemented as documented in the roadmap.

Headless stop now uses a private per-turn request accepted by the live wrapper, which terminates its own Unix group or Windows job. No saved PID authorizes a signal. Legacy records without the key are refused, and stale acknowledgements cannot confirm new requests. Receipt is acceptance, not proof of exit; abrupt wrapper death can still leave descendants for manual inspection. Earlier RC1/RC2 builds do not include this correction and must not be used as the final release.

## Upgrade notes

- Let legacy headless turns finish or inspect them manually before upgrading; automatic stop refuses records without a private stop key. Do not use an older binary to stop new turns.
- Retain a private backup of the old executable and runtime state. Replacing a binary does not replace a running daemon; restart only the identified supervisor using the same configuration. Do not clear controls, delete accounting files, change timers or transfer a thread as an upgrade step.
- Existing holds stay held, including a hold created by v0.1.3 before the cooldown fix. Review the reason and explicitly resume when appropriate. The fix does not refund spent sends or retries, enable fallbacks, or change a login/model.
- Goal, registry, transfer and resume-ticket records are private local state. Older binaries may not understand new records or honor a pending transfer fence. Do not downgrade an interrupted transfer or manually copy old config/state over its recovery record; inspect and complete the documented recovery first.
- Continue using the existing task prompt and control commands. Goal records are descriptive metadata; sharing them with the executor requires explicit `prompt_goal` opt-in. Users do not need a separate loop skill.
