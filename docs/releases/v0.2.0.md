# v0.2.0 — Recovery that keeps going, a panel, and a new licence

This is the first release under the [Sustainable Use License 1.0](../../LICENSE) (see [licence](#licence) below). It collects everything merged since v0.1.5. The full detail, entry by entry, is in the [changelog](../../CHANGELOG.md). Packaging and check evidence is in [release verification](../release-verification.md).

**Why 0.2.0 and not 0.1.6.** In a 0.x version the minor number is the one that signals a break, and this release has three:
- the licence changes for every user of the new version;
- several behaviours change on upgrade (below);
- the records it writes cannot be read by v0.1.5 without the steps under [going back](#going-back-to-v015). A loop that has run on v0.2.0 is not simply downgradable.

It also adds new commands (`panel`, `dock`, `runs`, `stop --lanes`, the `fallbacks` editing commands) and a new agent type.

## What is new

**Recovery and reliability.** Nearly all of this is implemented and fixture-tested only; see [evidence](#what-is-fixture-tested-and-what-is-live).
- **Network-aware recovery.** Before a re-prompt, a handoff, a stall nudge, a hold for a session in error or a fallback probe, keepgoing checks connectivity. While the network is down it spends nothing and holds no one. The first check after it returns recovers.
- **A failed BB turn is retried by reference** (`bb thread retry`) instead of being prompted again.
- **Stale BB retry notices** stop being waited on after `bb.retry_signal_ttl`, and a retry BB has already declined is not waited out.
- **Hung turns.** A BB turn that hung through an outage or a sleep has its nudges held back, counted but not sent. The stall rule's hold comes when it always would, with a reason that says why.
- **A stopped scheduler is noticed.** `status`, `doctor`, the panel and the BB plugin say when a loop's checks have stopped. The macOS menu can post one notification per gap. There is an opt-in `check_gap` report.
- **The daemon checks again sooner.** Within a minute of the network coming back, and at a provider limit's reported reset.
- **Children and lanes.** The parent is told when its child threads fail, and the owner can be told (`child_error`). Opt-in recovery of failed lanes (`bb.children.retry_errored`). `stop --lanes` and `--immediately`.
- **Bounds.** One loop per session; every automatic send recorded before it is made; a hard time limit per check (`loop.tick_timeout`); the no-progress flag; a single report for a long limit wait.

**Seeing and controlling loops.**
- `keepgoing panel` opens a local page for every registered loop (`keepgoing dock`). `--allow-changes` lets it pause, stop and resume, each reviewed before it is confirmed.
- The macOS menu preview is rebuilt around the panel: pause, stop and resume a loop, pause all, and notifications.
- **Pause all and stop all**, from the panel and the menu: one review of every loop, then each loop stopped or paused as its own review offered.
- `keepgoing runs` shows run references, sends and what a loop is waiting on. `timeline` is a navigable event log. `--routine` records which scheduler called a check.
- Usage readings from probes, and opt-in `loop.timing` to collect them.

**Agents and fallbacks.**
- Agents defined in configuration (`adapter: custom`).
- A primary-only Cursor CLI adapter.
- An [adapter capability matrix](../adapters.md).
- Handoff into a new BB conversation (`bb.new_thread`).
- `fallbacks add`, `fallbacks handoff on|off`, `move` and `remove`, so fallbacks can be managed without editing YAML.
- A standard route list (first part). A loop with `routes: standard` follows one ordered list of routes kept once per user in `routes.yaml`; `keepgoing routes list` shows it. The commands that edit it are not built yet. Existing loops are unchanged. See [the standard route list](../routes.md).

## Behaviour changes on upgrade

- **keepgoing now makes an outbound request of its own**: one `GET https://api.github.com/zen`, with no identifier, only when a recovery step is about to happen. Set `loop.network` to use another address or a command, or `check: "off"` for none.
- **Every automatic send is recorded in `sends.json` before it is made.** A check killed mid-send never repeats it blindly.
- **An explicit `resume` of a loop held on a spent cap starts a new error episode.**
- **BB retry notices**: three corrections in what counts as a live retry.
- **`no_progress_timeout` and the stall clock no longer count time in which nothing could run** (a missed-time gap, or the network down).
- **A time window follows the local clock** on the days the clocks change.
- **The nudges to a turn that looks hung are held back** (as above).
- **`keepgoing tick` exits 0 whenever the check ran and was recorded**, including checks that could not observe or send; failures are in the record.
- **`enable --take-over` waits up to 5 seconds** for the check lock instead of exiting 75.
- **The panel's runtime files** move to the user state directory (on Linux, out of `~/.config/keepgoing`).
- **Windows** needs Windows 10 version 1709 or newer, for read-only snapshots with delete sharing.

## Upgrading

1. **Copy each loop's state directory first.** Going back needs it (below).
2. Replace the executable, then restart each daemon or service. Replacing the binary does not replace a daemon that is already running.
3. Nothing in the configuration has to change. A `client prepare-resume` ticket made before the upgrade is refused after it; prepare it again. New report events (`limit_wait`, `network_wait`, `child_error`, `child_recovery`) are in the default list. `check_gap` and `hung_turn` are opt-in. An explicit `report.events` list must name what it wants.
4. Decide on the connectivity check (`loop.network`) if the default address is not right for you.
5. Loops run from an external scheduler, such as a BB automation, keep working as before. The daemon's faster re-checks apply only under `keepgoing start` or a service; see [services](../services.md#the-recommended-way-to-keep-checks-running).

## Going back to v0.1.5

A loop that has run on v0.2.0 writes records v0.1.5 cannot read. Before running v0.1.5 against the same state directory:
- **`incidents.json`** (schema 9). v0.1.5's `tick` exits 1, `start` refuses and `timeline` exits 1. Restore it from the copy, or remove it, which loses only the incident history.
- **`deliveries.json`.** Once it holds a delivery for a new event (`limit_wait`, `network_wait`, `child_error`, `child_recovery`, `check_gap`, `hung_turn`), v0.1.5 cannot load it: status shows it unavailable, reports still go out but each returns an error, and once-only reports may be sent again. Move it aside.
- **The configuration.** v0.1.5 reads the configuration strictly and refuses to load one with settings or report events it does not know, such as `check_gap`, `hung_turn`, `tick_timeout`, `network`, `timing`, `routes`, `adapter: custom` and `bb.new_thread`. Remove them.
- **The run graph.** Once a handoff into a new conversation is recorded, v0.1.5 refuses `graph.json`. Do not run it against that directory.
- **Fields v0.1.5 drops.** It drops fields it does not know from `state.json`, `control.json` and `bb-cursor.json`, such as the resume episode, held-back nudges, the hung-turn watch and the scheduler record. The effect is that the newer behaviours restart from nothing if you go forward again.

The [operations guide](../operations.md) has each case in detail.

## What is fixture-tested and what is live

**Fixture-tested only, not observed live:** everything listed under reliability above. That covers:
- network-aware recovery, turn retry by reference and the retry-notice corrections;
- hung turns, the scheduler overdue rule and the daemon's sooner checks;
- lane recovery, `stop --lanes`, one loop per session and sends recorded before they are made;
- agents defined in configuration, and the panel's controls.

The [live outage check](../testing.md#live-check-a-long-time-offline) has not been run, so recovery from a real outage is not proven. The hung-turn and turn-activity bookkeeping is built from the event shapes of a real BB 0.48 log, but no real hung turn has been observed.

**Live, with what was observed:**
- **Cursor:** one walkthrough on macOS with one CLI version: a first turn, exact resume and stop. Permission rejection was not observable.
- **Earlier and unchanged:** BB status and log reading, a BB automation and the daemon supervising a real chat, Claude Code probes, and report delivery. See [integrations](../integrations.md).

## BB plugin v0.3.0

The BB plugin is released from the same tag as **v0.3.0** and installed separately, as before ([install](../../integrations/bb-plugin-keepgoing/README.md#install)). The CLI archives and Homebrew contain no plugin and no macOS menu. Changes since its v0.2.0:
- The loop card says `keepgoing: checks have stopped` when the loop's scheduler may have stopped, with the reason. Its details show the schedule line, and say checks are running at their usual interval only when that has been judged.
- The skill's wording follows the CLI's resume rule: resuming a loop held on a spent cap starts a new episode.
- The plugin is under the Sustainable Use License, as the CLI is.

The plugin needs a CLI that gives `schedule` in `status --json` for the first item; with an older CLI the card shows what it did before.
