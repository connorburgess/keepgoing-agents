# v0.1.5 — Goal-aware setup and clearer supervision evidence

This maintenance release pairs the CLI with BB plugin v0.2.0 from the same repository tag. The plugin is installed separately; CLI archives and Homebrew contain no plugin or menu app. Publication and package evidence are tracked in [release verification](../release-verification.md).

## Changes since v0.1.4

- Guided setup offers a goal choice; scripts opt in with `init --with-goal`. One private `task.md` snapshot supplies objective and acceptance references to goal revision 1. Stable wake instructions share the current goal revision. The agent must read its referenced files. Preview writes nothing; creation remains disabled. Existing noninteractive callers retain prompt-only setup.
- Status records the latest returned automatic prompt attempt's goal ID/revision, target alias, mode and adapter result without task text. This record is saved at tick completion: it has crash gaps and does not prove receipt or execution. Source-file changes and semantic drift are not tracked.
- BB's structured `thread_command_failed` diagnostic code is retained. Its decision classification remains `unknown`; this does not identify or restart a disconnected host, or enable failover for unknown failures.
- Repeated control writes advance the loaded timestamp when the clock repeats or moves backwards, preventing a repeated pause from leaving unchanged evidence for an older registered-resume ticket.
- `goal create|revise|show --help` and `-h` return success without reading configuration or changing state. v0.1.4 returned usage exit code 2 for these help commands.

## BB plugin v0.2.0

The separately installed plugin adds an explicit goal checkbox to **Supervise this thread**, binds the preview to that choice, and shows recorded goal identity/revision in setup and expanded status. It withholds goal titles, task text and references. Goal setup requires CLI v0.1.5; an older selected CLI is rejected until upgraded or the user explicitly deselects goal creation and previews again. No automatic downgrade, install or login change occurs.

The repository collection manifest enables selection by `--plugin keepgoing` from the release tag. See the [plugin installation guide](../../integrations/bb-plugin-keepgoing/README.md#install) for the paired commands and compatibility limits. Git installation builds the declared server, app and host entries using BB's toolchain; it requires Git and network access for dependencies/toolchain downloads. No global npm package is published by this release.

## Verification limits

Offline CLI, SDK, host and DOM fixtures cover the setup choice, goal persistence, privacy, diagnostic gating and explicit start. Package smoke checks exercise BB/Claude/Codex prompt-only and goal setup, disabled preview/create, holds, completion declarations, ownership refusal/takeover and goal preservation. Provider executables are traps; no real model is called. Recovery fixtures use local stand-ins. Native archive execution and clean dependency-only plugin builds must be recorded against the selected revision; cross-compilation alone is not a native installation test.

A live installed-plugin walkthrough, timed first-loop acceptance, live provider resume/cancellation, separate-account handoff, installed-service lifecycle and broad BB-pilot readiness remain unfinished. Goal records and `complete` do not independently verify task success or bind completion to the current goal revision. The native macOS menu remains a separate read-only developer preview.

## Upgrade notes

- Back up the executable and private runtime files. Replacing a binary does not replace an already-running daemon. Restart only the identified supervisor with its existing configuration; preserve timers, targets, ownership, holds and accounting.
- Existing loops do not acquire a goal automatically. New goal setup is explicit; importing an original task file creates a snapshot, not a live link. Editing referenced files does not increment the goal revision.
- Update the CLI selected by the plugin on every host where goal setup will run. Plugin and CLI versions are independent; the plugin does not install or upgrade the executable. Existing managed plugin installs use BB's update flow, not a second install.
- Keep existing permission restrictions and logins. Do not resume a held or completed loop merely to upgrade. Retain v0.1.4's owned-cancellation and interrupted-transfer downgrade precautions.
