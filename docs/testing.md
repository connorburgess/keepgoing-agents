# Testing

For a built or unpacked executable, [release verification](release-verification.md) provides a provider-free setup smoke check, a [local recovery smoke check](release-verification.md#check-recovery-with-local-stand-ins), and a separate live walkthrough. Both scripts run in macOS/Linux CI. Recovery uses stand-in providers, a loopback webhook and actual temporary daemon processes; neither script certifies real provider sessions.

## Review and execution evidence

These checks guide new changes; adding them does not certify existing code or close roadmap acceptance criteria.

- **Validate environment-derived paths.** For settings whose contract requires an absolute path, reject empty or relative environment values before joining child paths or performing filesystem operations. If relative paths are supported, resolve them against a documented base rather than an incidental working directory. Test unset, empty, relative and non-ASCII values, including execution from another working directory. Absolute paths alone do not establish ownership, privacy or freedom from symlink races.
- **Prove cache behavior through dependencies.** Inject the underlying reader/provider and clock where relevant. Assert which calls occur on a miss, a hit, expiry and invalidation, and how failures affect cached data. Include changed target/account/model keys where those identities scope the cache. At least one cache-specific assertion should fail if caching is bypassed; identical returned values alone do not demonstrate a cache hit. Use local fakes, not paid provider calls.
- **Establish that checks actually ran.** A submitted command or silent wrapper exit is insufficient evidence. Verify the expected test summary, exit status and artifacts for the intended source commit. If a policy hook or expired execution lease refuses work, mark the check not run and inspect which operations executed before updating records or performing cleanup. Follow the local lease/approval rules; do not bypass a guard or assume another project's hook patterns and deadlines apply here.
- **Keep review inputs concrete.** Give a reviewer the exact diff/base/head, checks actually run, relevant contracts and a plain list of checks not run. An independent review, when available, should assess behavior and failure paths rather than inherit the author's conclusions. Reconcile findings before merge and update the PR description when the implementation changes. A review of an earlier head does not cover later edits; review never substitutes for current-head/current-base checks.

## Capability and documentation review

Apply this review before checking off a roadmap item and before merging changes to behavior, setup, limitations or release availability. Repeat it after review fixes or release-scope changes affect those claims. It is part of delivery, not a periodic cleanup deferred until the end of the roadmap.

1. **Compare claims with the final implementation.** Read the affected README sections and linked setup, operations and integration guides alongside the changed code and tests. Confirm supported targets, defaults, prerequisites, controls, failure behavior and limitations. New capabilities must be discoverable; removed or narrowed behavior must not remain advertised. Record the reviewed sections and corrections in the PR, or explain why they remain accurate without edits.
2. **Check the path a user follows.** Verify install/version guidance, example command names and flags, config-path handling, provider login prerequisites, creation versus start, and relevant links. Use the intended artifact's help or a safe fixture where feasible; never turn a documentation check into an unapproved live model call, login change or production control action. State commands not exercised and why.
3. **Separate availability from evidence.** Confirm the published release/tag and package version before naming a latest release. Label source-only changes as unreleased, and separately identify plugin/client distribution, installed-loop versions, fixture execution and live acceptance. Updating a source checkout does not update a release artifact, package or running supervisor. Avoid duplicating detailed evidence; link the authoritative verification record.
4. **Reconcile the roadmap and changelog.** Link completed work to its implementation and applicable test/live evidence. Keep partial acceptance unchecked with its remaining work explicit. Update release notes when their promised contents change; a docs-only correction must not imply a feature shipped or passed live tests. Close or revise dependent claims if a prerequisite changes.
5. **Report the result and next gap.** The PR and milestone check-in should say what changed for users, where it is available, what verified it and what remains open. The PR template's documentation review is a concrete record of this check, not an automatic correctness test. Missing evidence stays missing even when all documentation links and CI jobs pass.

## Lifecycle and platform review

Apply these checks when changing runners, stop commands, service integrations, installers or platform UI. They are review requirements, not claims that current implementations satisfy every case.

- **Prove process identity before stopping it.** A PID file and a successful liveness check establish neither ownership nor creation identity. Persisted wall-clock timestamps and command basenames alone are insufficient. Use native process identity/creation evidence or an authenticated owned control channel, and account for the race between validation and signalling. Unknown or mismatched identity must refuse destructive control. Test stale records left by abrupt termination, a live unrelated process at the recorded PID, legacy records lacking identity, and identity changes during inspection. Tests must use owned disposable processes or injected identities; never signal arbitrary host PIDs.
- **Consume machine interfaces.** Prefer native APIs or documented structured command fields to human-oriented output. Do not infer state from translated status words or decode a displayed path as if it were lossless. Where command output carries paths, round-trip a temporary path containing Latin accents, CJK characters and spaces. Include malformed/partial responses and the real encoding/localization failure shapes in fixtures.
- **Make regression fixtures fail before the fix.** Record which assertion reproduces the old behavior and run it against the pre-fix implementation when feasible. A fake that only returns idealized JSON/English/safe ASCII can miss the defect. Keep realistic failures synthetic and free of real transcripts, hostnames, account paths and secrets; label unobserved assumptions explicitly.
- **Distinguish compilation from execution.** Identify the CI job that compiles platform-specific code and the tests it actually executes. Cross-compilation, native test execution, installer testing and live VM acceptance are separate evidence. State architecture, OS, source commit and what was not run. Use existing CI or disposable test hosts; do not infer Windows execution from a generic green PR check.
- **Verify user-visible behavior at its boundary.** Add a DOM/browser or native assertion for a changed UI action where supported. Request owner-only VM/desktop checks only when required evidence cannot be obtained independently, and leave them marked not run. If screenshots are needed, capture the relevant window and sanitize hostnames and other private metadata before sharing; do not commit raw desktop captures.
- **Exercise the deployment environment.** If PowerShell is part of the supported path, test the supported language mode and prefer cmdlets for operations that must work under constrained language. Do not assume arbitrary .NET method calls are available. When Windows PowerShell 5.1 is supported, use ASCII script source or an explicitly tested encoding; test non-ASCII data separately. Verify actual subprocess/pipe encoding and console availability instead of assuming UTF-8 or a particular code page. An installation that requests elevation must show an accessible approval prompt in a visible user-initiated flow; a hidden background process is not an acceptable interactive installer test. Record the test host's accessible paths and sharing restrictions rather than generalizing one VM's setup to all Windows hosts.
- **Describe dependency limits honestly.** A dependent change must say what users can do before its prerequisite is available. Keep implemented, tested, released, installed and live-verified claims separate. Recheck the current head against current main after integration; a passing earlier base does not close the review.

The runner now exercises owned cancellation with native subprocess fixtures: legacy and mismatched records, changed saved PIDs, stale acknowledgements, old requests after a new turn, wrapper death, descendant cancellation, and accented Latin/CJK paths. The legacy-record regression failed against the old implementation before the fix. macOS/Linux full-suite CI and the dedicated Windows job execute these tests. These checks do not certify live provider cancellation, abrupt-death descendant cleanup, or hostile runtime-file writers.

## Run discovery contract tests (D1)

`go test -race ./internal/rundiscovery` exercises only the unreleased internal identity and run-boundary contract. Tables cover enrollment and explicit opening, legacy adoption, completion with and without a known run, reopen identity, scheduled triggers with and without an explicit start, unchanged runs across holds, checks, retries, restart events, goal revisions and transfers, distinct attempts across repeated wakes, retry and restart, late/duplicate/conflicting adapter returns, one run recording several sessions and successive runs recording the same session, goal and invocation links, registry references, dry-run immutability, malformed inputs and clock rollback. Tests use fictional caller-supplied IDs and timestamps; no providers, processes, files or controls are used.

A `Restart` event test shows the reducer keeps the run for the same in-memory values. It is not a daemon-restart or durable-state test. No production caller, storage transaction, migration, ID-history uniqueness check, invocation deduplication, provider-session validation or CLI/GUI resolver exists yet. Those need separate D2–D6 fixtures and live evidence where applicable. README artwork stays deferred.

## On a machine with Go

```sh
go vet ./...
go test -race ./...
```

The end-to-end tests in `cmd/keepgoing` drive the real CLI against fake `bb`, `claude`, `codex`, and `gh` executables and a local webhook receiver. They need a POSIX shell, so they run on macOS and Linux only.

Guided-setup tests use temporary Git repositories and fake CLI discovery. They cover wizard/flag equivalence, private disabled output, task-file handling, ordered account routing, operating limits, cancellation, existing-file preservation, and checkout/symlink rejection. Structured setup fixtures also cover JSON preview/create consistency, ordered account metadata without account paths, stdin bounds/UTF-8/errors/cancellation, and failed creation without a success report. They make no model calls and do not establish live account or IDE compatibility.

LaunchAgent tests use an injected fake launchctl and temporary private directories. They cover install/status/remove, unchanged holds and ownership, conflicting installers, duplicate refusal, failed bootstrap, interrupted removal, unknown registration, modified/symlinked files, checkout rejection, config-independent recovery, XML escaping, and state-directory binding. macOS also validates the generated plist with `/usr/bin/plutil -lint`. A read-only macOS 26.4 check confirmed exit 113 for a fictional missing service and exit 0 for its accessible GUI domain. These checks do not install a real service or establish login/logout/reboot behavior; live lifecycle and soak checks remain outstanding.

## On a machine or VM without Go

Build a bundle on a machine that has Go, copy it over, and run it there:

```sh
scripts/build-test-bundle.sh linux arm64 out/linux      # writes out/linux/bundle.tar.gz
scripts/build-test-bundle.sh windows arm64 out/windows  # writes out/windows/bundle.zip
```

Unpack the archive in a scratch directory on the target. Then run `src/run-tests.sh` on Linux or macOS, or this on Windows:

```powershell
powershell -ExecutionPolicy Bypass -File src\run-tests.ps1
```

Each package's test binary runs from its own directory, so fixtures resolve as they do under `go test`. The bundle also holds a `keepgoing` binary for smoke checks such as `keepgoing validate -c examples/keepgoing.bb.yaml`.

Service-executable inspection uses native temporary-file fixtures on macOS/Linux for matching/different content, symlinks, missing files, absent execute bits, denied reads (non-root), FIFO rejection/nonblocking open, size bounds, cancellation, and identity/metadata changes. A native fixture hashes the test executable; script fixtures have a marker proving they were never run. Fake-manager status tests verify both service backends, unchanged controls/recovery files, no provider calls, redaction, and removal with a missing executable. The comparison concerns on-disk files only; loaded process images, executable validity, signing, effective execute access, live service startup/recovery, and adversarial filesystem changes are not verified.

Linux service-to-daemon binding uses pure tables and fake-manager queries to cover matching identities, mismatches, reused PIDs with changed invocation IDs, old/manual daemons without identity, malformed/oversized/failed manager responses, and changed unit identity/state. A Linux-only integration fixture compares fake manager metadata with a real local authenticated responder using a fictional invocation environment; it checks human/JSON redaction, absent/stopped responders, unchanged private files/holds, and zero provider calls. Shared daemon-info tests cover optional metadata, invalid invocation redaction, backward-compatible responsiveness, and fresh challenge verification. This is not evidence of a live installed service, process-image identity, or macOS binding.

Child-input precedence is tested through the real fake-CLI adapter and supervisor poll with a three-second test deadline, separately from command-level control-cycle timing. It no longer assumes that notification scanning plus parent/child subprocess inspection always fits a 500 ms poll under race/build load. Existing daemon fixtures still verify early timer advancement, bounded slow commands, holds, tick-lock contention, and saved-cursor deduplication. A deterministic supervisor fixture cancels during observation after consuming a one-shot signal: no early check, replay, prompt, or hold mutation occurs, and the next ordinary tick still records the child's awaiting-user hold without sending or probing. Production polling limits and at-most-once notification semantics are unchanged.

## BB setup plugin

Run `npm ci`, `npm run typecheck`, and `npm test` in `integrations/bb-plugin-keepgoing`; `bb plugin build` checks bundle generation when the BB CLI is available. The plugin CI job runs typechecking and tests. SDK fake-host tests cover metadata resolution, host routing, private reference persistence and reload, and absence of thread creation/send calls. Controller fixtures cover preview/creation/start separation, stale input, repeated/concurrent requests, holds, failed diagnostics, and error redaction. A real local Node subprocess fixture verifies stdin and bounded output; it starts no agent. DOM fixtures cover the three explicit user actions and visible failure states. The public-SDK scanner checks package boundaries. None of this verifies live deployment, remote host connectivity, paid turns, or install-to-completion behavior.

Goal setup integration tests also accept `KEEPGOING_TEST_BINARY=/absolute/path/to/keepgoing`. With a trusted source-built CLI, the plugin host fixture previews and creates a disabled goal loop in a temporary directory, checks snapshot/reference storage and privacy, and traps any BB execution. The plugin job builds and supplies that executable. Without the variable, this one fixture is explicitly skipped; the SDK/DOM tests still run. This is actual CLI execution with an isolated destination and fake BB discovery, not live BB setup or provider verification.

The detached background-start fixture repeats on native Windows CI and, on failure, prints the named wait stage, a bounded snapshot of its synthetic control/state/incident/run files, local daemon-query evidence and adapter marker presence before cleanup. It never reads a configured user loop. The fixture first settles the saved pause, then requires a stop check to begin (or finish) within five seconds. It separately allows the configured observation/stop command timeouts for completion; slow OS subprocess startup must not be confused with delayed control polling. A timeout remains a failure requiring investigation. These snapshots do not establish live provider or service-installation behavior.

Daemon control-change regressions explicitly preserve file size and modification time while changing pause/stop, both before waiting and during a poll. They exercise atomic replacements and in-place writes, with the changed flag beyond a stream-copy buffer, and verify unchanged/missing controls do not cause repeated early checks. The metadata-only implementation failed the regression. Native Windows CI runs these cases explicitly; macOS/Linux include them in the full suite. This is synthetic filesystem evidence, not attribution of the earlier background-stop timeout or live service acceptance.

Control-snapshot fixtures deliberately hold the production reader open across `control.Save`, verify the original snapshot and replacement are distinct, and check read-only access, missing files, relative paths and accented Latin/CJK paths longer than 300 characters. The writer uses Windows POSIX rename flags; the first reader-sharing-only revision failed this held-reader test natively because legacy `MoveFileEx` still rejected replacement. Windows writer fixtures additionally verify read-only originals and staging cleanup, and inject typed unsupported/access/sharing failures to check no fallback, unchanged source/destination and handle release. A signature fixture saves a pause while its hashing reader remains open. The Windows-only comparison opens an explicit legacy handle without delete sharing, verifies replacement fails without changing controls, then closes it and verifies replacement succeeds; it does not assume future Go releases retain the old sharing mode. The Windows job explicitly runs these fixtures. Local macOS execution and Windows cross-compilation alone do not prove Windows sharing behavior; native execution must be recorded in the PR. This isolates a concrete reader/write conflict without claiming attribution of every earlier timeout or live service acceptance.

### Cursor CLI source adapter

The unreleased primary-only Cursor runner has native subprocess fixtures for stdin-only Unicode task transport, model/workdir/environment forwarding, active-send rejection, exact session reuse after adapter reconstruction, target separation and owned cancellation. Parser fixtures reject duplicate keys, conflicting or missing identities, result-before-init, missing/null booleans, truncated/malformed output, nonzero exits and output beyond the 8 MiB turn / 2 MiB event bounds. Missing identity refuses a fresh retry; common holds exercise the real factory without provider work. Schema/config tests refuse Cursor fallback paths. Doctor/status tests keep login and saved-session liveness explicitly unverified. Setup fixtures cover `agent` discovery rather than the desktop launcher, preserved existing default selection, private stdin/JSON preview and disabled task/goal creation, model persistence, unsupported account/fallback rejection without writes and a native executable trap proving setup never invokes Cursor.

Combined command fixtures additionally exercise active holds, completion while held, stop precedence, exact resumption after stop, unknown-error backoff and retry-budget exhaustion. Each invocation reloads config/control/state and reconstructs the adapter. The unexpected-crash fixture retains its own wrapper process handle through kill/wait, waits for the disposable child to exit, and resumes the initialized session after reconstruction; it never signals a PID from a file. These Go cases are command/adapter reconstruction checks. Separately, `scripts/smoke-recovery.py --include-cursor` drives a built binary through actual held-daemon SIGKILL/restart with a local Cursor executable, unknown partial-turn failure, exact session reuse after explicit resume, preserved controls/owner/send allowance and no notification replay. The source macOS/Linux CI smoke step runs this option; it does not install a service or call Cursor.

The Go fixtures run in the macOS/Linux full suite and Windows native runner job; Windows also explicitly runs the Cursor command journeys, guided setup and idle-hold factory cases. The separate Python held-daemon smoke runs only on macOS/Linux, not Windows. Passing compilation or fake execution does not establish real provider behavior. A local read-only installed prompt-function check is recorded in [Cursor evidence](cursor.md#evidence-and-next-gates); no live two-turn, provider cancellation, permission, quota or outage acceptance has been run for this adapter.

## Antigravity ACP internal gate

`go test -race ./internal/adapter/runner -run '^TestAntigravityACP'` exercises a pure ACP v1 gate with fictional messages. Fixtures cover truthful capabilities, exact opaque session reuse, request correlation, cancellation-only permission replies, input evidence that remains latched through completion/error/EOF, invalid envelopes, Unicode ambiguity, bounded frames/connection/request counts and typed-looking model text. The gate has no process execution, factory registration, setup choice or automatic-loop eligibility. See the [contract and remaining gates](antigravity.md#internal-acp-permission-gate). Owned bidirectional transport, durable supervisor holds, question handoff, installed-version compatibility and live acceptance were not exercised by these tests.

The internal ACP exchange adds injected stream tests and a two-way in-memory pipe peer. They verify fragmented LF framing, finite frame/connection reads, truncated EOF, local-input rejection before writes, prompt-attempt and permission-hold checkpoint ordering, checkpoint errors/cancellation, short writes without replay and redacted injected failures. Checkpoint callbacks are fakes: disk durability, supervisor hold recovery and process lifecycle were not exercised. The synchronous API has no wall-time bound for blocking reader/writer/callback implementations; the future owner must supply deadlines/closure. No provider was executed.
