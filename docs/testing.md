# Testing

For a built or unpacked executable, [release verification](release-verification.md) provides a provider-free setup smoke check, a [local recovery smoke check](release-verification.md#check-recovery-with-local-stand-ins), and a separate live walkthrough. Both scripts run in macOS/Linux CI. Recovery uses stand-in providers, a loopback webhook and actual temporary daemon processes; neither script certifies real provider sessions.

## Review and execution evidence

These checks guide new changes; adding them does not certify existing code or close roadmap acceptance criteria.

- **Validate environment-derived paths.** For settings whose contract requires an absolute path, reject empty or relative environment values before joining child paths or performing filesystem operations. If relative paths are supported, resolve them against a documented base rather than an incidental working directory. Test unset, empty, relative and non-ASCII values, including execution from another working directory. Absolute paths alone do not establish ownership, privacy or freedom from symlink races.
- **Prove cache behavior through dependencies.** Inject the underlying reader/provider and clock where relevant. Assert which calls occur on a miss, a hit, expiry and invalidation, and how failures affect cached data. Include changed target/account/model keys where those identities scope the cache. At least one cache-specific assertion should fail if caching is bypassed; identical returned values alone do not demonstrate a cache hit. Use local fakes, not paid provider calls.
- **Establish that checks actually ran.** A submitted command or silent wrapper exit is insufficient evidence. Verify the expected test summary, exit status and artifacts for the intended source commit. If a policy hook or expired execution lease refuses work, mark the check not run and inspect which operations executed before updating records or performing cleanup. Follow the local lease/approval rules; do not bypass a guard or assume another project's hook patterns and deadlines apply here.
- **Keep review inputs concrete.** Give a reviewer the exact diff/base/head, checks actually run, relevant contracts and a plain list of checks not run. An independent review, when available, should assess behavior and failure paths rather than inherit the author's conclusions. Reconcile findings before merge and update the PR description when the implementation changes. A review of an earlier head does not cover later edits; review never substitutes for current-head/current-base checks.

## Capability and documentation review

Apply this review before checking off a roadmap item and before merging changes to behavior, setup, limitations or release availability. Repeat it after review fixes or release-scope changes affect those claims. It is part of delivery, not a periodic cleanup deferred until the end of the roadmap.

1. **Compare claims with the final implementation.** Read the affected README sections and linked setup, operations and integration guides alongside the changed code and tests. Confirm supported targets, defaults, prerequisites, controls, failure behavior and limitations. New capabilities must be discoverable; removed or narrowed behavior must not remain advertised. Record the reviewed sections and corrections in the PR, or explain why they remain accurate without edits.
2. **Check the path a user follows.** Verify install/version guidance, example command names and flags, config-path handling, provider login prerequisites, creation versus start, and relevant links. Use the intended artifact's help or a safe fixture where feasible; never turn a documentation check into an unapproved live model call, login change or production control action. State commands not exercised and why.
3. **Separate availability from evidence.** Confirm the published release/tag and package version before naming a latest release. Label source-only changes as unreleased, and separately identify plugin/client distribution, installed-loop versions, fixture execution and live acceptance. Updating a source checkout does not update a release artifact, package or running supervisor. Avoid duplicating detailed evidence; link the authoritative verification record.
4. **Reconcile the roadmap and changelog.** Link completed work to its implementation and applicable test/live evidence. Keep partial acceptance unchecked with its remaining work explicit. Update release notes when their promised contents change; a docs-only correction must not imply a feature shipped or passed live tests. Close or revise dependent claims if a prerequisite changes.
5. **Report the result and next gap.** The PR and milestone check-in should say what changed for users, where it is available, what verified it and what remains open. The PR template's documentation review is a concrete record of this check, not an automatic correctness test. Missing evidence stays missing even when all documentation links and CI jobs pass.

## Lifecycle and platform review

Apply these checks when changing runners, stop commands, service integrations, installers or platform UI. They are review requirements, not claims that current implementations satisfy every case.

- **Prove process identity before stopping it.** A PID file and a successful liveness check establish neither ownership nor creation identity. Persisted wall-clock timestamps and command basenames alone are insufficient. Use native process identity/creation evidence or an authenticated owned control channel, and account for the race between validation and signalling. Unknown or mismatched identity must refuse destructive control. Test stale records left by abrupt termination, a live unrelated process at the recorded PID, legacy records lacking identity, and identity changes during inspection. Tests must use owned disposable processes or injected identities; never signal arbitrary host PIDs.
- **Consume machine interfaces.** Prefer native APIs or documented structured command fields to human-oriented output. Do not infer state from translated status words or decode a displayed path as if it were lossless. Where command output carries paths, round-trip a temporary path containing Latin accents, CJK characters and spaces. Include malformed/partial responses and the real encoding/localization failure shapes in fixtures.
- **Make regression fixtures fail before the fix.** Record which assertion reproduces the old behavior and run it against the pre-fix implementation when feasible. A fake that only returns idealized JSON/English/safe ASCII can miss the defect. Keep realistic failures synthetic and free of real transcripts, hostnames, account paths and secrets; label unobserved assumptions explicitly.
- **Distinguish compilation from execution.** Identify the CI job that compiles platform-specific code and the tests it actually executes. Cross-compilation, native test execution, installer testing and live VM acceptance are separate evidence. State architecture, OS, source commit and what was not run. Use existing CI or disposable test hosts; do not infer Windows execution from a generic green PR check.
- **Verify user-visible behavior at its boundary.** Add a DOM/browser or native assertion for a changed UI action where supported. Request owner-only VM/desktop checks only when required evidence cannot be obtained independently, and leave them marked not run. If screenshots are needed, capture the relevant window and sanitize hostnames and other private metadata before sharing; do not commit raw desktop captures.
- **Exercise the deployment environment.** If PowerShell is part of the supported path, test the supported language mode and prefer cmdlets for operations that must work under constrained language. Do not assume arbitrary .NET method calls are available. When Windows PowerShell 5.1 is supported, use ASCII script source or an explicitly tested encoding; test non-ASCII data separately. Verify actual subprocess/pipe encoding and console availability instead of assuming UTF-8 or a particular code page. An installation that requests elevation must show an accessible approval prompt in a visible user-initiated flow; a hidden background process is not an acceptable interactive installer test. Record the test host's accessible paths and sharing restrictions rather than generalizing one VM's setup to all Windows hosts.
- **Describe dependency limits honestly.** A dependent change must say what users can do before its prerequisite is available. Keep implemented, tested, released, installed and live-verified claims separate. Recheck the current head against current main after integration; a passing earlier base does not close the review.

The runner now exercises owned cancellation with native subprocess fixtures: legacy and mismatched records, changed saved PIDs, stale acknowledgements, old requests after a new turn, wrapper death, descendant cancellation, and accented Latin/CJK paths. The legacy-record regression failed against the old implementation before the fix. macOS/Linux full-suite CI and the dedicated Windows job execute these tests. These checks do not certify live provider cancellation, abrupt-death descendant cleanup, or hostile runtime-file writers.

## Stand-in executables in tests

Install any shell script a test executes with `internal/testexec`, not `os.WriteFile`: `testexec.Script(t, path, content)` for a script used by one test, `testexec.Shared` for content that many fixtures install unchanged. The content must begin with `#!/bin/sh`. In `cmd/keepgoing`, the `write` helper already does this for executable shell scripts.

The reason is a host behaviour, not style. macOS checks a file the first time it is executed and queues those checks across the whole machine, so the first run of a new script takes from half a second to many seconds while later runs take milliseconds. A test that writes a script and runs it under a deadline, a context timeout or a configured command timeout then fails when other tests are starting new scripts too, and passes alone. The helper runs the script once while the fixture is built, in a mode that exits before its body, so the cost is paid outside any deadline. On Linux and Windows it only writes the file.

To replace a script installed this way, call the helper again; never write through the path, because a shared script is a hard link. Scripts that are written but never executed, such as service-file fixtures, do not need it. Compiled fixtures are not covered.

## Scenario suite (T2)

`go test ./internal/scenario` drives the built binary through whole journeys. `TestMain` builds `cmd/keepgoing` and a stand-in for `bb`, `claude` and `codex` (`internal/scenario/standin`, a Go program, so no POSIX shell is needed); set `KEEPGOING_TEST_BINARY` to an absolute path to run the scenarios against another build. Every command runs as a separate process with an environment built from nothing: `PATH` holds only the stand-in and a link to `git`, `HOME` and the XDG directories are private, reports go to a local receiver that checks signatures, and `KEEPGOING_NET_PROBE_URL` points at a local connectivity target that can answer, drop the connection, or redirect to a captive portal's sign-in page. Time comes from `tick --now` and `status --now`; nothing sleeps for timing and nothing reaches a real network, agent or model.

Every step records four things: what the stand-in agents were sent (`bb thread tell`, `bb thread retry`, `bb thread spawn` and headless turns, with the probes run alongside), the holds in force, the reports delivered, and what `status --json`, `timeline --json` and `runs --json` say. Invariants run after every step: a check that starts on a hold sends nothing; a check exits 0 and is the latest check in both `status` and `timeline`, the three commands agree on the control state, and `runs` records as many send attempts as the agents received. The stand-in agents react to what they are sent: a turn starts, and fails at once with a network error while the provider is unreachable. A failing scenario prints its journal.

Scenarios:

- `TestScenarioFirstLoop`: `init`, a disabled check that runs no `bb` command, `enable`, a wake with the task, a working agent left alone, a wake after progress, the agent's own `complete` with one `complete` report, and completed checks that query nothing.
- `TestScenarioOutage`, at 20 minutes, 4 hours, 3 days and 3 weeks: the network drops mid-turn while a child works, BB retries and gives up, the host sleeps so checks run irregularly or not at all, the network returns behind a captive portal, the portal clears and the work completes. When the session is still failed half an hour after the network returns, a person retries it in BB and resumes the loop, as they must on main today.
- `TestScenarioLimitHandoffSwitchBack`: a limit that resets within `wait_if_reset_within` is waited out with nothing sent or probed; one that resets in five hours hands off to a BB fallback on another account after an exact probe of its model, with the model switch before the brief and one `handoff` report; the fallback works while the primary is left alone and unprobed, and redundancy is reported `degraded`; a fallback turn that finishes before the reset is woken, not switched; after the reset the loop switches back after an exact probe of the primary, then reports `recovered`.
- `TestScenarioNewConversationHandoff`, for each answer `bb thread spawn` can give: created; created but the answer lost, then found by its title; refused with an invocation code, so the attempt is uncounted, recorded in `runs` as `adapter_error`, and the next fallback takes the loop in the same check; and created but not listed under its title, so the loop is held for a person with one `await_user` report, no other fallback is tried, held checks run no `bb` command, `resume` looks again and holds again, and once the title is restored `resume` settles it on the created thread. Every case checks that later checks never create a second conversation, the first prompt continues the primary, the permission mode is explicit, and the `handoff` report says `newThread` without the thread ID.
- `TestScenarioHeadlessOutage`, for headless Claude Code and Codex at each outage length: the stand-in CLI's turns succeed, fail with the CLI's structured error, or print a captive portal's page, following the fake network. A broken turn, irregular checks, the portal and its clearing, then recovery by a re-prompt into the saved session (or, once held, by a person: `resume`, and when that holds again, `retarget primary` then `resume`, as today). Every turn after the first resumes exactly the saved session and carries the task. The harness waits for each detached turn to end before it records the step. It replaces `cmd/keepgoing/offline_scenario_test.go`.
- `TestScenarioHeadlessFirstTurnFails`: a first turn that fails before the CLI reports a session saves nothing, so each of the three re-prompts starts a new conversation with the whole task, then the loop is held with one `await_user` report. Today's behaviour, listed as a gap in [adapters](adapters.md).

**Known failures.** An assertion that fails on main because of open work is wrapped in `World.Known` with the work it waits on. It still runs on every build: while it fails the scenario passes and logs a line starting `KNOWN FAILURE [<work>]`; when it starts to pass the scenario fails with `FIXED KNOWN FAILURE`, so the change that fixes it must delete the marker and the assertion is enforced from then on. Nothing is skipped. List them with `go test ./internal/scenario -v -count=1 | grep 'KNOWN FAILURE'`. The work named today is network gating (#154), turn retry, child recovery, and two items with no open work: a captive portal is read as online, and the stall clock runs through an outage so a recovered turn is nudged at once.

Each scenario was run against a deliberately broken build to show it fails. For the handoff scenarios: treating an uncertain creation as refused (`bb`: return `ErrSpawnRefused` for a server error) fails the not-found case, which then hands the loop to the other fallback; skipping the model switch (`bb`: `Activate` does nothing) fails the handoff; ignoring the primary's reset time (`supervise`: `switchBackReady` never waits) fails the switch-back journey before the reset. For the first two: a completed loop that still queries its agent (`supervise`: drop `gate.Completed` from the hold check) fails both scenarios; ignoring BB's own retry (`decide`: never honour `Retrying`) fails the outage scenario at the retrying check; waiting on every error (`decide`: return `none` for the error state) turns known failures into `FIXED KNOWN FAILURE`.

Not covered yet: child failure reports, scheduler death, state upgrades, two supervisors, a full or unwritable state directory, fault injection (T3). The suite runs in the macOS and Linux CI jobs as part of the full suite; it is not yet run on Windows (T4), where the link to `git` and the environment need work.

## Timing-sensitive tests

Four causes were found behind intermittent failures, each reproduced before it was fixed. Use them when a test fails only sometimes.

- **A deadline that times the host, not the code.** macOS assesses a file the first time it is executed and serialises those assessments across the machine. A new shell script takes about half a second to start on an idle machine and many seconds when other processes are also starting new executables; later runs take milliseconds. CPU load alone does not reproduce this. Stand-in CLIs are therefore installed with `internal/testexec`, which runs each script once in a mode that exits before its body while the fixture is built, and hard-links scripts whose content is shared by many fixtures. Replace such a script with the same helper, never by writing through its path. New fixtures that execute a script under a deadline should use it. Compiled fixtures and scripts in service tests are not covered.
- **A retry budget that is a deadline in disguise.** A fixed number of short retries measures how slow the filesystem is. Retry on the condition itself and let the test timeout bound a real hang.
- **Two ready cases in one `select`.** Go chooses at random, so code that must not act after cancellation has to check the context when it receives the other event. `TestDaemonWaitNeverPollsAfterCancellation` holds a poll past several ticks to force both cases ready.
- **A reader blocking a writer on Windows.** An ordinary open handle prevents a file from being replaced. A polling test per record (`Test…SnapshotSavesWhileReadersPoll` for state, the send and progress ledgers, health, the incident and delivery journals, the registry and the daemon endpoint, plus `TestStateSnapshotSaveReplacesFileHeldByReader` and `TestTransferRecordReadsDoNotBlockControlOrStateSaves`) runs natively in the Windows job. The fallback for an unsupported rename and the reader's short retry are covered by injected error codes there, not by a real exFAT or network volume; the retry was added after the health polling test failed a read with access denied in two of five runs. A program outside keepgoing that opens these files without delete sharing can still block a save; one such failure of a control save was seen in a hundred Windows iterations and is not explained. Local macOS execution and cross-compilation say nothing about these tests.

Reproduce before changing anything: repeat the one test with `-count`, then add the pressure that matches the suspected cause (CPU, filesystem writes, or many first executions of new files). Record the failure rate before and after, and name what was not reproduced. Raising a timeout is a fix only when the deadline is shown to be the sole defect.

## Run discovery tests (D1, D2)

`go test -race ./internal/rundiscovery` exercises the pure identity and run-boundary contract with fictional caller-supplied IDs and timestamps: every run-boundary case, distinct attempts, run/session links and malformed input.

`go test -race ./internal/rungraph` exercises the persisted graph in temporary directories: legacy directories with no graph, boundaries derived from saved control state, intents left unconfirmed, direct lookup of every reference type, shared and multiple sessions, retention bounds, file mode and replacement under an open reader, and newer-schema, corrupt, aliased and conflicting records that must stay unread and unwritten. The Windows CI job runs this package natively.

`go test -race ./internal/supervise -run 'Graph|Tick.*Intent|Handoff.*Sessions|DryRuns|Unrecordable'` uses fake adapters. It shows the intent is on disk before the send, that an unusable graph leaves each tick's action, reason, sends, control state and saved check identical apart from one warning, that a completion recorded while a check is starting is not read as a reopen, and that an unrecordable chat identifier warns once.

`go test -race ./cmd/keepgoing -run 'RunReference|LostRunBoundary|ClientHoldRecords'` runs the real command entrypoint in separate OS processes against one state directory, with a shell stand-in for BB. It enables a loop, ticks, starts a daemon, kills it, starts another, and checks that the durable loop and run references are unchanged and that every send is its own attempt. This is the D1 restart evidence. It builds only on Unix because the stand-in is a shell script.

`go test -race ./cmd/keepgoing -run '^TestRuns'` exercises the `runs` reader against graphs written in temporary directories: loop, registry and exact-reference views, a text-mode walk of every documented path, evidence labels including a superseded chat, bounds, unreadable graphs answering `unavailable`, absent records, a stale registry binding, two registered loops with one name, held loops with the tick, control and graph locks held, and byte-for-byte unchanged files. The Windows CI job runs these natively. A Unix-only test follows real `enable`/`tick` commands with the reader and checks the stand-in provider was not called.

Routine identities are covered at each layer: parsing in `internal/rundiscovery`, routine and invocation lookup in `internal/rungraph`, a supplied identity that leaves a check's action unchanged in `internal/supervise`, and `--routine` on real `enable`, `tick` and `resume` commands in the Unix-only command tests. Those compare the whole check line, exit code and sends with and without the flag from identical state, and show a check still runs, with one warning, when the value cannot be recorded. A store test sends 400 distinct triggers at a graph with six runs and checks that no run, send, chat link or goal link is dropped. `registry add` recording a reference only when a graph exists is in `^TestRuns`.

Blockers are covered at each layer: the waiting record and its schema upgrade in `internal/rungraph`; a check recording the child picture by key only, and as unknown when it is incomplete, in `internal/supervise`; blocker, blocking-loop and owner projection in `^TestRuns`; and a Unix-only command test that runs a parent and a child loop at once against the stand-in provider and checks that reading and following the blocker sends nothing and changes no file in either loop.

Not exercised: a service-managed daemon restart, a host reboot, power loss (the flush before replacement is not tested), a real provider session, a real scheduler supplying a routine identity (only the flag was exercised), and any GUI reader. `keepgoing runs` has one [live check](run-discovery.md#live-check) on a BB target and one of [what a loop is waiting on](run-discovery.md#live-check-waiting-on), which showed a working child and the owner but not a failed, stuck or registered child; its headless, duplicate-name, registry and send traversal paths are fixture-only. Those need D4–D6 fixtures and live evidence where applicable. README artwork stays deferred.

## Adapter capability checks

`go test ./internal/adapter/capability` compares the [adapter capability matrix](adapters.md) with the code: the decision inputs each adapter's source refers to, the adapters the factory builds, the optional interfaces each implements, which adapters a check records a session for, and that every reference in the matrix names a file and test that exist. It also fails when `docs/adapters.md` differs from the table it is generated from. It reads source files and runs no provider.

`go test ./cmd/keepgoing -run TestOffline` runs the offline scenario for headless Claude Code and Codex through the real commands with stand-in CLIs and a moved check clock. It is Unix-only. The stand-ins' failure output is an assumption about the real CLIs, not an observation.

## On a machine or VM without Go

Build a bundle on a machine that has Go, copy it over, and run it there:

```sh
scripts/build-test-bundle.sh linux arm64 out/linux      # writes out/linux/bundle.tar.gz
scripts/build-test-bundle.sh windows arm64 out/windows  # writes out/windows/bundle.zip
```

Unpack the archive in a scratch directory on the target. Then run `src/run-tests.sh` on Linux or macOS, or this on Windows:

```powershell
powershell -ExecutionPolicy Bypass -File src\run-tests.ps1
```

Each package's test binary runs from its own directory, so fixtures resolve as they do under `go test`. The bundle also holds a `keepgoing` binary for smoke checks such as `keepgoing validate -c examples/keepgoing.bb.yaml`.

Two workflows produce the five checks on a pull request. `checks.yml` runs the build, test, Windows and plugin jobs when a pull request is opened, pushed to or reopened, on pushes to `main`, and on manual dispatch. `contributions.yml` runs only `Contribution metadata`, the one check that reads the title and description, and also runs when those are edited. Editing a description therefore re-runs that one job and leaves the other four results on the head commit untouched; it does not start or cancel a build. The two results come from different runs, so cite both run links when the metadata check matters. Changing a pull request's base branch does not by itself re-run the build jobs: merge the new base into the branch, which branch protection requires anyway, or close and reopen the pull request.

## Antigravity ACP internal gate

`go test -race ./internal/adapter/runner -run '^TestAntigravityACP'` exercises a pure ACP v1 gate with fictional messages. Fixtures cover truthful capabilities, exact opaque session reuse, request correlation, cancellation-only permission replies, input evidence that remains latched through completion/error/EOF, invalid envelopes, Unicode ambiguity, bounded frames/connection/request counts and typed-looking model text. The gate has no process execution, factory registration, setup choice or automatic-loop eligibility. See the [contract and remaining gates](antigravity.md#internal-acp-permission-gate). Owned bidirectional transport, durable supervisor holds, question handoff, installed-version compatibility and live acceptance were not exercised by these tests.

The internal ACP exchange adds injected stream tests and a two-way in-memory pipe peer. They verify fragmented LF framing, finite frame/connection reads, truncated EOF, local-input rejection before writes, prompt-attempt and permission-hold checkpoint ordering, checkpoint errors/cancellation, short writes without replay and redacted injected failures. Checkpoint callbacks are fakes: disk durability, supervisor hold recovery and process lifecycle were not exercised. The synchronous API has no wall-time bound for blocking reader/writer/callback implementations; the future owner must supply deadlines/closure. No provider was executed.

The unregistered [detached runner](antigravity.md#detached-runner) has native fixtures in which the test binary is a stand-in ACP agent: two turns with exact resume after rebuilding the adapter, on-disk reservation and hold records checked by the stand-in before the frames they guard, a held permission request across rebuilt adapters, unknown-only failures, bounded setup and exit, owned stop with a forged saved process ID, a worker killed by its own agent right after the prompt, leaving an unconfirmed reservation; a turn recorded without a confirmed worker, which fails closed; a worker overtaken by a later turn, which neither prompts nor writes the shared exit record; and refused inconsistent records. A separate test shows that the variable selecting the ACP worker, inherited or set in a loop's env, cannot divert a Claude, Codex or Cursor turn. They run in the macOS/Linux full suite and the Windows native runner job. Antigravity is not installed anywhere these run: supported-version evidence is none, and no supervisor check uses the real runner type.

The [saved interaction hold](antigravity.md#saved-interaction-hold) has runner, decision and supervisor fixtures. A fictional permission exchange checks the on-disk records from its writer before the prompt and cancellation frames. Reconstructed readers then verify that a restarted exchange cannot reserve a second prompt, and that every refusal leaves file names and bytes unchanged and echoes no content, path or identity. Concurrent reservations admit one prompt, evidence without its own reservation is refused while another identity reserves, and saves succeed while readers hold every existing record open. No fixture places a reader between a record's publication and the removal of its temporary name; on Windows that window is reached only by chance in the concurrent cases, which tolerate a leftover temporary file there and fail on one elsewhere. Supervisor ticks rebuild a stand-in adapter over the real records each time: the awaiting-user hold is saved before the progress fingerprint in the default configuration, repeated restarts neither observe nor send, an explicit resume is not held again once adopted, and a simulated adoption failure costs one more resume instead of losing the hold. Stop, pause, dry runs, an unsaved hold and holds owned by other rules are table cases. The runner cases, including the open-reader and concurrency fixtures, run in the native Windows runner job as well as the macOS/Linux suite; the supervisor cases run on macOS/Linux only, and the unsaved-hold case needs symlinks. Not exercised: a registered adapter, an ACP subprocess, a killed process, power loss or a failed sync, filesystems without hard links, a configured no-progress timeout or yield ending the tick before observation, turn rollover, question handoff or any live provider.
