# Testing

For a built or unpacked executable, [release verification](release-verification.md) provides a provider-free setup smoke check, a [local recovery smoke check](release-verification.md#check-recovery-with-local-stand-ins), and a separate live walkthrough. Both scripts run in macOS/Linux CI. Recovery uses stand-in providers, a loopback webhook and actual temporary daemon processes; neither script certifies real provider sessions.

## Review and execution evidence

These checks guide new changes; adding them does not certify existing code or close roadmap acceptance criteria.

- **Validate environment-derived paths.** For settings whose contract requires an absolute path, reject empty or relative environment values before joining child paths or performing filesystem operations. If relative paths are supported, resolve them against a documented base rather than an incidental working directory. Test unset, empty, relative and non-ASCII values, including execution from another working directory. Absolute paths alone do not establish ownership, privacy or freedom from symlink races.
- **Prove cache behavior through dependencies.** Inject the underlying reader/provider and clock where relevant. Assert which calls occur on a miss, a hit, expiry and invalidation, and how failures affect cached data. Include changed target/account/model keys where those identities scope the cache. At least one cache-specific assertion should fail if caching is bypassed; identical returned values alone do not demonstrate a cache hit. Use local fakes, not paid provider calls.
- **Establish that checks actually ran.** A submitted command or silent wrapper exit is insufficient evidence. Verify the expected test summary, exit status and artifacts for the intended source commit. If a policy hook or expired execution lease refuses work, mark the check not run and inspect which operations executed before updating records or performing cleanup. Follow the local lease/approval rules; do not bypass a guard or assume another project's hook patterns and deadlines apply here.
- **Keep review inputs concrete.** Give a reviewer the exact diff/base/head, checks actually run, relevant contracts and a plain list of checks not run. An independent review, when available, should assess behavior and failure paths rather than inherit the author's conclusions. Reconcile findings before merge and update the PR description when the implementation changes. A review of an earlier head does not cover later edits; review never substitutes for current-head/current-base checks.

## Capability and documentation review

Apply this review before checking off a roadmap item and before merging changes to behavior, setup, limitations or release availability. Repeat it after review fixes or release-scope changes affect those claims. It is part of delivery, not a periodic cleanup deferred until the end of the roadmap.

1. **Compare claims with the final implementation.** Read the affected README sections and linked setup, operations and integration guides alongside the changed code and tests. Confirm supported targets, defaults, prerequisites, controls, failure behavior and limitations. New capabilities must be discoverable; removed or narrowed behavior must not remain advertised. Record the reviewed sections and corrections in the PR, or explain why they remain accurate without edits.
2. **Check the path a user follows.** Verify install/version guidance, example command names and flags, config-path handling, provider login prerequisites, creation versus start, and relevant links. Use the intended artifact's help or a safe fixture where feasible; never turn a documentation check into an unapproved live model call, login change or production control action. State commands not exercised and why.
3. **Separate availability from evidence.** Confirm the published release/tag and package version before naming a latest release. Label source-only changes as unreleased, and separately identify plugin/client distribution, installed-loop versions, fixture execution and live acceptance. Updating a source checkout does not update a release artifact, package or running supervisor. Avoid duplicating detailed evidence; link the authoritative verification record.
4. **Reconcile the roadmap and changelog.** Link completed work to its implementation and applicable test/live evidence. Keep partial acceptance unchecked with its remaining work explicit. Update release notes when their promised contents change; a docs-only correction must not imply a feature shipped or passed live tests. Close or revise dependent claims if a prerequisite changes.
5. **Report the result and next gap.** The PR and milestone check-in should say what changed for users, where it is available, what verified it and what remains open. The PR template's documentation review is a concrete record of this check, not an automatic correctness test. Missing evidence stays missing even when all documentation links and CI jobs pass.

## Lifecycle and platform review

Apply these checks when changing runners, stop commands, service integrations, installers or platform UI. They are review requirements, not claims that current implementations satisfy every case.

- **Prove process identity before stopping it.** A PID file and a successful liveness check establish neither ownership nor creation identity. Persisted wall-clock timestamps and command basenames alone are insufficient. Use native process identity/creation evidence or an authenticated owned control channel, and account for the race between validation and signalling. Unknown or mismatched identity must refuse destructive control. Test stale records left by abrupt termination, a live unrelated process at the recorded PID, legacy records lacking identity, and identity changes during inspection. Tests must use owned disposable processes or injected identities; never signal arbitrary host PIDs.
- **Consume machine interfaces.** Prefer native APIs or documented structured command fields to human-oriented output. Do not infer state from translated status words or decode a displayed path as if it were lossless. Where command output carries paths, round-trip a temporary path containing Latin accents, CJK characters and spaces. Include malformed/partial responses and the real encoding/localization failure shapes in fixtures.
- **Make regression fixtures fail before the fix.** Record which assertion reproduces the old behavior and run it against the pre-fix implementation when feasible. A fake that only returns idealized JSON/English/safe ASCII can miss the defect. Keep realistic failures synthetic and free of real transcripts, hostnames, account paths and secrets; label unobserved assumptions explicitly.
- **Distinguish compilation from execution.** Identify the CI job that compiles platform-specific code and the tests it actually executes. Cross-compilation, native test execution, installer testing and live VM acceptance are separate evidence. State architecture, OS, source commit and what was not run. Use existing CI or disposable test hosts; do not infer Windows execution from a generic green PR check.
- **Verify user-visible behavior at its boundary.** Add a DOM/browser or native assertion for a changed UI action where supported. Request owner-only VM/desktop checks only when required evidence cannot be obtained independently, and leave them marked not run. If screenshots are needed, capture the relevant window and sanitize hostnames and other private metadata before sharing; do not commit raw desktop captures.
- **Exercise the deployment environment.** If PowerShell is part of the supported path, test the supported language mode and prefer cmdlets for operations that must work under constrained language. Do not assume arbitrary .NET method calls are available. When Windows PowerShell 5.1 is supported, use ASCII script source or an explicitly tested encoding; test non-ASCII data separately. Verify actual subprocess/pipe encoding and console availability instead of assuming UTF-8 or a particular code page. An installation that requests elevation must show an accessible approval prompt in a visible user-initiated flow; a hidden background process is not an acceptable interactive installer test. Record the test host's accessible paths and sharing restrictions rather than generalizing one VM's setup to all Windows hosts.
- **Describe dependency limits honestly.** A dependent change must say what users can do before its prerequisite is available. Keep implemented, tested, released, installed and live-verified claims separate. Recheck the current head against current main after integration; a passing earlier base does not close the review.

The runner now exercises owned cancellation with native subprocess fixtures: legacy and mismatched records, changed saved PIDs, stale acknowledgements, old requests after a new turn, wrapper death, descendant cancellation, and accented Latin/CJK paths. The legacy-record regression failed against the old implementation before the fix. macOS/Linux full-suite CI and the dedicated Windows job execute these tests. These checks do not certify live provider cancellation, abrupt-death descendant cleanup, or hostile runtime-file writers.

Whether a headless turn is running is decided by a lock, not a PID. The turn wrapper holds `turn.lock` from its start until it publishes its exit code, and the operating system releases it if the wrapper ends any other way. `Start` returns only once the wrapper holds it, and a read that lands in the moment between release and the exit code waits for the code. So "running" means the lock is held. Fixtures cover a three-week-old record whose PID belongs to a live unrelated process (crashed), a held lock with no usable PID (running), a recorded exit code (finished), a real wrapper killed with SIGKILL and its record then pointed at a live PID (crashed, Unix only), and a record from an older build, which is still judged by its PID. Both of `Start`'s waits are tested with a shortened limit: a held lock (refused, nothing changed, no process started) and a wrapper that never takes the lock (abandoned, crashed on every read, the next start runs), the second for the Antigravity runner too, which records the turn as not started. A binary on disk that answers with another wrapper label, and one that does not answer in time, are each refused with their own reason before anything is created, and the answer is kept until the file is replaced or changes. A check whose send is refused this way spends no send and no re-prompt over eight checks, reports once, and is shown by `status` and `doctor` (`TestARefusedStartSpendsNothingAndIsReportedOnce`, `TestStatusAndDoctorSayWhyNoTurnCanBeStarted`). A start that fails after the previous turn was set aside (a missing working directory) puts it back, and one that cannot put a file back says which and leaves the turn failed and incomplete, not finished and empty. A Cursor loop whose first turn was abandoned sends again. Unix-only fixtures cover a previous turn whose files cannot be cleared, both with a read-only directory and with one immovable file after others were already moved (refused, every file as it was, the turn still finished, the agent not run), a wrapper that takes the lock after `Start` gave up (it runs nothing), a wrapper kept alive for three seconds after publishing (the lock is already free), and two `Start` calls at once (the agents never overlap). Each of the first three was checked to fail on every run with its guard removed. Also covered: something unreadable in place of the exit code, a finishing marker a minute old, and an older build's record from before the machine started, with the machine's start injected and read for real once per platform. The Windows job runs the cross-platform cases natively. A real reboot was not run, and neither was an upgrade of a loop that was stuck.

### Daemon stop with an unavailable configuration file

The unreleased stop-only path reuses the existing adapter stop contract; it adds no PID signalling or process discovery. Unix command fixtures use a fictional BB target and stand-in executable, isolated runtime storage, and cancellation of only their own daemon. They exercise a moved or unreadable source, no continue sent, the structured last-read timestamp in state and log, session-claim contention followed by release, a transferred target, readable invalid content, dry runs, a failed stop retried at the control poll, and the ordinary interval after a completed stop. Config tests distinguish unreadable sources from changed and oversized readable files, including a changed primary alongside a missing fallback. A deterministic command fixture restores an unchanged or retargeted source after the preliminary eligibility check and proves the check under the tick lock refuses the retained configuration. Supervisor tests refuse a last-configuration check unless it is stop-only, before observing or sending. Monitor assertions cover the retry and control-change early-return paths so a pass is completed rather than read as sleep.

These are native fixture checks on macOS, not live BB/provider stop acceptance. The daemon command fixtures are Unix-only; cross-compilation does not establish Windows execution. No installed service restart, reboot, external scheduler or Linux/Windows native acceptance was run for this change. The existing process-identity contract and legacy/stale runner cases are unchanged. No UI action changes; dedicated configuration-unavailable reports and status/panel wording remain follow-up work. See the [operations limits](operations.md#when-the-configuration-file-is-unavailable). Record exact commands, source head, regression/mutation evidence and platform results in the review handoff.

## Stand-in executables in tests

Install any shell script a test executes with `internal/testexec`, not `os.WriteFile`: `testexec.Script(t, path, content)` for a script used by one test, `testexec.Shared` for content that many fixtures install unchanged. The content must begin with `#!/bin/sh`. In `cmd/keepgoing`, the `write` helper already does this for executable shell scripts.

The reason is a host behaviour, not style. macOS checks a file the first time it is executed and queues those checks across the whole machine, so the first run of a new script takes from half a second to many seconds while later runs take milliseconds. A test that writes a script and runs it under a deadline, a context timeout or a configured command timeout then fails when other tests are starting new scripts too, and passes alone. The helper runs the script once while the fixture is built, in a mode that exits before its body, so the cost is paid outside any deadline. On Linux and Windows it only writes the file.

To replace a script installed this way, call the helper again; never write through the path, because a shared script is a hard link. Scripts that are written but never executed, such as service-file fixtures, do not need it. Compiled programs go in a `testexec.Dir`; see below.

### Executables that tests run

A test that creates an executable and runs it is exposed to one more host behaviour: **macOS can refuse a file it has not run before, and a refusal kills the process as it starts.** The caller sees `signal: killed` with no deadline of its own involved. It happens on a busy machine, and it was behind a day of reports of tests that failed once and then passed.

The evidence is in the system log. The kernel says which file it refused, and the policy daemon says why:

```text
kernel: (AppleSystemPolicy) ASP: Security policy would not allow process: 55465, /private/var/folders/…/T/TestScenarioUpgradeFromEachReleasev0.1.0…/001/bin/claude
syspolicyd: [com.apple.syspolicy.exec:default] Couldn't find a cached target for <private> during malware scan
```

Find them with `/usr/bin/log show --last 1h --predicate 'eventMessage CONTAINS "Security policy would not allow process"'`. Write the full path: in zsh, plain `log` is a shell builtin that takes these arguments and prints nothing useful, which hides the evidence. It is not memory pressure: the same log held no `memorystatus` or Jetsam kill, only non-fatal limit notes for unrelated applications. And no test signals a process by a saved ID.

On the day this was found, with nine lanes testing on one machine, the two and a half hours the log still held (21:38 to 00:00) had 166 refusals:

| Refused file | Count | Whose |
| --- | --- | --- |
| scenario stand-ins (`bb`, `claude`, `codex`), linked into a new directory for every scenario | 62 | `internal/scenario`, before the change below |
| `launcher`, built into a new temporary directory | 80 | a test suite not yet on `main` |
| `npx-cli.js` | 16 | not a keepgoing test: another tool's Node installation under the home directory |
| `fictional keepgoing`, a script written into a new directory per test | 3 | `integrations/macos` Swift tests |
| a defined-agent stand-in, two stand-ins in review scratch directories, the shared scenario directory during its own first runs | 7 | |
| any script installed with `testexec.Script` or `testexec.Shared` | 0 | `cmd/keepgoing`, `internal/adapter/*`, `internal/probe`, `internal/supervise` |

The last row is the point: suites that run each new file once while building the fixture were not refused during a test, although they ran all day. A refusal lands on whoever runs a file first.

**The rule.** Do not let a test be the first to run a file, and do not create a new path for the same program in every test. `internal/testexec` has both halves:

- `testexec.Script` and `testexec.Shared` for shell scripts, as above. Their first run now retries a launch that was ended by a signal; a first run that ends on its own with a non-zero exit fails the installation, because the guard always exits 0.
- `testexec.Dir` for compiled programs: one directory for a whole test binary, created in `TestMain` or once per test that builds something. `Build` compiles a Go package into it (a build gets five minutes), `Alias` gives a program a second name, `Host` links one host command such as `git`, and each of them runs the new file once as it is added (`testexec.RunOnce`), retrying a launch ended by a signal up to 20 times. Hand tests the directory's path; do not copy or link its files into a directory per test.
- A file still refused after 20 launches is reported as `ENVIRONMENT FAILURE: the host ended <path> by a signal on each of 20 launches`, naming the path. It is the host's failure and says nothing about the code under test.

**What uses it.** The scenario suite builds one directory with `bb`, `claude`, `codex`, `example-agent` and a link to `git`, and the `keepgoing` binary beside it, in `TestMain`; every scenario uses that directory as its whole `PATH`. `TestStartBackgroundProcess` builds its two programs through it. The Swift client tests cannot use a Go helper, so their fixture does the same thing itself: the script gets the same first line, is run once, and a launch ended by a signal is retried.

Measured for the scenario suite with the old and new harness alternating for 17 minutes under a load average of 40 to 50:

| Harness | Failing runs | Refusals logged for its paths |
| --- | --- | --- |
| Stand-ins linked into a new directory per scenario | 4 of 40 | 20 |
| One shared directory, each file run once first | 0 of 40 | 0 |

Not covered: the two Python smoke scripts write their own stand-in scripts and run a freshly built binary, and do not retry; the Swift change was checked for syntax and by building the package here, and runs only in the macOS CI job (this machine has no XCTest); and nothing here was observed on Linux or Windows, where no such refusal is known.

## Scenario suite (T2)

`go test ./internal/scenario` drives the built binary through whole journeys. `TestMain` builds `cmd/keepgoing` and a stand-in for `bb`, `claude` and `codex` (`internal/scenario/standin`, a Go program, so no POSIX shell is needed); set `KEEPGOING_TEST_BINARY` to an absolute path to run the scenarios against another build. Every command runs as a separate process with an environment built from nothing: `PATH` holds only the stand-in and a link to `git`, `HOME` and the XDG directories are private, reports go to a local receiver that checks signatures, and `KEEPGOING_NET_PROBE_URL` (the variables are given their [earlier names](configuration.md#environment-variables) here, so the journeys also run against builds from before the rename and show those names still work) points at a local connectivity target that can answer, drop the connection, or redirect to a captive portal's sign-in page. Time comes from `tick --now` and `status --now`; nothing sleeps for timing and nothing reaches a real network, agent or model.

Every step records four things: what the stand-in agents were sent (`bb thread tell`, `bb thread retry`, `bb thread spawn` and headless turns, with the probes run alongside), the holds in force, the reports delivered, and what `status --json`, `timeline --json` and `runs --json` say. Invariants run after every step: a check that starts on a hold sends nothing; a check exits 0 and is the latest check in both `status` and `timeline`, the three commands agree on the control state, and `runs` records as many send attempts as the agents received. The stand-in agents react to what they are sent: a turn starts, and fails at once with a network error while the provider is unreachable. A failing scenario prints its journal.

**Stand-ins are run once before any scenario, from one shared directory**, built with `testexec.Dir`, because macOS can refuse a file it has not run before and kill the process as it starts. The cause, the log evidence and the measurements are under [executables that tests run](#executables-that-tests-run).

**A stand-in that is ended early is still an environment failure.** Each stand-in marks its start and its own end, and after every command the harness compares the two and reads the command's error output for a killed process. A difference stops the scenario with `ENVIRONMENT FAILURE`, naming the step, before any expectation about the product is evaluated: a check that loses its stand-in records that it could not observe, which is correct, and `status` keeps what it knew (for example the time a network outage began), but the scenario's next expectation would fail for a reason that has nothing to do with the product. Rerun; it is not a product result. `TestHarnessNoticesAStandInEndedEarly` covers the rule.

Scenarios:

- `TestScenarioFirstLoop`: `init`, a disabled check that runs no `bb` command, `enable`, a wake with the task, a working agent left alone, a wake after progress, the agent's own `complete` with one `complete` report, and completed checks that query nothing.
- `TestScenarioOutage`, at 20 minutes, 4 hours, 3 days and 3 weeks: the network drops mid-turn while a child works, BB retries and gives up, the host sleeps so checks run irregularly or not at all, the network returns behind a captive portal, the portal clears and the work completes. The first check after the portal clears retries the failed turn once, with no new prompt, and the loop recovers without a person. The child's failed turn is not retried, which is the known failure below.
- `TestScenarioOutageHungTurn`: the same outage with a turn that never fails, because the host sleeps mid-request and BB still shows it active. A session that looks stalled while offline is neither nudged nor held, and once the network is back it is not nudged for the time it could not work.
- `TestScenarioDeclinedRetryNotice`: a BB turn fails while the provider still announces a retry. With nothing saying the retry is dead the notice is waited out; with a decline recorded by BB's retry plugin the next check retries the failed turn, without a second copy of the prompt.
- `TestScenarioLimitHandoffSwitchBack`: a limit that resets within `wait_if_reset_within` is waited out with nothing sent or probed; one that resets in five hours hands off to a BB fallback on another account after an exact probe of its model, with the model switch before the brief and one `handoff` report; the fallback works while the primary is left alone and unprobed, and redundancy is reported `degraded`; a fallback turn that finishes before the reset is woken, not switched; after the reset the loop switches back after an exact probe of the primary, then reports `recovered`.
- `TestScenarioLimitWhileChildrenWork`: the supervised conversation reaches its usage limit while a child it started is still working, and again with a child listing that cannot be read. Child work keeps an idle parent from being woken but does not hold back a parent in error: the loop moves to its confirmed fallback at the next check, and the child is never sent anything.
- `TestScenarioSchedulerDeathAndRestart`, with a stand-in scheduler that, like a BB automation, disables itself after three consecutive failing exits and treats exit 75 as success. First, BB cannot be reached for three checks: each exits 0 with outcome `failed`, sends nothing, is reported as one `error`, and `status` counts them (`failedChecks` 1, 2, 3 since the first), so the scheduler keeps running; when BB is back the next check wakes the session and the count clears. Then the scheduler is moved to another BB thread: three checks are refused with exit 1 before any `bb` command runs, nothing is recorded or reported, and the scheduler disables itself. For three hours nothing runs, is sent or is reported, and `status` says the history is stale with the reason `no recent check; inspect the supervisor and its scheduler`. Restarted under the loop's own thread, the first check wakes the idle session once and the next leaves it to work: three wakes in the whole journey. Mutations that fail it: a failed check exiting 1 again, a failed-check count that never clears, a check that does not verify its owner, and a history that is never stale.
- `TestScenarioNewConversationHandoff`, for each answer `bb thread spawn` can give: created; created but the answer lost, then found by its title; refused with an invocation code, so the attempt is uncounted, recorded in `runs` as `adapter_error`, and the next fallback takes the loop in the same check; and created but not listed under its title, so the loop is held for a person with one `await_user` report, no other fallback is tried, held checks run no `bb` command, `resume` looks again and holds again, and once the title is restored `resume` settles it on the created thread. Every case checks that later checks never create a second conversation, the first prompt continues the primary, the permission mode is explicit, and the `handoff` report says `newThread` without the thread ID.
- `TestScenarioUpgradeFromEachRelease`, for v0.1.0 to v0.1.5: today's build runs on the state directory that release's own binary left behind (`internal/scenario/testdata/released/<version>/state`): a loop held for a person, with a wake and one re-prompt in its history. The first check honours the hold (no `bb` command, no send, no report), the note and the saved re-prompt count and last send time are intact, and for v0.1.3 and later the journal's earlier records are still in `timeline`. After `resume` the failed turn is retried once, the session is left to work, woken after progress, and completed: two sends in the whole journey, neither a repeat. `testdata/released/generate.sh` rebuilds the fixtures by checking out and building each tag and driving it through one journey against the stand-in `bb`; it needs the tags and a work directory outside the checkout. The fixtures hold no path and no real identifier; `control.json` and journal timestamps are the wall clock of the day they were generated.
- `TestScenarioFilesFromANewerBuild`: the rollback direction. Old releases cannot be built in CI, so this build plays the older one against files given a schema or record kind it does not know. With the incident journal one schema ahead, a check still retries the failed turn but exits 1 with `tick: incident history unavailable; check private state storage`, `timeline` exits 1 with its source unavailable, `pause` is saved with a warning and exit 1 and then holds, and the journal is left byte for byte. With a run graph holding an unknown record kind, the check does the same work with exit 0 and one warning, `runs` exits 1 with `graph: corrupt`, and the graph is left byte for byte. The same commands were run once by hand with the real v0.1.5 binary against a state directory today's source had written to; the messages matched and are recorded in [operations](operations.md#upgrading-and-rolling-back). Mutations that fail these two: a hold not honoured, saved counters dropped on load, an older journal discarded on upgrade, and a newer journal silently reset.
- `TestScenarioUnwritableStateDirectory` (macOS and Linux; it needs an ordinary user, because root can write a read-only directory): the state directory becomes read-only while the session is in error. Every check exits 1 and names the cause (`permission denied`). `status` still works, and `pause` fails with exit 1. `state.json`, `control.json`, the journal and the run graph are left byte for byte, and no temporary file is left. Once the directory is writable again, the next check retries the failed turn and counts it. The record of a send is saved before the send, with or without `limits.max_sends`, so it cannot be saved and nothing is sent. Before (v0.2.0), without a send allowance every check re-prompted and none was counted, so the re-prompt cap never ended in a hold: six checks, six retries.
- `TestScenarioNoRoomToWrite` (macOS and Linux), with an idle session and with one in error: the disk is full. The harness runs `keepgoing` with a zero file-size limit, under which creating a file works and writing into it fails with `file too large`, as on a full disk; the stand-ins lift the limit for themselves. Checks exit 1 naming the cause and send nothing, `pause` fails with exit 1, `status` works, no record changes or is truncated, and no temporary file is left. With room again, the next check wakes the idle session or retries the failed turn. Nothing is sent because the record of the send cannot be saved before it is made (see [a send recorded before it is made](operations.md#a-send-recorded-before-it-is-made)); on a full disk the BB log cursor also fails to save first, which makes the retry state unverified, so either alone keeps the send from being made. Mutations that fail these two: a control file written in place instead of replaced, a temporary file not removed, a check that could not be recorded exiting 0, and a send allowed through when its reservation could not be saved.
- `TestScenarioHeadlessOutage`, for headless Claude Code and Codex at each outage length: the stand-in CLI's turns succeed, fail with the CLI's structured error, or print a captive portal's page, following the fake network. A broken turn, irregular checks, the portal and its clearing, then recovery by a re-prompt into the saved session (or, once held, by a person: `resume`, and when that holds again, `retarget primary` then `resume`, as today). Every turn after the first resumes exactly the saved session and carries the task. The harness waits for each detached turn to end before it records the step. It replaces `cmd/keepgoing/offline_scenario_test.go`.
- `TestScenarioHeadlessFirstTurnFails`: a first turn that fails before the CLI reports a session saves nothing, so each of the three re-prompts starts a new conversation with the whole task, then the loop is held with one `await_user` report. Today's behaviour, listed as a gap in [adapters](adapters.md).
- `TestScenarioChildFailureNoticeAndReport`, with lane recovery off (the default): a conversation hands work to two children and waits. One fails while the other works: the owner gets one `child_error` report at once, carrying counts and no child identity, and the waiting conversation is told an hour after its last message with the notice alone (`[keepgoing:child-errors count=1 running=1]`, no task prompt). A re-failure 38 minutes after recovery says nothing; a failure 80 minutes after recovery is reported again and the notice ends the next ordinary wake, after the task. A third child that fails during a pause is neither observed nor reported until `resume`, when the first check reports it. At every step no child is sent anything, and over the whole journey the only `bb` commands naming a child read its status or pending interactions. Two assertions are known failures: see the child report episode below. Mutations that fail it: forgetting a recovered child at once, dropping the spacing of the notice-only wake, never adding the notice, and a pause that does not stop the check.
- `TestScenarioTwoSupervisorsOnOneLoop`: two callers for one loop. A check held in the middle of observing the session (the stand-in `bb` can hold `thread show` until the test releases it) makes a second check exit 75, `another tick holds the lock; skipping`, before it runs any `bb` command, and the session gets one wake. A second daemon exits 75, `another daemon is running for example-loop`. A check from another BB thread is refused with exit 1. After `enable --take-over` from that thread (which waits for the tick lock the old owner's daemon takes for each control poll), the daemon the old owner started stops by itself within seconds, sending nothing, and the new owner's daemon starts; a check from the old owner then does no work (exit 1 for its ownership, or 75 when the new daemon is in the middle of a check, because the tick lock is taken before ownership is checked). Mutations that fail it: no tick lock, no daemon lock, a daemon that ignores a takeover, and checks that do not verify their owner.
- `TestScenarioTwoLoopsOnOneSession`: two separately configured loops, each with its own state directory, are set up on one BB thread. Enabling the second is refused, naming the first, and succeeds with `--allow-second-loop` and a warning. Checked one after the other, the second sees the session working and sends nothing. Checked at the same moment (the first held at `thread show`), the second finds the session claimed, sends nothing and exits 75 naming the first; the session is woken once. The same holds the other way round. Unit tests in `internal/session`, `internal/supervise` (`session_claim_test.go`) and `cmd/keepgoing` (`sessions_test.go`) cover the rest: the claim is held from observing until sending (a test that releases it in between fails), a stuck holder is reported once and a stop goes past it, a daemon retries a skipped stop within one control poll, a too-open directory is made `0700`, a planted file or symlink makes the check act on nothing, two spellings of one directory on the case-insensitive macOS disk are one session, a leftover holder file is not believed, and degraded and recovered reports are retried until delivered.

**Known failures.** An assertion that fails on main because of open work is wrapped in `World.Known` with the work it waits on. It still runs on every build: while it fails the scenario passes and logs a line starting `KNOWN FAILURE [<work>]`; when it starts to pass the scenario fails with `FIXED KNOWN FAILURE`, so the change that fixes it must delete the marker and the assertion is enforced from then on. Nothing is skipped. List them with `go test ./internal/scenario -v -count=1 | grep 'KNOWN FAILURE'`. The outage scenario runs twice at each length. With lane recovery on (`bb.children.retry_errored`) every assertion is enforced. With it off, its default, twelve assertions are still known failures, three at each length: a child's failed turn is not retried, so the session also receives the child-error notice. The network check closed the rest, including a captive portal read as online and the stall clock running through an outage.

**The child report episode, a known failure with no owner yet.** The documentation says a child that stayed out of error for `min_wake_interval` is forgotten, and that an episode of `child_error` reports ends when every covered child has been forgotten. When no check runs while the child is healthy (the host was asleep) and the child then fails again, that one check both forgets it and sees the new failure. The failure is reported, as it should be, but the report is numbered inside the old episode and counted against its cap of three, so a loop whose checks are irregular reaches the cap sooner than the documentation says. With a check in between, the next report is the first of a new episode. `TestScenarioChildFailureNoticeAndReport` marks the two report numbers it expects with `KNOWN FAILURE [child report episode when checks were missed, unassigned]`.

Each scenario was run against a deliberately broken build to show it fails. For the handoff scenarios: treating an uncertain creation as refused (`bb`: return `ErrSpawnRefused` for a server error) fails the not-found case, which then hands the loop to the other fallback; skipping the model switch (`bb`: `Activate` does nothing) fails the handoff; ignoring the primary's reset time (`supervise`: `switchBackReady` never waits) fails the switch-back journey before the reset. For the first two: a completed loop that still queries its agent (`supervise`: drop `gate.Completed` from the hold check) fails both scenarios; ignoring BB's own retry (`decide`: never honour `Retrying`) fails the outage scenario at the retrying check; waiting on every error (`decide`: return `none` for the error state) turns known failures into `FIXED KNOWN FAILURE`.

Fault injection (T3) is in its own section below. The suite runs in the macOS and Linux CI jobs as part of the full suite; it is not yet run on Windows (T4), where the link to `git` and the environment need work.

## Fault injection (T3)

`go test ./internal/scenario -run TestFault` breaks the supervisor on purpose, on the built binary, and checks what a restart does.

**Killed partway through a check** (`TestFaultKilledCheck`). A check records each send in `sends.json` before making it, and saves the rest of what it did at its end: `state.json`, then the run graph, the run log and the incident journal. The stand-in `bb` can kill the `keepgoing` process that called it once a command has answered (`kill.<command>` in its directory) or just before the command does anything (`killbefore.<command>`), and the webhook receiver can kill it while a report is arriving. So a kill can be placed just before a send, right after it and before anything else was saved, or after `state.json` and during a report. The restart runs one minute later.

| Killed | The restart | |
| --- | --- | --- |
| while observing, before anything is written | does the interrupted check: one turn retry, counted | enforced |
| right after a turn retry | waits out the backoff and counts the interrupted retry, found as a recorded send with no recorded outcome | enforced |
| right after a stop | sends the stop again, once (it cannot tell a stop made from one recorded and not made, and a second stop is harmless); the stop hold is kept | enforced |
| just before a stop is made | makes the stop; the stop hold is kept | enforced |
| right after a handoff brief | holds for a person (`a handoff brief to <fallback> may have been delivered ...`) and sends nothing to either conversation | enforced |
| right after a switch-back brief | holds for a person (`a switch-back brief to the primary may have been delivered ...`), does not wake the fallback and does not brief the primary again | enforced |
| right after a handoff brief, with two fallbacks, then `resume`, or `retarget` to the briefed fallback and `resume` (`TestFaultHandoffBriefKilledThenResumed`) | `resume` names the brief it settles and the route the loop continues on; the next check briefs no fallback, and the second fallback is never briefed | enforced |
| right after a send, with `max_sends` | the allowance already counts the interrupted send (it is reserved first) | enforced |
| while the report of a hold is delivered | keeps the hold, sends nothing, runs no `bb` command, does not report again (the hold is saved first) | enforced |
| while a report with no hold is delivered (a question on the thread) | sends nothing and does not report again | enforced |

Before (v0.2.0) the turn retry and the report were repeated, because a check saved what it did only at its end; each is now recorded in `sends.json` before it is made, and a record with no saved outcome is counted as sent, or, for a brief that may have put the task on a second conversation, holds for a person (see [a send recorded before it is made](operations.md#a-send-recorded-before-it-is-made)). A new conversation's first prompt is covered by `TestScenarioNewConversationHandoff` and its own record. No case lost a hold or put the task on two conversations; held checks, dry runs and checks that cannot read `sends.json` settle no record, so a kill followed by a pause and a resume still holds (`TestASendRecordedWithoutAnOutcomeAtEachKillPoint`). Kills inside a single file write cannot be placed from outside; every record is replaced atomically (written to a temporary file, then renamed), so a kill leaves either the old record or the new one.

**Damaged records** (`TestFaultDamagedRecord`). Each record is emptied, cut in half or overwritten with bytes that are not JSON, then a check, `status` and `pause` run. No damaged record is rewritten by any of them.

| Record | The check | `status` | `pause` |
| --- | --- | --- | --- |
| `control.json` | exits 1, sends nothing, names the file | exits 1, names the file and what to do, and prints what it can | exits 1: nothing keepgoing offers can hold the loop (known failure) |
| `state.json` | exits 1, sends nothing, names the file | exits 1, names the file and what to do, and prints what it can | works |
| `sends.json`, `progress.json`, `health.json` | exits 0 with outcome `failed`, sends nothing, names the file | works | works |
| `incidents.json` | does its work, then exits 1: `incident history unavailable` (documented in [diagnostics](diagnostics.md)) | works | saves the change, warns, exits 1 |
| `deliveries.json`, `graph.json` | does its work, exits 0 | works | works |

A loop whose `control.json` is damaged cannot be paused or stopped through keepgoing; its checks send nothing, so it is held in effect, but a daemon or scheduler keeps running. That is marked `stop with a damaged control.json, unassigned`.

Mutations that fail these: a hold saved after its report instead of before, a damaged `state.json` read as a new loop, and a damaged `health.json` read as empty.

**Setup checks.** A fault scenario's setup relies on its first check to wake the session, and confirms it did (`setupWake`): action `wake` and one message to the session. A check that found the provider retry state unverified could not read what the stand-in `bb` serves (a `thread log` that failed gives exactly that), which is the host or the harness and not the step under test: it is run again a minute later, up to three checks in all, and then fails as `ENVIRONMENT FAILURE`. Any other answer fails the setup at once as `SETUP FAILURE`, with what the check said. The stand-in's `fail.<command>` file makes the next N calls of `bb thread <command>` fail, which is how `TestSetupWakeRunsAgainAfterAFailedRead` proves the retry.

Not covered: cutting each external command at its time limit (the other half of T3 on the roadmap), a kill inside a write, and power loss (nothing here cuts the power, so a flush is never tested).

## Timing-sensitive tests

Four causes were found behind intermittent failures, each reproduced before it was fixed. Use them when a test fails only sometimes.

- **A deadline that times the host, not the code.** macOS assesses a file the first time it is executed and serialises those assessments across the machine. A new shell script takes about half a second to start on an idle machine and many seconds when other processes are also starting new executables; later runs take milliseconds. CPU load alone does not reproduce this. Stand-in CLIs are therefore installed with `internal/testexec`, which runs each script once in a mode that exits before its body while the fixture is built, and hard-links scripts whose content is shared by many fixtures. Replace such a script with the same helper, never by writing through its path. New fixtures that execute a script under a deadline should use it. Compiled programs go in a `testexec.Dir`; scripts in service tests are not covered.
- **A retry budget that is a deadline in disguise.** A fixed number of short retries measures how slow the filesystem is. Retry on the condition itself and let the test timeout bound a real hang.
- **Two ready cases in one `select`.** Go chooses at random, so code that must not act after cancellation has to check the context when it receives the other event. `TestDaemonWaitNeverPollsAfterCancellation` holds a poll past several ticks to force both cases ready.
- **A reader blocking a writer on Windows.** An ordinary open handle prevents a file from being replaced. A polling test per record (`Test…SnapshotSavesWhileReadersPoll` for state, the send and progress ledgers, health, the incident and delivery journals, the registry and the daemon endpoint, plus `TestStateSnapshotSaveReplacesFileHeldByReader` and `TestTransferRecordReadsDoNotBlockControlOrStateSaves`) runs natively in the Windows job. The fallback for an unsupported rename and the reader's short retry are covered by injected error codes there, not by a real exFAT or network volume; the retry was added after the health polling test failed a read with access denied in two of five runs. A program outside keepgoing that opens these files without delete sharing can still block a save; one such failure of a control save was seen in a hundred Windows iterations and is not explained. Local macOS execution and cross-compilation say nothing about these tests.

Reproduce before changing anything: repeat the one test with `-count`, then add the pressure that matches the suspected cause (CPU, filesystem writes, or many first executions of new files). Record the failure rate before and after, and name what was not reproduced. Raising a timeout is a fix only when the deadline is shown to be the sole defect.

## Slow test packages

`internal/supervise` and `cmd/keepgoing` run thousands of checks in the test process, and each check saves several records. Every save flushed its file to the device before renaming it. On macOS that flush waits for the device: about 4 ms for a 2 KB record against 0.1 ms for the write and rename alone, measured on the development machine, and flushes from every process on the machine queue behind one another. So these packages spent most of their wall time waiting, not computing, and several copies running at once slowed each other almost linearly until Go's ten-minute package limit was reached. One test, `TestCheckEndsWithinItsHardLimitInEveryCombination`, used 99 seconds of wall time for 2.7 seconds of user CPU.

The flushes now go through `snapshot.Sync`. A test binary may call `snapshot.SkipSyncInTests` from an `init` function in a `_test.go` file to make it a no-op; the call panics anywhere else, so no command, flag, setting or environment variable can turn the flush off. `internal/supervise` and `cmd/keepgoing` do this. No assertion changed: a test cannot observe a flush, because nothing cuts the power (that gap is listed under run discovery below and is unchanged). The scenario suite runs the built binary and keeps the flush.

Measured on macOS (Apple silicon) with `-race`, on a machine other lanes were also using:

| What | Before | After |
| --- | --- | --- |
| `TestCheckEndsWithinItsHardLimitInEveryCombination` (`internal/supervise`), alone | 88.6 s | 9.9 s |
| The same test, four copies at once | 360 s each | 19.4 s each |
| `TestCursorCommandActiveHoldsAndResume` (`cmd/keepgoing`), alone | 17.9 s | 10.7 s |
| `TestEndToEndRateLimitHandoff` (`cmd/keepgoing`), alone | 4.5 s | 2.6 s |

Whole-package times are in the pull request that made the change, from CI. The whole packages were not timed locally, alone or four at once, because running them on the shared machine is what was causing the timeouts.

What was looked for and not found, or not done:

- **Real sleeps.** `internal/supervise` has none. `cmd/keepgoing` has only 10 to 25 ms polling intervals inside wait-for-a-condition loops; there is no fixed long sleep to replace with a clock.
- **First execution of stand-in scripts.** Every executable script in both packages is already installed through `internal/testexec`.
- **`t.Parallel`.** Not added. Most `cmd/keepgoing` tests set environment variables with `t.Setenv`, which Go refuses to combine with parallel tests, and the packages' fake clocks and stand-ins were not audited for shared state.
- **`internal/incident`** also takes over a minute under `-race`, but skipping the flush there changed nothing, so its time goes elsewhere. Not investigated.

**Which packages skip the flush, and which must not.** Exactly two: `internal/supervise` and `cmd/keepgoing`, each from its `sync_test.go`. They run the check in the test process and assert on decisions, sends and saved records, none of which a flush changes. That includes their tests that kill a process and check what it left behind (`transfer_process_test.go`, `run_graph_test.go`): data a process has written survives that process being killed whether or not it was flushed, so those tests still prove what they claim. It also means the helpers those two packages re-execute from the test binary to act as the real command run unflushed. A package must not skip the flush if it tests what survives power loss or an operating-system crash, or if it runs the built binary: the scenario suite does not skip it, so every scenario exercises the command as it ships. Adding a package means adding it to the list in `internal/snapshot/sync_guard_test.go` and to this paragraph.

**What the helper covers, and what is not flushed.** `snapshot.Sync` is used for the records a check saves: `state.json`, the send ledger, `control.json`, the incident journal and the delivery journal. Other writers call `File.Sync` directly and are unchanged: the BB transfer record, the Antigravity runner's records, the service plan and the guided fallback edits. Some records were never flushed and still are not: `health.json`, the registry, the BB log cursor, `runs.jsonl`, the daemon endpoint, the client resume record and the headless turn directories. That is a known gap in what survives power loss, not changed here.

**Why the switch cannot be off in a shipped binary.** Three tests hold it:

- `TestOnlyNamedTestFilesSkipTheFlush` scans the source: only the listed `_test.go` files may mention `SkipSyncInTests`, so no file compiled into a command can call it. It also fails if any file other than the helper's own names the flag, which is how a `go:linkname` directive would reach it. A copy of the source with its own `go.mod`, such as a test bundle unpacked inside the checkout, is not scanned.
- `TestFlushCannotBeSkippedOutsideATestBinary` builds an ordinary program (`internal/snapshot/testdata/flushprobe`), the way the command is built, and shows that the call panics there and that the flush is attempted before and after it, including when the program is given test flags and test-like environment variables. The guard is Go's `testing.Testing()`, which is set by the linker when `go test` builds a test binary and by nothing at run time.
- `TestBuiltBinaryCannotSkipTheFlush`, in the scenario suite, inspects the symbols of the `keepgoing` binary the scenarios run: the flag `Sync` reads is present, and the only function that sets it is absent, as is the variable `testing.Testing()` reads. It fails on a stripped binary supplied through `KEEPGOING_TEST_BINARY`, because that cannot be checked.

The second and third need the Go toolchain and say they were not run when it is absent, as in the test bundle for machines without Go; the scenario suite as a whole says the same there.

Each was run against a broken build: a command that calls the switch behind an environment variable fails the first and third; a switch without its guard fails the second. What they do not cover: someone deliberately building the command with a linker flag that sets `testing.testBinary` and adding a call to the switch, which is a source change the first test catches; and whether a flush that is requested reaches the device, which depends on the operating system and disk.

## Live check: a long time offline

`TestOfflineForAnyLengthThenRecoversOnce` covers this with a fake clock, a stand-in `bb` and a stand-in connectivity target. Nothing below has been run on a real machine; this is the procedure for doing so. It changes no scheduler or service: use whatever already runs your loop, and do not reconfigure it for the test.

**The scenario.** Someone is working at home, disconnects, closes the lid, and hours later opens it on a different network that needs a sign-in, then signs in.

**Before you start**

1. Use a loop on a BB thread you can afford to interrupt, with the connectivity check on (`keepgoing validate` prints no `connectivity check` warning, and `keepgoing doctor` shows `network.check` as ok).
2. Note the loop's check interval (the scheduler's, or `daemon.interval`).
3. Save a reference: `keepgoing status > before.txt` and `keepgoing timeline --limit 20 > timeline-before.txt`.
4. Have the thread mid-turn, ideally with a child thread working.

**Do**

1. Turn the network off (Wi-Fi off, or unplug). Wait until the thread shows an error in BB.
2. Close the lid. Leave it for the length you want to test: start with 20 minutes, then try a few hours or overnight.
3. Open the lid on a network with a captive portal if you have one (a phone hotspot with no data, a guest network before signing in). Leave it two or three check intervals. If you have no portal, skip this step.
4. Sign in to the portal, or turn the normal network back on. Note the time.
5. Wait two check intervals.

**Then look at**

```sh
keepgoing status
keepgoing timeline --since <when you disconnected> --limit 100
keepgoing runs
tail -n 40 <state_dir>/runs.jsonl
```

**Pass**

- While offline and behind the portal, every recorded check has action `none` and the reason `network down; waiting for connectivity` (or `provider is retrying the turn` for the first minutes, or `active` for a turn that hung and never failed, before the outage was noticed). None is `reprompt`, `handoff`, `nudge` or `await_user`. In `runs.jsonl`, probes in those checks are `"skipped":"network_down"`, apart from the occasional `connectivity verification` probe (after one hour offline, then after twice as long each time).
- `status` while offline shows `network: down at the last connectivity check, failing since <time>`.
- The loop was not held: `status` does not say `awaiting user`, and `reprompts` is what it was in `before.txt`.
- The first check after you signed in has `"network":"restored"` with `networkDownFor`, and action `reprompt` (or `wake`, or `none` for a turn that hung and is working again). There is exactly one recovery: for a BB thread the failed turn was retried with no new prompt (`"recovery":"turn_retry"`), followed by one short `[keepgoing:child-errors count=N running=M]` message only if a child had failed; another adapter received one re-prompt, which ends with a `[keepgoing:child-errors count=N]` line. The task prompt did not arrive again.
- `timeline` shows the waiting checks as one entry with a first and last time, then the recovery.
- Recovery started within one check interval of signing in. Note how long it took.

**Fail, and worth reporting with the output above**

- Any re-prompt, nudge or handoff while offline or behind the portal; more than one message after recovery.
- An `awaiting user` hold with a reason about re-prompts, `auth error` or `no Git progress` that appeared during the outage.
- `network: down` still shown by `status` long after recovery.
- No check recorded at all after the lid was opened: that is the scheduler, not keepgoing. See [external schedulers can stop on their own](operations.md#external-schedulers-can-stop-on-their-own).

**What this does not show.** A check target that is unreachable while the provider works (test that separately with `keepgoing doctor` from the environment your scheduler uses), an outage of weeks, or an expired provider login after a long gap.

### Observed once: a real outage (2026-11-14)

The first live evidence of network-aware waiting and recovery comes from one incident on one machine. It was an unplanned network outage, not this procedure. It comes from the coordinator's reading of the loop's `runs.jsonl`. The loop supervised a BB chat and was run by a BB automation.

- **While the network was down.** Checks were recorded at 08:40, 09:20, 09:30 and 09:40 UTC. Each had the reason `network down; waiting for connectivity`, and none sent anything.
- **When it came back.** The check at 10:02 UTC recorded `network back: the connectivity check passed after failing for 1h21m57s`, and made one re-prompt.
- **The scheduler.** Every check succeeded, so the BB automation stayed enabled. An external scheduler can turn itself off after failed runs; see [external schedulers can stop on their own](operations.md#external-schedulers-can-stop-on-their-own).

**What it did not show:**
- **Lanes.** Lanes were restarted by the coordinator, not by keepgoing. Lane recovery (`bb.children.retry_errored`) was not observed.
- **Unrecorded details.** The record does not show whether the re-prompt was a turn retry by reference. It also doesn't show what `status` and `timeline` displayed, or how long after the network returned the 10:02 check ran.
- **The daemon.** The daemon's re-check within a minute of the network returning was not exercised, because an external scheduler ran the checks.
- **The procedure's other steps.** The lid, a captive portal, a second network and the pass criteria above as a whole were not covered.

The full procedure still has to be run once.

## On a machine or VM without Go

Build a bundle on a machine that has Go, copy it over, and run it there:

```sh
scripts/build-test-bundle.sh linux arm64 out/linux      # writes out/linux/bundle.tar.gz
scripts/build-test-bundle.sh windows arm64 out/windows  # writes out/windows/bundle.zip
```

Unpack the archive in a scratch directory on the target. Then run `src/run-tests.sh` on Linux or macOS, or this on Windows:

```powershell
powershell -ExecutionPolicy Bypass -File src\run-tests.ps1
```

Each package's test binary runs from its own directory, so fixtures resolve as they do under `go test`. The bundle also holds a `keepgoing` binary for smoke checks such as `keepgoing validate -c examples/looptender.bb.yaml`.

Neither is the full POSIX CLI suite. Cite the specific Actions run and jobs when reporting results.

Two workflows produce the six checks on a pull request. `checks.yml` runs the build, test, two Windows and plugin jobs when a pull request is opened, pushed to or reopened, on pushes to `main`, and on manual dispatch. `contributions.yml` runs only `Contribution metadata`, the one check that reads the title and description, and also runs when those are edited. The same check refuses a pull request that adds or changes a file which is larger than 1 MB or begins like a compiled executable (Mach-O, ELF or PE), naming the path and its size, unless the path is listed in `scripts/contribution-file-allowlist.txt`. That list is empty: when the rule was added nothing on `main` was over 1 MB (the largest file was 140 KB) or began like an executable. It also refuses a text file the change adds or changes that has git conflict markers (a line beginning `<<<<<<< ` or `>>>>>>> `, or exactly `=======`), naming the lines, unless the path is in `scripts/conflict-marker-allowlist.txt`, which is empty too. A merge committed with its conflicts unresolved had put markers in `docs/roadmap.md` on `main` (#162) without any check noticing. `scripts/check-contributions.sh --scan-tree <commit>` applies the rule to every file of a commit, and `scripts/check-contributions-test.sh` is its table test, run by the Ubuntu job. Editing a description therefore re-runs that one job and leaves the other five results on the head commit untouched; it does not start or cancel a build. The two results come from different runs, so cite both run links when the metadata check matters. Changing a pull request's base branch does not by itself re-run the build jobs: merge the new base into the branch, which branch protection requires anyway, or close and reopen the pull request.

**CI time limits.** Each job has a time limit (`timeout-minutes`). A job that reaches it is stopped and reported as cancelled, the same as a job cancelled by a newer push, so the last step of the build-and-test and Windows jobs runs only when the job was cancelled and says which it was in the job summary: either "This job ran out of time: it is not a failing test", with how long it ran and the step it was in, or that it was cancelled before its limit. `scripts/ci-timeout-note.sh` reads the run's steps from GitHub (the jobs have `actions: read` for it) and never fails the job; `scripts/ci-timeout-note-test.sh` is its table test. It was run once at a real limit, on a scratch copy of the workflow with a 2-minute limit ([run 43481521177](https://github.com/connorburgess/keepgoing-agents/actions/runs/43481521177)), and named the step it stopped in.

**The Windows jobs' time.** The Windows tests were one job with a 10-minute limit. Its time on `main` grew from 361 s to 511 s in under two hours of merges on 13 November 2026, mostly from new Cursor and Antigravity runner tests (about 120 s), and on a slower runner it reached the limit (PR #187, [run 43471568103](https://github.com/connorburgess/keepgoing-agents/actions/runs/43471568103)). Each step's time was within a few seconds of its tests' own time, so nothing was being rebuilt; the time is the tests, and every step tests Windows behaviour. They now run as two jobs at once, split by what they exercise:

| Job | Steps | Typical (main, 17:28 run) | Worst seen (the run that hit the limit) | Limit |
| --- | --- | --- | --- | --- |

**What runs for a documentation-only change.** When every file a pull request changes is documentation, the Ubuntu build-and-test job runs everything as usual, including the tests that read the documentation (the generated adapters table, the examples, the contribution metadata), and the macOS and Windows jobs skip their work. `scripts/ci-scope.sh` decides, from the files the pull request changes against its base:

- Documentation is: anything under `docs/` or `LICENSES/`; Markdown files elsewhere; and the top-level `LICENSE`, `LICENSING`, `NOTICE`, `COPYING` and `AUTHORS` files, with or without an extension.
- Never documentation, whatever the file is called: anything under `cmd/`, `internal/`, `scripts/`, `schema/`, `examples/`, `.github/` or `.bb/`, and anything in a `testdata`, `fixtures`, `__fixtures__` or `node_modules` directory. So a Markdown test fixture, the pull request template and the workflow itself all run everything.
- Anything else, an empty list, a renamed file whose old name is not documentation, a checkout that is not a pull request merge, and any error all mean "run everything". So do pushes to `main` and ordinary manual runs.

The jobs are not skipped; their steps are. Branch protection requires `Build and test (macos-15)`, `Build and test (ubuntu-24.04)` and `Contribution metadata` by name, so each job always starts, decides in its second step, and reports success under its usual name with the later steps marked skipped and a line in the job summary saying why. For a code change nothing differs from before. The BB plugin job is not gated and always runs. `scripts/ci-scope-test.sh` is a table of file lists and the answer for each; the Ubuntu job runs it.

A manual run of the Checks workflow with a `base` commit previews the decision for a branch as if it were a pull request against that commit. Its macOS and Windows jobs report as `Scope preview - …`, so a preview can never satisfy a required check.

One limit: a pull request runs the workflow and script as that pull request has them. One that edits either is run in full, but what "in full" means is then its own version, as for any workflow change; that is for review to catch.
