## Done

**Milestone 1: supervise one loop.** Config validation, the pure decision engine, BB and process adapters, stall detection, time windows, the tick lock, control commands, and JSON tick output.

**Milestone 2: confirmed fallbacks.** `fallbacks.yaml`, headless Claude Code and Codex runners, three probe tiers with a daily cap, the health registry, redundancy across providers or groups, and handoff with an exact probe. It also covers model switching on BB threads, the generated brief with a file override, and manual retarget. **Milestone 3: operate it.** The daemon with immediate control handling and config reload. Signed webhook reports in the Standard Webhooks format, checked against its published test vector. `ci-wait`, `net-retry`, yield checks, scheduler examples, JSON Schemas with a drift test, Windows locking, and release automation.

**Verification pass.** The test suite was run on Ubuntu 26.04 ARM64 and Windows 11 Arm VMs. An independent audit of the docs against the code fixed these:

- Stop now wins even while the loop is paused or disabled.
- The daemon now notices a control change made during a pass.
- Relative config paths now work with headless runners and commands.
- Retarget now applies the target's model.
- A brief error no longer half-switches a candidate.
- Failed manual probes no longer delay scheduled probes.

See [integrations.md](integrations.md) for what is verified live.

**Agent chats.** BB pending interactions mean waiting on a person. `await-user` reports at once. A guide covers supervising a live chat thread. A session that stays stalled through `max_nudges` nudges now asks a person.

**0.1.0, released.** keepgoing supervises a live BB chat through a BB automation, reporting to a real webhook. The live checks verified:

- BB send, stop, and model switching against a scratch thread;
- the daemon's wakes, await-user hold, and SIGTERM exit;
- signed reports in the bearer and text formats;
- the release workflow, by publishing 0.1.0.

**BB plugin.** `integrations/bb-plugin-keepgoing` shows keepgoing's state in each supervised thread's context banner or card and adds `bb keepgoing status`, `pause`, `resume`, and `stop`.

**Homebrew.** `brew install connorburgess/tap/keepgoing` installs the release binaries from the [homebrew-tap](https://github.com/connorburgess/homebrew-tap) repository.

**Switch-back.** With `switch_back` on, the loop returns to the primary between the fallback's turns once the primary's limit resets and it passes an exact probe.

**Windows runners.** Headless Claude Code and Codex turns now run on Windows, through a detached copy of the keepgoing binary. Tested in a Windows 11 Arm VM.

**Codex limits.** A real Codex limit showed that `codex exec --json` reports it only as prose. keepgoing now classifies Codex failures from the app-server's structured rate-limit snapshot, with the reset time.

**Multiple accounts.** Headless Claude Code and Codex targets accept account environment overrides for fresh and resumed turns. Probes inherit them, and Codex limit checks use the same effective environment. The three-account example uses separate quota groups. Covered by fakes; live handoff between separate subscriptions remains to be verified.

## Next: first supervised loop in five minutes

keepgoing is the loop runner. A user supplies a task, chooses an agent, and starts the loop; a separate loop skill is not required. The current prompt and idle-wake mechanism already repeats work. This milestone makes task setup, completion, recovery, and operation one understandable experience. An optional agent skill may explain the CLI, but cannot be a prerequisite for ordinary use.

Unchecked items below have unfinished acceptance criteria; some contain an implemented or released subset, described explicitly in their evidence. Implement one focused PR at a time. The sections group capabilities; the delivery priorities below supersede their numerical order. A live check needing an account, host, or explicit authorization blocks only that check. Move to independent authorized work, without creating accounts, changing logins, manufacturing quota limits, or replacing an existing timer. ### Delivery priorities after roadmap reassessment

The project retains **Apache-2.0**. Optional paid products or support are business hypotheses, not prerequisites for the local supervisor or a license change.

Reliability of supervision comes before new features: a day of live supervision stopped the loop four separate ways. Most of that list has since landed in unreleased source, so priority 0 now lists what is still open and what has to be proven.

0. **Keep the loop going: supervision reliability.** A supervisor that waits silently is worse than none.
   Landed, unreleased, fixture-tested and now running on one live loop: expiry of a stale provider-retry notice, a tick time budget with an exit-code contract an external scheduler cannot trip on, tolerance for a missing worktree, a notice to the parent and a report to the owner when child threads fail, per-fallback caps on rejected handoff briefs, a single report for a long limit wait ([R8](#priority-reliability-checkpoints)), tiered event history ([R7](#priority-reliability-checkpoints)), and the timing-test and Windows record fixes. None has yet been through a real outage.
   Still open, in this order:
   - **Prove recovery live.** Cut the network on a supervised loop with child threads for longer than the provider's own retries, with nobody watching, and record whether the loop and its children come back. Until this passes once, the items above are fixture evidence only.
   - **Network-aware sending.** Do not spend re-prompts or probes into a dead network; record "network down" as its own waiting reason and act on the first check after it returns.
   - **Follow-ups from review of the stale-notice and tick-budget changes**: requested input re-arming an expired notice, a notice kept after recovery into a long tool call, the deferral counter reset, scheduled probes ahead of a due handoff, and a measured worst-case check time.
   - **Scheduler independence.** An external scheduler can still stop by itself; add the "no check has run for N intervals" self-check and make the built-in service the recommended path.
   - **Recovering failed children.** Today the parent is told and the owner can be told; nothing restarts a failed child. Decide whether keepgoing should, and under what bound. See [BB child awareness](#3-bb-child-awareness-and-loop-ownership).
   - **Reacting faster than the check interval** to a hard limit, and noticing a limit that was lifted early.
   - **The remaining event-log records** ([R7d](#priority-reliability-checkpoints)).
   Owner-only or live recovery checks in the [reliability checkpoints](#priority-reliability-checkpoints) still block only themselves.
1. **Finish run discovery.** D1 and D3 are checked: the identity contract, and `keepgoing runs` navigation, live-verified for a BB target on macOS and fixture-only elsewhere. Open: the remaining [D2](#priority-run-and-conversation-discoverability-planned) items (a routine identity on `start` and `daemon`, registry references for loops registered before their first run); D4, where child conversations and the owning conversation are implemented and unreleased, lock holders are not, and a live check on a loop with children is outstanding; then D5 and D6. Record identities and relationships when work starts or a transition is verified; users must not reconstruct them from timestamps, Git history or directory searches. Publish the approved README artwork only with the implemented feature and evidence for every relationship it depicts.
2. **Supervise every popular agent, not only BB.** keepgoing is meant to be the supervisor whichever tool the work runs in. Today the reliability behaviours are uneven: BB threads have all of them; headless Claude Code and Codex have the general ones (time-bounded checks, bounded re-prompts with exact session resume, fallbacks, limits, reports) but nothing for child work; Cursor is a source-only primary runner whose failures are all unclassified and which cannot be a fallback; Antigravity has protocol groundwork and no runner; and no adapter can attach to a chat already open in an IDE window. Close this in order:
   - **A capability matrix** that states, per adapter, which behaviours apply (stale-notice expiry, turn retry, connection-loss recovery, child awareness, handoff, quota readings, new-conversation handoff), with a test or an explicit "not applicable" for each cell, so a new behaviour cannot land for one adapter silently.
   - **Connection-loss recovery for the headless runners**: the offline scenario at any duration must pass for Claude Code, Codex and Cursor sessions as it must for BB.
   - **Cursor** ([C3–C4](#6-cursor-and-antigravity-integrations)): guided setup and diagnostics, a structured account and model probe so it can be a fallback, and an authorized live two-turn walkthrough.
   - **Antigravity** ([A2–A4](#6-cursor-and-antigravity-integrations)): the permission contract, the detached runner, then setup and a live walkthrough.
   - **IDE chats**: establish, per IDE, whether a chat already open in its window can be observed and continued through a documented interface; record what is and is not possible instead of implying support.
   Each provider keeps its own lifecycle, permission and live-evidence gates; focused PRs merge sequentially against current main.
3. **Make fallbacks easy and quota-aware.** Guided setup now covers headless and BB-thread candidates, model and thread pick lists, handoff on/off, reorder and remove, all unreleased and run only against stand-in CLIs. Usage readings from existing probes are recorded and shown (Q1, Q2), live-verified by one manual probe. Open:
   - The switch threshold (Q4): move to the next fallback at a configured share of a quota window, evaluated at turn end. A model-specific window is reported only by a probe or turn on that model, so the reading must come from there. A reading that is unavailable never triggers a switch, and keepgoing never reads credentials to obtain one.
   - More sources (Q3), including Codex readings on healthy probes.
   - Pick lists for detected accounts on headless candidates.
   - A live handoff to a candidate created by the guided flow.
   - Cursor as a fallback candidate waits for its own structured account and model probe contract.
4. **Prove and package the core journey.** Reconcile release/Homebrew instructions and changelog with actual artifacts; prepare a reproducible install-to-completion walkthrough covering a BB target and a headless runner. Verify holds, restart/resume, ownership, and truthful completion. Perform live checks only within their authorized account/host/spend scope. Keep release preparation moving when a particular live check is blocked.
5. **Bound repeated work.** The audit is done and failed sends now count toward the per-episode caps. Remaining: a decision on a default bound or count-based no-progress limit, and completion reporting, before claiming termination guarantees. Do not treat a nudge cap as a total-work budget.
6. **Add minimal portable goal state.** Establish identity, a display title, revisions, evidence references and explicit state before a UI promises to display goals. Keep execution planning outside the supervisor.
7. **Finish safe BB transfer.** Preserve holds and goal identity, fence stale owners, and reset thread-specific observations. The source-snapshot guard is a prerequisite, not completed transfer. 8. **Add optional menu-bar visibility.** Start with local loops, goals and explicit freshness through a versioned read/control contract. Configured stages can be shown when supplied; a stage engine is not required for the initial client.
9. **Pilot bounded independent review.** Use an external workflow with pinned inputs, preserved dissent, explicit incomplete results and budget limits. Evaluate value against a single-review baseline before adding more orchestration.

- [x] Bound stale BB retry notices (unreleased; offline fixtures only): a `willRetry` notice suppresses recovery only while fresh within `bb.retry_signal_ttl` (default 15m) of the newest notice on an errored thread, the newest provider event on an active thread, or a rate-limit notice's structured reset. - [ ] Read BB's retry plugin directly as evidence of a pending or declined retry (`bb provider-retry status <thread> --json` lists queued retries with `sendAt`; `explain` gives the last decision, `retry` or `decline` with a reason such as `not-retryable` or `beyond-maximum-wait`). #### Preferred routes (planned)

A route is a model on an account at an effort level ([glossary](glossary.md)). Today a loop has a primary and an ordered list of fallbacks, moves down on a structured usage limit, and can return to the primary after the reported reset. The intended rule is simpler and stronger: **work does not stop while any route can take it, and the loop prefers the best route available.** Routing is decided from facts about resources only; it never judges the content of the work. Every move is recorded with a one-sentence reason, can be previewed in advance, and a move to a weaker route is always visible.

- [ ] **P1 — A limit on the supervised session is handled even while its lanes are working.** Observed twice: a rate-limited session with a healthy fallback was left alone because the check stopped at "child work running". Error rules apply to an errored session regardless of its lanes.
- [ ] **P2 — Move before the limit.** The switch threshold in Q4 below: at a configured share of a quota window, move at the end of a turn so no turn fails.
- [ ] **P3 — Return to the most preferred available route.** Generalise switch-back from "the primary, after the reported reset" to "the highest route in the list that is available now", checked on an interval that backs off, so a limit lifted early is noticed. Guards: a minimum time on a route before moving again, movement only at a turn boundary, and cheaper returns within one conversation than between conversations.
- [ ] **P4 — Spread lanes across allowances.** Lanes of one loop should not all draw on one allowance when another has room. Needs lanes to be first-class (P6).
- [ ] **P5 — Connectivity-aware routes.** A route may be usable only online or only offline (a local model); the list is filtered by what is reachable.
- [ ] **P6 — Lanes as first-class members of a loop.** Today a loop's lanes are known by count and state only. Give a loop a group of members so each lane can have routes of its own, be moved or have its effort changed, and be recovered; either by supervising each lane as a small loop or by extending the parent's loop. Decide after trying the first on one lane.
- [ ] **P7 — Owner limits on routing.** A floor ("hold instead of going below this route"), a spend ceiling, and no move to a metered route unless allowed.
- [ ] **P8 — Refusals and restrictions hold, they never route.** Where an agent or provider reports a refusal, a policy block or an account restriction in a structured form, classify it as its own state that holds for a person and can never trigger a handoff, a new conversation or a retry on another route. Until a structured signal exists for an adapter, such a turn stays `unknown`, which already never triggers failover; record per adapter what is and is not detectable. Also bound repeated wakes of a session whose turns keep ending without progress, so a loop does not press an agent that has declined.
- [ ] **P9 — Fleet safety before fleet features.** Before any multi-device work: devices are enrolled by a person and can refuse; a device pulls the loops it may run rather than receiving pushed commands; each device has its own stop that the root cannot override; a default bound on new loops; and one control that stops every loop on a device.

There is no "ask first" or grace mode: turning handoff off entirely (an empty `failover_on`) remains the way to make a loop wait.

Work that moves to wherever it can continue must not be able to spread by itself. The bounds are stated in the [glossary](glossary.md#what-moves-and-what-never-does) and in AGENTS.md, and each item above is implemented inside them: only configured routes, accounts and devices; no self-installation; one owner per loop; capped and spaced creation; every move recorded.
