# Roadmap

## Done

**Milestone 1: supervise one loop.** Config validation, the pure decision engine, BB and process adapters, stall detection, time windows, the tick lock, control commands, and JSON tick output.

**Milestone 2: confirmed fallbacks.** `fallbacks.yaml`, headless Claude Code and Codex runners, three probe tiers with a daily cap, the health registry, redundancy across providers or groups, and handoff with an exact probe. It also covers model switching on BB threads, the generated brief with a file override, and manual retarget. BB limit detection uses structured provider-error and rate-limit events, and the loop waits for a reset when it is near.

**Milestone 3: operate it.** The daemon with immediate control handling and config reload. Signed webhook reports in the Standard Webhooks format, checked against its published test vector. `ci-wait`, `net-retry`, yield checks, scheduler examples, JSON Schemas with a drift test, Windows locking, and release automation.

**Verification pass.** The test suite was run on Ubuntu 26.04 ARM64 and Windows 11 Arm VMs. An independent audit of the docs against the code fixed these:

- Stop now wins even while the loop is paused or disabled.
- The daemon now notices a control change made during a pass.
- Relative config paths now work with headless runners and commands.
- Retarget now applies the target's model.
- A brief error no longer half-switches a candidate.
- Failed manual probes no longer delay scheduled probes.

See [integrations.md](integrations.md) for what is verified live.

**Agent chats.** BB pending interactions mean waiting on a person. `await-user` reports at once. A guide covers supervising a live chat thread. A session that stays stalled through `max_nudges` nudges now asks a person.

**0.1.0, released.** keepgoing supervises a live BB chat through a BB automation, reporting to a real webhook. The live checks verified:

- BB send, stop, and model switching against a scratch thread;
- the daemon's wakes, await-user hold, and SIGTERM exit;
- signed reports in the bearer and text formats;
- the release workflow, by publishing 0.1.0.

**BB plugin.** `integrations/bb-plugin-keepgoing` shows keepgoing's state in each supervised thread's context banner or card and adds `bb keepgoing status`, `pause`, `resume`, and `stop`.

**Homebrew.** `brew install connorburgess/tap/keepgoing` installs the release binaries from the [homebrew-tap](https://github.com/connorburgess/homebrew-tap) repository.

**Switch-back.** With `switch_back` on, the loop returns to the primary between the fallback's turns once the primary's limit resets and it passes an exact probe.

**Windows runners.** Headless Claude Code and Codex turns now run on Windows, through a detached copy of the keepgoing binary. Tested in a Windows 11 Arm VM.

**Codex limits.** A real Codex limit showed that `codex exec --json` reports it only as prose. keepgoing now classifies Codex failures from the app-server's structured rate-limit snapshot, with the reset time.

**Multiple accounts.** Headless Claude Code and Codex targets accept account environment overrides for fresh and resumed turns. Probes inherit them, and Codex limit checks use the same effective environment. The three-account example uses separate quota groups. Covered by fakes; live handoff between separate subscriptions remains to be verified.

## Next: first supervised loop in five minutes

keepgoing is the loop runner. A user supplies a task, chooses an agent, and starts the loop; a separate loop skill is not required. The current prompt and idle-wake mechanism already repeats work. This milestone makes task setup, completion, recovery, and operation one understandable experience. An optional agent skill may explain the CLI, but cannot be a prerequisite for ordinary use.

Unchecked items below have unfinished acceptance criteria; some contain an implemented or released subset, described explicitly in their evidence. Implement one focused PR at a time. The sections group capabilities; the delivery priorities below supersede their numerical order. A live check needing an account, host, or explicit authorization blocks only that check. Move to independent authorized work, without creating accounts, changing logins, manufacturing quota limits, or replacing an existing timer. Record evidence and limitations in [integrations.md](integrations.md).

#### Preferred routes (planned)

A route is a model on an account at an effort level ([glossary](glossary.md)). Today a loop has a primary and an ordered list of fallbacks, moves down on a structured usage limit, and can return to the primary after the reported reset. The intended rule is simpler and stronger: **work does not stop while any route can take it, and the loop prefers the best route available.** Routing is decided from facts about resources only; it never judges the content of the work. Every move is recorded with a one-sentence reason, can be previewed in advance, and a move to a weaker route is always visible.

- [ ] **P1 — A limit on the supervised session is handled even while its lanes are working.** Observed twice: a rate-limited session with a healthy fallback was left alone because the check stopped at "child work running". Error rules apply to an errored session regardless of its lanes. Implemented in #169, unreleased and fixture-tested; the live loop that showed it has not been re-run with the fix.
- [ ] **P2 — Move before the limit.** The switch threshold in Q4 below: at a configured share of a quota window, move at the end of a turn so no turn fails.
- [ ] **P3 — Return to the most preferred available route.** Generalise switch-back from "the primary, after the reported reset" to "the highest route in the list that is available now", checked on an interval that backs off, so a limit lifted early is noticed. Guards: a minimum time on a route before moving again, movement only at a turn boundary, and cheaper returns within one conversation than between conversations.
- [ ] **P4 — Spread lanes across allowances.** Lanes of one loop should not all draw on one allowance when another has room. Needs lanes to be first-class (P6).
- [ ] **P5 — Connectivity-aware routes.** A route may be usable only online or only offline (a local model); the list is filtered by what is reachable.
- [ ] **P6 — Lanes as first-class members of a loop.** Today a loop's lanes are known by count and state only. Give a loop a group of members so each lane can have routes of its own, be moved or have its effort changed, and be recovered; either by supervising each lane as a small loop or by extending the parent's loop. Decide after trying the first on one lane.
- [ ] **P7 — Owner limits on routing.** A floor ("hold instead of going below this route"), a spend ceiling, and no move to a metered route unless allowed.
- [ ] **P8 — Refusals and restrictions hold, they never route.** Where an agent or provider reports a refusal, a policy block or an account restriction in a structured form, classify it as its own state that holds for a person and can never trigger a handoff, a new conversation or a retry on another route. Also bound repeated wakes of a session whose turns keep ending without progress, so a loop does not press an agent that has declined.
- [ ] **P9 — Fleet safety before fleet features.** Before any multi-device work: devices are enrolled by a person and can refuse; a device pulls the loops it may run rather than receiving pushed commands; each device has its own stop that the root cannot override; a default bound on new loops; and one control that stops every loop on a device.

##### Usage-aware timing (planned)

Use each allowance fully before it resets, and avoid running out before it does. A loop may move to a stronger route on the same allowance (a stronger model or a higher effort) when the allowance would otherwise reset unused, move to a cheaper one earlier in the window when the recorded readings project it running out before its reset, and move back when the reason passes. Using an allowance up is a person's choice: they decide whether it happens, how far it goes, how much is kept for their own use and which loops may do it, and they can see what it would do before turning it on. U1 and U2 are built and display only; nothing else here is.

The rules, inside the same bounds as every route move:

- **Within one allowance only.** Routing (handoff, P2, P3, [Q4](#quota-monitoring-planned)) chooses the allowance; timing chooses among the steps a person listed on that allowance, cheapest to strongest. The person's order is the order; keepgoing never ranks models or effort names. It never moves to another account, and never rotates accounts to get more.
- **From recorded readings only.** A reading is a used fraction and a reset time per window, at an age, for an account that was probed or used recently, and sometimes there is none. Timing acts only on windows the person names, whose keys stay opaque. A projection is a rate fitted through the recorded readings of one window instance (at least three, over at least 6 h, never extended more than four times their span ahead), and only readings taken after the last step count. A missing, stale or malformed reading never causes a move; it shows as "can't project" with its reason.
- **Up near the reset, straight to the ceiling.** When a named window resets within `near_reset` (default 6 h) and a reading no older than 1 h shows at least `unused_at_least` (default 25%) unused, the loop moves to the ceiling step. It returns when the reset recorded at the step passes, or earlier when readings since the step project the allowance running out before it resets.
- **Down when projected to run out.** When the projection reaches `down_at` (default 95%) with more than `near_reset` left, the loop moves down one step, never below the lowest listed step, and returns at the reset.
- **At a turn boundary, after everything else.** Stop, pause and holds win, then errors and limits, then Q4 and P3; timing is evaluated last, only after a turn that ended normally. A refusal or an `unknown` turn never causes a timing move. Each move stays at least 2 h before the next, except the return at a reset, and is recorded in words the panel can show, for example "stepped up: the seven-day allowance resets in 2 h with 40% unused".
- **Readings cost probes.** Today readings come only from probes on every route: BB does not pass the provider's rate-limit events through, and headless turns do not record them yet (Q3). For loops on BB threads that stays so, and timing there depends entirely on probing. With timing on, the home allowance is probed on its schedule: about 15 small paid probes a week for each timed allowance at a 12 h cadence, on the probe model, never above `probe.daily_cap`. With timing off nothing changes from today.

How this relates to the items around it: readings come from [Q1 and Q3](#quota-monitoring-planned). P2 and Q4 move to another allowance at a fixed share; timing never does. P3 returns across allowances; timing's return stays within one. Spreading several loops or lanes across allowances is P4, and the owner's ceiling is part of P7. Every item below except U1 and U2 is unchecked.

#### Quota monitoring (planned)

The owner wants keepgoing to move to another target at a usage threshold, for example 80%, instead of only after a turn fails on a limit. Deliver it in four steps. Throughout, an unavailable reading never triggers a switch, readings come only from structured provider fields, and keepgoing never reads stored credentials or calls a provider usage endpoint.

- [x] **Q1 — Readings from probes that already run.** Record per-candidate usage windows (opaque key, used fraction, reset time, status) with their observation time in `health.json`: from the Claude probe's `rate_limit_event` stream messages and from the Codex app-server read that already follows an unclassified probe failure. The Claude probe now requests `stream-json`; fixtures show the same judgement as `json` for the same result object. Bounded and defensively parsed; a reading is tied to the account identity it was read from and goes stale once its window resets. No raw output stored, no decision reads the values, no provider call added. Implemented in unreleased source with offline fixtures only. The Claude event shape was observed by the project coordinator on Claude Code 2.1.318 with live one-turn probes on two models; it is not documented. The `stream-json` argv change affects every Claude probe; its live evidence is one live manual probe by the project coordinator, with a binary built from this source, of one headless Claude candidate on Claude Code 2.1.318 and macOS arm64, judged healthy with a reading recorded. Other tiers, a failing probe, Codex readings, other CLI versions and Windows are not live-verified. See [usage readings](fallbacks.md#usage-readings).
- [x] **Q2 — Display.** `fallbacks list` and `status` show each reading with its age and source, or `stale` / `unavailable`, in text and JSON. Cursor and other providers show unavailable. CLI fixtures only; the BB plugin and macOS preview do not show it. Unreleased.
- [ ] **Q3 — More sources.** Decide whether a healthy Codex probe may add the app-server read (an extra provider call per probe), capture the event from headless Claude turns, and ask BB to expose it for BB-run turns. Until then the active target usually has no fresh reading.
- [ ] **Q4 — Switch threshold.** Optional per-target `switch_at`, evaluated only at turn end on the highest used fraction among reported windows, as a pure decision with tables. Requires a confirmed fallback and the existing exact probe; stop, pause and holds win; a missing, stale or malformed reading never switches. Needs a freshness rule and live evidence before any claim.

### 9. Independent review and configured stages (planned)

- [ ] Define a versioned external stage/result contract tied to goal revision, repository revision, policy version and evidence. Support user-selected stages rather than imposing one universal sequence.
- [ ] Pilot two blind independent reviews of the same pinned inputs, followed by a synthesis of findings, disagreements and missing evidence. Resolve material disagreements with bounded tests or targeted review; preserve dissent and distinguish incomplete review from approval.
- [ ] Define explicit event keys, stale-result rejection, ownership fencing, concurrency limits, retry/review budgets and crash recovery. A result may satisfy only a pre-authorized gate; it cannot widen scope, clear human holds, or authorize itself.
- [ ] Compare single review, independent samples, independent review plus synthesis, and bounded debate at comparable cost. Measure evidence quality, missed defects, false acceptance, retained dissent, latency and human review time. Agreement alone is not correctness.
- [ ] **Review as a lane role.** A lane may carry a declared role, `work` or `review`, recorded with the loop and shown wherever lanes are shown. A review lane reads pinned inputs and reports; it may run on a different route or device from the work it reviews, so the reviewer does not share the author's model, allowance or context. The role is explicit metadata set by a person or by the agent that started the lane; keepgoing never infers it from a title or from text, and a review result still passes only a gate that was authorized beforehand. Depends on lanes as first-class members (P6) and on the route view (V2). Today this is done by hand: each change is read by an independent reviewer that sees the code and not the author's reasoning.

Reviewer execution and interpretation belong in a BB workflow or other external coordinator. keepgoing never spawns reviewer threads or re-parents threads (the one thread it can create is the opt-in [handoff to a new conversation](fallbacks.md#hand-off-to-a-new-conversation)), never interprets review prose, or treats arbitrary model-produced JSON as provider status. Explicit control commands need validated provenance/authorization and revision checks; a JSON shape alone is insufficient. No general planner, recursive review system or second scheduler is part of this plan.
