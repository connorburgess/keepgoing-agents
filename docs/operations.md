# Operations

## Running it

There are two ways to run keepgoing. Pick one per loop.

- **`keepgoing tick` from a scheduler.** Each run makes one pass and exits. Ticks never overlap, because a tick that finds the lock held exits 75. See [examples/schedulers](../examples/schedulers) for launchd, cron, a BB automation script, and a GitHub Actions job.
- **`keepgoing daemon`.** This runs a pass every `daemon.interval`. Between passes it checks `control.json` every `daemon.control_poll`, so changes such as `keepgoing stop`, `pause`, or `complete` request a check within seconds. The daemon reloads `keepgoing.yaml` and `fallbacks.yaml` before each pass and retains the last timing and diagnostic context when an edit is broken. Provider work is withheld while the loaded source snapshot cannot be verified. Changing `state_dir` requires a restart: a running daemon keeps its original lock and diagnostic endpoint and withholds provider work until the original configuration is repaired or the daemon is restarted with a valid configuration. SIGINT or SIGTERM ends it at once and cancels any command in flight. A control change written while a pass is running starts the next pass immediately after it. Only one daemon runs per state directory, and a second one exits 75. `--dry-run` applies to every pass. See the systemd unit in the examples.

Ending the daemon does not stop the agent. To stop the agent, run `keepgoing stop`.

### Control-change detection

v0.2.0 includes a content fingerprint alongside the regular control file's modification time and size when checking for changes between daemon passes. This catches same-size edits whose filesystem timestamp was preserved or did not advance. Published v0.1.5 and earlier use metadata alone and can wait until the normal interval in that case. Scheduler-driven ticks are unaffected: each invocation already reloads controls.

v0.2.0 on Windows opens control loads and content-poll snapshots with read, write and delete sharing, and the control/goal writer uses `FileRenameInfoEx` with replacement and POSIX semantics. Both are necessary: the legacy `MoveFileEx` call can reject an open destination even when that reader permits deletion. This write path requires Windows 10 version 1709 or newer and a filesystem supporting POSIX-style rename; unsupported operations return an error without falling back to legacy rename or removing the destination first. See Microsoft’s [rename operation](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_rename_information) and [version requirement](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/ne-wdm-_file_information_class). The handle is read-only; delete sharing permits another handle to replace the file without granting the reader delete access. An opened snapshot continues reading its original file after a cooperating writer atomically replaces it, and the next poll/load observes the replacement. A reader opened without delete sharing can still block a save. The other records a tick replaces while another command may read them now use the same reader and writer: `state.json`, `sends.json`, `progress.json`, `health.json`, the incident and delivery journals, the loop registry and the daemon endpoint record. Client status, hold, resume, transfer, timeline and doctor reads of these files use that reader too. Before this, a reader holding `state.json` made the daemon's tick fail after acting. For these records, unlike control and goal files, a system or filesystem that reports the POSIX-style rename as unsupported (by Windows error code) falls back to the ordinary rename they used before, so such a volume keeps working but a reader can again block a save there. A sharing violation or access denial never falls back. A reader that arrives while a record is being replaced can be refused for an instant with one of those two codes; the shared reader retries only them, a few times over about thirty milliseconds, then returns the error. Saves are not retried. Per-target files (the BB cursor and headless turn files), configuration sources and any outside program that opens these files itself still use ordinary opens.

A failed `state.json` save has a consequence on every platform: the tick has already acted, so the record that a stop or prompt was sent is lost, the next tick can send it again, and the daemon waits its ordinary interval before that tick. `state.json` and control files are now synced before they are published; this is not a power-loss guarantee. The writer opens only its staging file with delete access, closes that handle on every return, and never asks to ignore read-only attributes. This is not a retry mechanism, a guarantee that all writes succeed, or isolation from external in-place edits.

The fingerprint streams the opened regular file's observed length with bounded memory and stays in memory; neither control text nor its digest is added to logs, status or reports. Missing, unreadable and non-regular files do not count as valid control evidence. A changed signature only requests a new check: ownership, configuration-source and parsed control checks still govern actions. Unchanged files do not trigger repeated early checks. This is change detection for local files, not an atomic snapshot across external in-place writers or a guarantee against hostile filesystem replacement. A saved stop can still wait for an in-flight check or adapter command; it does not kill the current command immediately.

### Loaded configuration checks

After acquiring `tick.lock`, ticks, daemon notification polls, retargets, and executing manual fallback probes verify that `keepgoing.yaml` and its loaded `fallbacks.yaml`, or for a loop that follows it the [standard route list](routes.md), still contain the exact bytes originally parsed (for the standard list, still missing if it was missing). Changed, missing, unreadable, or non-regular sources suppress provider work. Ticks, retargets, and probe execution return exit 75 with a reload/retry diagnostic; early polls wait for the next ordinary reload instead of querying the stale target. Rejected work leaves control, state, health, history, and cursors unchanged. A skipped tick does not advance the last-check timestamp; a responsive daemon alone does not prove checks are succeeding.

Pause and other holds remain saved. **Stop execution also waits for a verified configuration:** the supervisor cannot safely observe or stop a target from an unverified snapshot. Repair the configuration and let the daemon reload (on its interval or the next control change), or reload and retry the command. Once verified, stop retains precedence over pause, disabled, completed, and awaiting-user holds. If the agent must stop before repair, use its provider's own stop control against the verified target. A changed `state_dir` requires restoring the original binding or restarting deliberately; the daemon never moves its lock or diagnostics automatically.

This is a prerequisite for a future cooperative thread-transfer operation, not a transfer feature. Only writers using the same `tick.lock` are serialized with provider work; arbitrary external file edits can still race after verification. The check covers the loaded YAML sources (`keepgoing.yaml` and `fallbacks.yaml` or the standard route list), not referenced prompt/secret files, executables, or runtime records. Private source digests are kept only in memory and are not serialized or printed. Byte-identical replacements are accepted. No target-state reset, cursor/session migration, or automatic thread transfer is implemented.

## Starting supervision

After reviewing a configured task, choose one:

```sh
keepgoing start --foreground -c /path/to/keepgoing.yaml
keepgoing start --background -c /path/to/keepgoing.yaml
```

`start --background --json` (v0.2.0) prints one JSON object on stdout instead of the sentence: `{"schemaVersion":1,"outcome":"started","pid":4242,"control":"…"}` when the daemon has started, `{"schemaVersion":1,"outcome":"failed","exitCode":1}` when it has not (the reason stays on stderr), or the same refused object `init --json` gives when another enabled loop supervises the session: `{"schemaVersion":1,"outcome":"refused","refusal":{"code":"second_loop_on_session","otherLoop":"example-loop"}}`. `--json` is accepted with `--background` only. Builds before this reject the flag; check the version first. `enable` has no JSON output and prints its refusal on stderr.

`start` defaults to foreground. It validates configuration and fallbacks, readable task-file type/access, recorded state/health and active target, configured agent executables, and headless working/account directories. Custom process command executables are checked without executing them. These are local setup checks; they do not verify authentication, provider access, model quotas, or the live target. No login command or probe runs during startup validation. Once started, ordinary ticks can send prompts and run configured probes. Use `doctor --offline` for a read-only inspection instead of starting supervision. `start` does not accept `--dry-run` or `--take-over`; transfer ownership explicitly first if needed.

Start acquires `daemon.lock` before changing controls, then the tick lock and short control lock. Another daemon returns exit 75 with no control changes. A scheduler tick in progress also returns 75; retry later. Start records a BB owner just like `enable`, refuses a conflicting owner, and sets `enabled` while preserving pause, stop, awaiting-user, completion, and the note. It never resumes a held task, retargets a session, or changes an external schedule. An existing stop is still processed by the ordinary tick, even while paused. External schedulers do not continuously hold the daemon lock: start cannot detect every installed timer. Choose one scheduling method per loop and remove your old schedule explicitly before switching.

Foreground startup prints the control state, then tick results; Ctrl-C ends the daemon. Background startup launches a detached copy of this executable with the inherited environment and working directory, and waits up to ten seconds for that specific child's acknowledgement. Success means the child owns the daemon lock, has opened live diagnostics, and has enabled the loop; it does not promise the first tick or a provider action has succeeded. Validation or diagnostic startup failures leave controls unchanged. A timeout or interrupted acknowledgement terminates the child; if it had already enabled the loop, that flag remains. Inspect `status` before retrying; crashes cannot make a multi-process start transaction atomic.

The background daemon disconnects from terminal input/output. Tick decisions and outcomes remain in private `state.json` and `runs.jsonl`; raw daemon stdout/stderr is discarded. Use `status`, `doctor`, and, when troubleshooting raw command errors, foreground mode. `pause`, `complete`, `await-user`, and `disable` hold future work while the daemon stays alive. `stop` stops the agent on a check and holds future prompts; it does not exit the daemon. To end the daemon itself, terminate the printed PID (SIGTERM on Unix, `Stop-Process -Id <PID>` in PowerShell). Ending it does not stop the agent.

Background mode survives the launching terminal closing. It does not install a user service, restart after crashes or reboots, or guarantee survival across OS logout/session cleanup. It cannot execute while the host sleeps or is off. After wake, the next available check applies current controls; there is no catch-up queue of missed ticks. Network errors retain the normal structured-error policy; in v0.2.0, recovery [waits while the connectivity check fails](#network-outages). macOS and Linux user-service management are available separately through [`service install|status|remove`](services.md); live service lifecycle verification remains roadmap work. Windows service support is still planned; see the [Task Scheduler investigation](windows-services.md). Offline fixtures exercise detached startup, parent exit, duplicate refusal, status, holds, and stop with a local process adapter; no live model call or multi-account handoff is part of these checks.

## Exit codes

| Code | Meaning |
| --- | --- |
| 0 | ok |
| 1 | failed: keepgoing could not run or could not record its result, or `fallbacks check` found redundancy unmet. For `tick`, see [the contract for schedulers](#exit-codes-for-external-schedulers) |
| 2 | usage or config error |
| 3 | `ci-wait`: no run appeared for the commit |
| 75 | skipped: the lock is held, another loop is acting on the same session (see [one loop per session](#one-loop-per-session)), a yield check reported other work, or `net-retry` waited longer than `--max-wait` for the network |
| 124 | `ci-wait`: timed out |

### Exit codes for external schedulers

Released in v0.2.0; fixture-tested only. The exit code of `keepgoing tick` says whether keepgoing ran and recorded the check. It does not say whether the session, the provider, the network or a repository was healthy. That is in the check's output and in `status`.

| `tick` exits | When | What a scheduler should do |
| --- | --- | --- |
| 0 | The check ran and was recorded. This includes a check that failed to observe or act: the session could not be observed, the target's adapter could not be built, a send or stop failed, a tracked repository or the fallback health file could not be read, or the operating window could not be evaluated. Such a check has `"outcome":"failed"` in its JSON line and in `runs.jsonl`, `outcome failed` in `status`, a line on stderr and an `error` report. A check that only left probes out for lack of time has outcome `succeeded` and a warning. | Nothing; run again on schedule. |
| 75 | The check was skipped: another tick holds the lock, another loop is acting on the same session right now, the yield command reported other work, or the configuration files changed while loading. | Treat as success. If the message says the other loop's process is stuck, a person should look (see [one loop per session](#one-loop-per-session)). |
| 1 | The check could not be recorded or could not start: `control.json`, `state.json`, the run log or incident history could not be read or written, the lock could not be taken, or loop ownership was refused. | Treat as a failure; a person should look. |
| 2 | Usage or configuration error. | Treat as a failure. |

Because such a failure no longer stops the scheduler, it must be visible another way. `status` prints `failed checks: N in a row since <time>` while consecutive checks fail, and `doctor` reports the same as a `supervisor.failed_checks` warning; both clear on the next completed check. Nothing escalates on that count by itself: one `error` report is sent for each failed check, and a persistent failure otherwise waits for someone to look. A check that could not observe its session reports `could not observe <target>` with the cause; before (v0.2.0) it sent that and a second `tick failed` report for the same failure, two notifications per check for as long as an outage lasted.

Before this change a check that could not observe or act exited 1. A scheduler that disables a job after a few consecutive failures (a BB automation does after three) was therefore switched off by an outage, and nothing ran when the network came back. Scripts that relied on exit 1 to detect a failed send should read `outcome` from the JSON line instead.

### External schedulers can stop on their own

keepgoing cannot run itself when an external scheduler stops calling it. Known ways this happens:

- The scheduler disables the job after consecutive failures or timeouts. A tick killed by the scheduler's own timeout writes nothing, so keepgoing's history simply ends.
- The host sleeps, reboots or loses the user session.

Nothing that has stopped can report that it stopped, so keepgoing judges it from the record, wherever the record is read. Released in v0.2.0; **fixture-tested only**.

**Which loops are judged.** Only an enabled loop that is not held: a paused loop, one waiting for a person, one declared complete and one whose requested stop a check has carried out may have had their scheduler stopped on purpose, and are never overdue. A requested stop not yet carried out is not a hold, because it needs a check. A loop that has never run a check is not judged. The time without a check is counted from the last check, or from the last change to its controls if that is later, so resuming, re-enabling or answering a loop starts the clock again. Only time inside the loop's [operating window](configuration.md#window) counts toward the time without a check.

**The overdue rule.** A judged loop is *overdue* when no check has been recorded for more than three times its usual interval, and never less than 15 minutes. The rule keeps its own record of the last five gaps between checks (`scheduleGapsNs` in `state.json`), uncapped, unlike the [missed-time rule](#time-in-which-no-check-ran)'s. With an operating window, only a gap wholly inside it is recorded, at its full length: a gap across a night or a weekend says nothing about how often checks run, so a scheduler that keeps running outside working hours, every 10 minutes, 30 minutes or hour, is not called overdue when the window opens, and nor is one whose first check of the day comes 20 minutes after it opens. The usual interval is the **second longest** of them, or `daemon.interval` if that is longer:

| Gaps seen (newest last) | Usual | Overdue after |
| --- | --- | --- |
| 10m, 10m, 10m | 10m | 30m |
| 10m, 10m, 4h, 10m, 10m (one outage) | 10m | 30m: one outage does not raise it for later checks |
| 10m, 10m, 10m, 10m, 1h (slowed to hourly) | 10m | 30m: the first hourly gap is still called stopped |
| 10m, 10m, 10m, 1h, 1h | 1h | 3h: learned at the second hourly gap |
| 10m, 10m, 10m, 24h, 24h (slowed to daily) | 24h | 72h |
| 5m, 1h, 5m, 1h, 5m (alternating) | 1h | 3h: never flagged |

Two outages within five gaps do raise it, until they leave the record. **Before three gaps** the usual interval is not known, and a loop is overdue only after 24 hours without a check, or three `daemon.interval`s if that is longer. With an operating window that is 24 hours *of its working hours*: on a Monday-to-Friday 09:00-17:00 window, three working days. A scheduler running every 8 hours that stopped would be flagged 118h56m after its last check. A new loop whose scheduler stops is still flagged, while a slow scheduler's first gaps are not taken for a stopped one. **Changing the window** starts the record again: gaps seen under the old window are set aside (`scheduleWindow` in `state.json` names the window they were seen under), so the rule falls back to the 24 hours until three gaps are seen under the new one.

**When it is not the scheduler.** Evidence is dated against when the last check *finished* (`checkFinishedAt`), so a check turned away while it was running does not count, and a time later than now (a clock that moved) is ignored.

- **A hung check.** A check that finds an earlier check still holding the tick lock exits 75 and records when it was turned away (`turned-away.json`). When that happened after the last check finished, the scheduler is running, and the message says an earlier check may be hung instead of blaming the scheduler.
- **Checks running but not recorded.** When the daemon running the loop has completed a pass that *began* after the last check finished (`lastPassStartedAt` in its status), that pass recorded nothing: the daemon is running passes that record nothing, for example because the state directory cannot be written, a lock fails or a source check fails. That holds for a daemon restarted since the last check too, as after an upgrade. Work a check does after it is saved, such as reports that time out, cannot make it look unrecorded, because its own pass began before it finished. The message says `checks are running but not being recorded`, and `doctor` points at the daemon's error output. A daemon that does not give `lastPassStartedAt` is judged by when its last pass ended (`lastPassAt`), more than a minute after the check finished, or failing that by the next check it set.
- **The computer slept.** When a daemon that answers `status` started before the last check, and there is none of that evidence of being awake, it has been running through the gap, so the computer slept. That is not overdue (`slept` in JSON). An older daemon that does not give `lastPassAt` is judged by the next check it set: one set after a pass since the last check means awake.

**Who says so, with no process of its own:**

- `status` prints `schedule:  no check has run for 3h10m (checks normally run every 10m): the computer may have slept, or the scheduler that runs `keepgoing tick` for this loop may have stopped`. `schedule` in `status --json` has `overdue`, `judging`, `notJudged` (`disabled`, `held` or `never_checked`), `basis` (`usual`, or `fallback` before three gaps), `gapsSeen`, `lastCheckAt`, `slept`, `blocked`, `notRecorded`, `startedBy` and `message`; `for`, `usual` and `threshold` only while it is judging.
- `doctor` adds `supervisor.schedule`: a warning when overdue; otherwise it says checks are running at their usual interval, or that the loop is not judged against one yet (`2 of 3 gaps between checks seen`), or that it is held.
- The panel lists an overdue loop under **needs you** (kind `overdue`), so the macOS menu's badge counts it, and the BB plugin's loop card says `looptender: checks have stopped` (`keepgoing: checks have stopped` before plugin v0.3.1) with the same sentence. The plugin says checks are running at their usual interval only for a judged loop whose usual interval is known.
- When the last check before the gap was started by a BB automation, they name it: `the computer may have slept, or the BB automation that runs this loop (auto_…) may have disabled itself; check it in BB's Automations`. That needs the automation to identify itself, as `keepgoing tick … --routine bb-automation/<automation id>` (see [run discovery](run-discovery.md)). It is never guessed from the configuration.
- `doctor --bb-automation <id> --bb-project <id>` reads the selected BB automation and warns `The selected automation is disabled; scheduled runs are not expected.` See [BB automation diagnostics](diagnostics.md#bb-automation-diagnostics).

**After the gap.** `check_gap` is **opt-in**: it is not in the default event list, so name it (or `all`) in `report.events` to receive it. The first check after an overdue gap then sends one report (`no check was recorded from <time> to <time> (3h10m, where checks normally run every 10m): the computer may have slept, or …`), naming a BB automation the same way. With an operating window the duration is the time inside it, and says so (`50m of its working hours`); before the usual interval is known it names the real threshold (`longer than the 30h …` with `daemon.interval: 10h`). It is sent after the check's own error report, if any, so it never takes a late-report slot that report needs. It is sent once per gap: the check saves its own record, which ends the gap, and only then sends the report, the way the error report is sent, with no entry in `sends.json`. Killed before that save, nothing was sent and the next check reports the gap; killed after it, the gap is over and is never sent again. Everything the check does first (stops, holds, records of earlier sends) comes before it. It makes a single attempt. A dry run sends nothing and leaves the gap (`checkGapPending`) and the last real check's `startedBy` for the next real check, which reports it. If that check has no time left for a report, the gap is not reported later.

**The bound.** With the macOS menu running, or the panel or the BB plugin open, a person is told within the overdue threshold plus one refresh (60 seconds for the menu, 30 for the plugin). With none of them open, a subscribed `check_gap` report tells them when checks run again. With the menu running from an app bundle, it also posts one macOS notification per gap, which stays in Notification Center until it is seen ([menu notifications](../integrations/macos/README.md#notifications-when-checks-stop)); it reads on its one-minute timer, so not in Low Power Mode, when it reads only when opened.

**Going back to an older binary.** `main` before this change and every release refuse a configuration whose `report.events` names `check_gap` (exit 2, unknown event): remove it first. Once a `check_gap` delivery has been recorded, their `LoadDeliveries` rejects `deliveries.json` because of the unknown event label, as for `limit_wait`: every later save of it fails, the delivery history stops recording, and their three once-only reports are sent again, up to three times each. Move that file aside, or upgrade again. They drop `checkFinishedAt`, `startedBy`, `scheduleGapsNs`, `scheduleWindow` and `checkGapPending` from `state.json` when they rewrite it: after going forward again the rule uses the day-long fallback until three gaps are seen, and a gap a dry run kept is not reported.

Prefer `keepgoing start`, the daemon or a managed [service](services.md) where one is available: the service manager restarts it, and it does not depend on a scheduler's failure counting. If you keep an external scheduler, give its timeout a comfortable margin over `loop.tick_timeout` (below) and treat exit 75 as success.

### Check time budget

Released in v0.2.0; fixture-tested only. A check has a hard limit: `loop.tick_timeout` (default `3m`) plus 90 seconds, so **4m30s at the defaults**. Whatever is slow, a check ends by then, apart from the two seconds a killed command is given to exit.

Each step is either mandatory, with a fixed maximum that is reserved for it until it has run, or optional, and then it runs only in time that no later mandatory step has reserved:

| Step | Kind | Maximum | Notes |
| --- | --- | --- | --- |
| Yield command | mandatory | `yield.timeout` (10s) | runs first |
| [Connectivity check](#network-outages) | mandatory when needed | `network.timeout` (8s) | reserved until it has run; made at most once |
| Observing the target (for BB: status, children, log, interactions) | mandatory | 90s for the whole observation, 30s per `bb` command | at the limit the check records `could not verify state; no action taken` |
| Scheduled fallback probes | optional | `probe.timeout` each (90s) | started only when the whole timeout fits; never shortened |
| Git progress fingerprint | mandatory | 60s for the whole fingerprint, 30s per `git` command | reserved until it has been taken |
| Exact probes before a handoff | optional | `probe.timeout` each | may be shortened to the time that is free |
| Exact probe before a switch-back | optional | `probe.timeout` | started only when the whole timeout fits |
| Model switch and send (wake, nudge, re-prompt or brief) | mandatory | 60s (30s per `bb` command) | reserved until the send has been made. A [handoff to a new thread](fallbacks.md#hand-off-to-a-new-conversation) uses the same 60s instead: read the place 10s, `bb thread spawn` 30s, look the thread up by title 20s. Looking for a thread whose creation is unsettled, at the start of a check, takes up to 20s out of the observation's 90s |
| Routine reports (`probe_failed`, `degraded`, `recovered`, `wake`, `nudge`, `reprompt`) | optional | two attempts of `report.timeout` (20s) each | sent only with at least 10s free, and limited to the free time |
| Essential reports (`await_user`, `error`, `stop`, `handoff`, `switch_back`, `complete`, `limit_wait`, `child_error`, `network_wait`, `check_gap`) | mandatory | 30s reserved: three reports of 10s each | use free time when there is some |

With the network down, each due fallback's scheduled probe ran to its 90-second timeout and was followed by a failed report, before the session was considered at all. Four due fallbacks made one check last over seven minutes, so a scheduler with a five-minute timeout killed it before it wrote anything.

How the time is spent:

- **Scheduled probes are never shortened.** One is started only when its whole timeout fits. A probe that then runs to its timeout is a real failure: recorded, reported, counted against the daily cap, and not due again until `probe.every`. One that does not fit is listed in the check's `probes` with `"skipped":"tick_timeout"`, a warning names `loop.tick_timeout`, and it stays due. So a fallback that hangs costs one check, after which the others are probed; it cannot starve them.
- **A due handoff comes first.** When the target is in an error that the loop fails over on and the redundancy rule is already met, the scheduled probes wait and the time goes to the exact probes the handoff needs. See [fallbacks](fallbacks.md#redundancy) for what that relies on. If no handoff is attempted after all (a limit wait, a hold, busy children), the scheduled probes run after the decision in the same check. If one is attempted and no fallback takes over, the held-back probes run then; while any of them ran or is still due, no re-prompt is spent and the check records a deferred handoff instead, within the limit below. After the late probes the redundancy picture and the `degraded` or `recovered` report are brought up to date.
- **Exact probes for a handoff may be shortened**, because a handoff is worth trying with the time there is. A probe stopped early is listed with `"skipped":"cut_short"`, is not held against the fallback, and the next candidate is tried in the same check. A fallback stopped early goes to the back of the order on the next check, so a hanging one cannot keep a working one from being tried.
- **A handoff that could not be confirmed is put off, within a limit.** The check records `handoff deferred: no fallback could be confirmed in this check; the next check retries` with the cause in brackets (incident cause `handoff_deferred`), spends no re-prompt and raises no hold. The limit is `errors.max_reprompts` such checks within one error episode, or the same number of early stops for one fallback. Past it the result is treated as real: the fallback's probe is recorded as failed, and the ordinary error rules act on the current target (re-prompts, then a hold, or a limit wait). The counts end with the episode, on the same evidence as the re-prompt count (the session seen idle, or active with Git progress), and on a handoff, switch-back, retarget or resume. They are not reset by a check in between, so the checks need not be consecutive: a fallback that is healthy but slower than the time left on three error checks of one long episode is recorded as failed. Raise `tick_timeout` or lower `probe.timeout` if that happens.
- **Mandatory steps are never cut by the accounting**, so a wake or re-prompt is not lost to slow probes and nothing is stopped in the middle of a write.
- Stop, pause and the other holds are handled before any optional work.

**Reports.** A routine report that cannot have ten seconds is not sent. The check's warnings say so and the delivery records get a `not_sent` entry with no request and no attempt, so `status` shows it among the notification warnings. Essential reports are still sent, three per check at most. The `limit_wait` and `child_error` reports make a single attempt per wait or episode; when no time is left for one, nothing is recorded and no request is made, so the attempt is kept for the next check.

**The limit, tested.** `TestCheckEndsWithinItsHardLimitInEveryCombination` charges every step either its maximum or almost nothing, independently (yield, observation, fingerprint, model switch, send), with probes hanging and reports failing on both attempts, against idle, active, rate-limited, unknown-error, auth-error and errored-children sessions, with and without previously healthy fallbacks, with the connectivity check configured throughout and failing at its timeout in some: 1,512 checks per configuration. The longest is 4m00s of the 4m30s limit at the defaults, and 4m30s of a 5m00s limit with `probe.timeout: 2m`. The same fixture run against the code before this accounting gives 4m40s and 5m10s. These are fake-clock figures: each step is charged its configured limit, and no command was actually hung. They rest on a limit being enforced by killing the command; a process that ignores the kill and keeps its output open is abandoned after two more seconds, and a filesystem call that hangs is abandoned, not stopped. Local file writes (state, run log, incident history) are not timed.

**Configuration.** The minimum `tick_timeout` is `2m40s`, the time the mandatory steps can take less the 90 seconds. The connectivity check uses only what `tick_timeout` has beyond that, up to `network.timeout`: at `2m40s` it is not made, and from `2m48s` it has its full 8 seconds. With fallbacks it must also be at least `probe.timeout` plus 90 seconds, or no scheduled probe could ever start. If `tick_timeout` is omitted it grows to that value, so a file with a long `probe.timeout` keeps loading; an explicit value that is too small is an error naming both settings. `status` prints the budget on its `check budget:` line and says when it was raised from the default (`tickBudget` in `status --json`), and `doctor` reports it as `supervisor.tick_timeout`. Those, and `validate`, warn when `tick_timeout` exceeds `3m15s`, because the limit is then over 4m45s and no longer leaves a margin under a five-minute scheduler timeout. That includes an omitted `tick_timeout` beside a `probe.timeout` above 105 seconds. The daemon and managed services have no such timeout.

## Status for other tools

`keepgoing status --json` prints the control file, state, window, and redundancy summary. It also prints `primaryAgent` and `targetAgent`, which describe the loop's own agent and the one it is supervising right now. Each has its `adapter`, `provider`, and `model`, plus `bbThread` for a BB thread or `workdir` for a headless runner. An agent workspace can use these to show keepgoing's state beside the right thread.

## Understanding recorded status

`keepgoing status` is read-only and makes no provider calls. It shows the task source (inline or a file, without task text), configured target/thread and quota group, current control holds, and the latest recorded decision. `status --json` keeps its existing fields and adds `taskSource`, optional `taskFile`, `targetConfigured`, and `runtime`; agent identities now include `group`. A missing or disabled fallback no longer appears to be the primary: `targetConfigured` is false and `targetAgent` is empty. Use `doctor` to check live BB target identity separately.

New ticks persist `state.lastCheck` with:

- `at`, the caller's `version`, and the final action `target`;
- `observedTarget`, `observedState`, and the structured `awaitingInput` flag, kept separate from the destination of a handoff;
- the selected `action` and supervisor-generated `reason`;
- `outcome` (`succeeded`, `failed`, or `dry_run`) and a `dryRun` flag.

`state.lastWakeAt`, printed as `last sent`, is the time of the latest wake, nudge or re-prompt attempt, including one whose adapter call failed or was unsupported. A failed send makes `lastCheck.outcome` `failed`. An unsupported send does not: the check records its action with outcome `succeeded` and a warning in the tick output, and only `lastPromptSend.outcome: adapter_error` marks the attempt. These describe a supervisor decision and its outcome. `succeeded` means the supervisor operation returned successfully, not that the agent turn or task finished. A failed send is not a successful action; a dry-run wake is a plan that was not executed. An action of `none` with outcome `succeeded` means a no-action check completed successfully. Raw provider errors and prompts are not copied into this record. Failures before a record can be saved leave the previous history intact. Older state files still load, with detailed history unavailable until a new tick records it.

`runtime.state`, `runtime.reason`, and `runtime.source` distinguish current control/configuration from history. Stop takes precedence, followed by disabled, paused, awaiting-user, and completed holds. Without a hold, an invalid configured target or closed operating window is shown before interpreting history. Historical states use names such as `recorded_active` and `recorded_idle`; they do not claim the agent is currently running. A structured pending interaction is `recorded_awaiting_input`, not inferred from a reason string. A failed check is `check_failed`; a dry run is `dry_run`. A target change or an unobserved target after handoff is not attributed the previous target's state.

`runtime.freshness` is `never`, `recent`, `stale`, or `future`. The default stale threshold is 30 minutes; use `--stale-after` above your scheduler's interval. Stale, future-dated, or incomplete history cannot establish current activity. Current control holds remain visible even with stale history. For a responding built-in daemon, `runtime.nextCheck` reports the next normal check time or an in-progress check; otherwise it remains unknown. A configured daemon interval does not establish an external scheduler's schedule.

`runtime.binaryComparison` compares the last recorded tick's build label with this status process: `match`, `different`, or `unknown`. Empty and `dev` labels are unknown. A different label can indicate a stale scheduler binary, but does not prove which build is newer or currently running. Doctor also flags a different recorded build. Manual and dry-run ticks can replace the latest history, so this is not a running-process inventory.

Existing `control.note` output is retained for compatibility; status is a private operational report. Doctor continues to withhold control notes, task text, environment values, and raw errors. This feature is implemented on `main`, not in v0.1.1, and is covered by offline fixtures for control precedence, failures, dry runs, handoffs, version comparisons, and legacy state.

## Completing a task

When the authorized work is finished and verified, the agent or operator runs:

```sh
keepgoing complete -c keepgoing.yaml --note "Example task verified"
```

This sets `control.completed` in `control.json` and records a control event in `runs.jsonl`. Status shows `completed` unless a higher-priority disabled, stop, pause, or awaiting-user hold is also set; JSON always exposes the completion flag. No model output or transcript text is inspected to decide completion. In v0.1.3 or newer, a new completion declaration also attempts a subscribed `complete` webhook event after saving control and appending the control log.

The standard-format event is `keepgoing.complete`, with `basis: explicit_declaration` and `verification: not_recorded`. Both standard and text formats say that completion was declared and keepgoing has not independently verified success. This does not contradict verification performed by the operator or agent; keepgoing has no independent acceptance evidence in this version. The private control note, task/prompt text and evidence descriptions are omitted from this notification.

Deduplication uses the persisted `completed` flag under the control lock. Only a false-to-true transition submits a report. Repeated `complete` commands, changed notes, enable, other holds, ticks and restarts do not replay it. An explicit `resume` clears completion, permitting a later declaration to submit a new report. Legacy completed records and declarations made without a subscription are not backfilled when reporting is enabled. A report describes the declaration at its recorded time; concurrent resume/stop or network delays may mean it no longer describes current controls.

Completion delivery makes one HTTP attempt without automatic retries or redirects, including network errors and 5xx responses. HTTP acceptance is not proof of human receipt. Control is saved before delivery, and delivery does not retain the control lock: stop and pause remain available while the webhook waits. Report failures warn without undoing completion. A crash, log-append failure or reporter configuration failure after control is saved can lose the notification; repeated commands intentionally do not replay uncertain delivery. A bounded [diagnostic delivery ledger](diagnostics.md#notification-delivery-evidence) now records setup/attempt/HTTP outcomes in v0.1.3 or newer, with receipt always unverified. It does not authorize retries or repair crash gaps before reporting begins; there is no retry command. Do not resume/re-complete solely to retry a notification: resume reopens work. This is an at-most-once submission policy, not an exactly-once delivery guarantee; external writers, storage loss, deletion/rollback of private control state and older binaries are outside deduplication guarantees. Verification uses local webhook and command fixtures, not a live completion event from this project loop.

On the next check, a completed loop skips observation, yield checks, progress reads, scheduled probes, wakes, retries, handoffs, and switch-back. The hold survives process restarts. A pass already in flight can finish before noticing the change. Completion does not terminate the current agent turn or cancel messages already queued by another caller; use `stop` when the running turn must end. Stop still wins even when completion is set.

Declaring completion also ends a wait on a person, so `status` shows the loop as completed and not as awaiting user. What the person was being asked is not thrown away: the hold may have been raised by a check (a child waiting on a person, a spent cap), its note is stored nowhere else, and a completed loop stops observing. `complete` prints that a question was still open (without repeating the note), `control.json` keeps the hold's note and the time as `openQuestion`, `status` shows it on an `open question:` line until a `resume`, and the `complete` entry in `timeline` records that an awaiting-user hold was outstanding. The incident history never stores notes, so the note itself is only in `control.json` and `status`. A pause or a stop is the operator's and stays.

To reopen the task, or continue with a revised `prompt` or `prompt_file`, run `keepgoing resume`. Resume explicitly clears completion along with pause, stop, and awaiting-user, and clears the old note. It preserves the current target and session; it does not create a fresh conversation. It also does not enable a disabled loop: use `enable` separately in that case. `enable` alone never clears completion. Manual commands such as `fallbacks check` remain explicit operations and can still run while a task is completed.

Use `await-user` when unfinished work needs a person, and `complete` when all authorized work is done. If the task is an entire roadmap, completing one item is not completion of the task.

## Bounds on repeated work

keepgoing repeats work by design: each ordinary check may send one message to the session. Which rule applies depends on what the adapter reports.

| Session | Sent | Spacing | Count kept | Count resets when |
| --- | --- | --- | --- | --- |
| Idle | wake | none: every eligible check | none | not applicable |
| Active, Git fingerprint unchanged for `stall_after` | nudge | `min_wake_interval` since the last send | `max_nudges` | the fingerprint changes, or the session is seen in any state other than active |
| Error | re-prompt (for a BB target in v0.2.0, a [retry of the failed turn](#recovering-a-failed-bb-turn-by-retry) with no new prompt) | `errors.backoff` | `max_reprompts` | the session is seen idle (a turn ended without an error), or it is active and the Git fingerprint changes |

The nudge and re-prompt caps each bound one stalled turn or one error episode. They are not a bound on total work: a session that keeps finishing turns is woken again on the next check, and both counts start over. Seeing the session active does not by itself restart the re-prompt count, because a re-prompt makes the session active: a re-prompted turn that fails again spends the same allowance, so repeated failures reach the hold. Git progress restarts it only while the session is active. A change first seen on a check that finds the session in error does not, although the fingerprint is taken there and no later check sees it: the fingerprint covers every worktree, so lanes, other loops and people change it, and a session that never leaves error would otherwise be re-prompted for as long as anyone committed, with no backoff and no hold. A session that worked, committed and failed again between two checks therefore carries its count into the new failure; telling that apart needs evidence about the session's own turns, which is a [roadmap item](roadmap.md#priority-reliability-checkpoints). The rejected handoff-brief counts restart on the same condition. The condition is evaluated at checks, so it is coarser than "one error": the count carries over when a session works for hours without a commit and then fails again, and when queued input starts the next turn before any check sees the session idle. Unrelated errors can therefore share one allowance and reach the hold sooner than three failures of the same kind would. Without `progress.repositories` there is no Git evidence, and the count restarts only when a check sees the session idle. An explicit [`keepgoing resume` starts a new episode](#what-resume-starts-over), so a loop held on a spent cap recovers again on the next check. Before the count was tied to evidence of recovery (v0.2.0) any active check restarted it, so a session alternating between active and error was re-prompted without limit. A handoff also restarts the re-prompt count, and a switch-back restarts both. With no `loop.limits` field configured, which is the default, nothing limits how many times this repeats. Sending then stops only through `complete`, a stop, pause or disable, or an awaiting-user hold: a per-episode cap, an auth error without a handoff, a missing target, or a child waiting on a person. Other gates, such as the operating window, queued messages, running children or a pending interaction, defer a send without ending the repetition.

v0.2.0 makes that visible. `keepgoing validate` prints a `warning:` line on stderr when none of the three limits below is configured, and otherwise a `bounds:` line naming those that are. `keepgoing status` prints the same on its `bounds:` line, and `status --json` adds `workBounds` with `limits` (configured limit names in decision order, possibly empty), `unbounded` and, when unbounded, `warning`. The warning is advice about the loaded configuration only: no default limit is applied, nothing is refused, exit codes are unchanged, and it says nothing about whether a configured limit has been reached. Other commands, including `start`, `tick` and `doctor`, do not print it.

#### What `resume` starts over

A check holds the loop for a person when a per-episode allowance is spent: the re-prompt cap (`error persisted after re-prompts`), the nudge cap (`no progress after N nudges`), or the patience for a silent provider retry. An explicit `keepgoing resume` of that hold, from the command line or a registered client, is a person saying "try again". It clears the holds and starts a new error episode:

| Started over by a `resume` of such a hold | Never refunded by `resume` |
| --- | --- |
| the re-prompt count and its `errors.backoff` clock | `loop.limits.max_sends`: sends used stay used |
| the nudge count, and the silent-retry clock of a loop without Git tracking | `loop.limits.deadline`: an absolute time |
| rejected handoff and switch-back brief counts, and handoffs put off for lack of time (these on every `resume`, whatever was held) | `loop.limits.no_progress_timeout`: the ledger of the last Git change |
| attempts of a child-error notice that was given up (on every `resume`) | the new-conversation cap (`loop.limits.max_new_threads`) and its spacing |
| | the count of turn retries the provider answered with nothing to do |

**Only that hold starts a new episode.** keepgoing marks it when a check raises it (`episodeHold` in `control.json`); no command can set the mark. A `resume` with nothing held, or of a hold a command created (`pause`, `stop`, `await-user`, `complete`), or of any other hold a check raised (a deadline, the send limit, a child waiting on a person, an auth error), leaves the re-prompt and nudge counts and the backoff alone. Otherwise holding and resuming before every check, by a person or by the owning agent, would refund the episode that is running: a session in error was re-prompted at every check with no backoff, cap or hold. To get a new episode the allowance has to be spent first, so each resume buys at most `max_reprompts` re-prompts or `max_nudges` nudges, and `loop.limits` bounds the total. A `resume` that starts no episode still gives a repaired fallback or primary fresh takeover briefs, as it always has.

**It is recorded and counted.** The `resume` entry in `timeline` says who ran it, as a role and never an identity (the owning BB thread, another BB thread, a terminal with no BB thread identity, a registered local client), and says when it started a new episode. `status` prints `resumed episodes: N (last <time>)`, and `state.resumeEpisodes` in `status --json`, so a loop that has been resumed out of its cap many times shows it. Known limit: the role comes from the `BB_THREAD_ID` environment variable, so the owning agent running the command with that variable unset is recorded as a terminal.

The reasoning: the per-episode counts exist to stop keepgoing repeating itself unattended. Once a person has looked and resumed, they have served that purpose, and keeping them made `resume` do nothing: the next check found the same spent count and raised the same hold, and the only ways out were to raise `max_reprompts`, or to `retarget primary` and then resume. The loop-wide limits are the owner's budget for the whole task, set on purpose, so only editing the configuration moves them; a resume with one of them reached holds again on the next check, as before.

A new episode is bounded like the first. If the session still fails, it is re-prompted up to `max_reprompts` times and held again, and every attempt still counts against `max_sends`. `resume` does not touch the time of the last send, so `min_wake_interval` still spaces the next nudge. It spaces nudges only: the first re-prompt of a new episode is sent by the next check, with no backoff, because the backoff belongs to the episode that ended. `enable`, a restart and a configuration edit do not start a new episode; `retarget`, a handoff and a switch-back do, as before.

If the saved counts cannot be reset, `resume` changes nothing: it says so and that the loop is still held, records nothing, and exits 1. The registered resume does the same with the issue `new_episode_unconfirmed`; its ticket is spent, as after any failure once it was consumed, so prepare again after repairing `state.json`.

Covered by `TestResumeStartsANewErrorEpisodeAndRefundsNoLoopWideLimit`, `TestHoldingAndResumingByHandDoesNotRefundTheRunningEpisode` (nothing held, and `pause`, `await-user`, `stop` or `complete` before each of eight checks: one re-prompt each), `TestResumeAfterASpentRepromptCapRecoversOnTheNextCheck`, `TestResumeChangesNothingWhenTheEpisodeCannotBeSaved`, `TestClientResumeStartsANewErrorEpisode`, `TestClientResumeFailsWithHoldsIntactWhenTheEpisodeCannotBeSaved` and, through the built binary, `TestScenarioHeadlessFirstTurnFails`. Offline fixtures only.

**Upgrading and rolling back.** This build writes incident schema 10 (`incidents.json`; schema 9 added who ran a resume and whether it started an episode) and two new fields elsewhere: `resumeEpisodes` in `state.json`, and `episodeHold` and `openQuestion` in `control.json`. Upgrading needs nothing: an older journal is read and rewritten in place. One thing to know: a hold raised before the upgrade carries no mark, so the first `resume` after upgrading starts no new episode; the next check raises the hold again, now marked, and the `resume` after that does. Rolling back is not only a matter of restoring the binary:

- An older binary does not read a schema 10 `incidents.json`. Its `tick` exits 1 with `incident history unavailable`, `start` refuses to start, and `timeline` exits 1. Before running the older binary, restore `incidents.json` from a copy taken before the upgrade, or remove it; removing it loses the incident history and nothing else.
- The older binary ignores the new fields and drops them the first time it saves those files: the count of resumed episodes, the mark that lets a resume start a new episode, and an open question kept by `complete` are lost. A loop held on a spent cap then behaves as it did before this change: `resume` clears the hold and the next check raises it again.

Take a copy of the state directory before upgrading a loop you may need to roll back.

Three optional limits apply across turns, targets, restarts and resume. Each persists an awaiting-user hold on the next ordinary check after it is reached:

| Limit | Counts | Not reset by |
| --- | --- | --- |
| [`max_sends`](#total-send-allowance) | automatic send attempts of every kind, including failed ones | progress, turn completion, handoff, restart, resume |
| [`deadline`](#loop-deadline) | host-clock time against an absolute cutoff | restart, resume, retarget; only editing the configured value moves it |
| [`no_progress_timeout`](#no-progress-timeout) | host-clock time since the Git fingerprint last changed; in v0.2.0, less [time in which nothing could run](#a-long-time-offline) | turn completion, recovery, handoff, restart, resume |

`max_sends` is the only count-based bound on total sends. The two time limits bound how long checks continue, so the number of sends they allow depends on the check interval. `no_progress_timeout` also needs Git to be a meaningful progress signal for the task.

Precedence is fixed. Stop wins over everything and is the only rule that acts on a running turn. Disabled, paused, awaiting-user and completed come next and send nothing. Then `deadline`, `max_sends` and `no_progress_timeout`, in that order, each ahead of every observation of the session.

What the limits do not cover:

- A turn already running or queued is not cancelled, and nothing bounds how long one turn runs or what it spends. Only `stop` reaches a running turn.
- Scheduled and exact probes, activation and manual commands are not counted by `max_sends`. Scheduled probes keep their own daily cap and stop once any limit hold is persisted.
- The per-episode caps and spacing count attempts, not deliveries. Once the adapter has been called for a wake, nudge or re-prompt, the attempt advances `max_nudges` or `max_reprompts` and starts `min_wake_interval` or `errors.backoff`, whether the call returned cleanly, failed or was unsupported. keepgoing cannot tell a failed send from one that was delivered before the error, so it treats both alike. The cost is that an adapter whose sends keep failing reaches the awaiting-user hold after `max_nudges` or `max_reprompts` attempts even if none arrived; inspect the adapter, then `resume`. In v0.1.5 and earlier, a failing send was retried such a send on every check with no cap or spacing. An idle wake has no cap either way: a failing wake is still attempted on each eligible check, bounded only by `max_sends` and the time limits.
- Rejected handoff and switch-back briefs are bounded per target in v0.2.0, as described under [rejected takeover briefs](#rejected-takeover-briefs). In v0.1.5 and earlier a fallback that passed its exact probe but rejected the brief was probed and sent to again on every check.
- The bounds depend on the private runtime records described in the sections below. Deleting or rolling them back, power loss, storage corruption and older binaries are outside what is tested.

Evidence is offline only. Decision tables enumerate every session state and error class against each observation gate, the operating window, switch-back, failover and spent or fresh per-episode counts. For each combination they check that a reached limit asks for a person and never sends, and that stop and the other holds win with or without a limit reached. A supervisor fixture with a fake adapter repeats wake, stalled nudge, wake and error re-prompt across completed turns with no Git change. With no limit it sends on every eligible check for twelve rounds without a hold; with each limit, and with all three together, sending stops at the configured point, one awaiting-user report is made, later rounds send nothing, and a stop request still reaches an active turn. Separate pure tables replay one-minute checks through the decision and the attempt accounting, and a fake-adapter fixture with failing and unsupported sends checks two attempts a backoff or wake interval apart, then one hold, where the earlier code sent on 20 of 20 checks. These tests establish when keepgoing stops sending in those fixtures. They do not establish that an agent's work terminates, and no live provider, installed service or paid call was used.

### Recovering a failed BB turn by retry

Released in v0.2.0; **offline fixtures only**, not verified against a live BB thread.

When a BB thread's turn fails, for example after a lost connection, keepgoing used to re-prompt it: each attempt sent the wake prompt again with `bb thread tell`. BB accepts a message into the provider session even when its turn then fails, so a session that failed three times held three more copies of the task, and all of them ran when it recovered.

The re-prompt decision is now carried out with `bb thread retry <thread> --json`, which re-submits the failed turn by reference. keepgoing sends no text. BB adds no user message to the timeline and increments the turn's attempt number. What BB sends the provider is BB's own business: an input the provider never accepted is sent again as it was, and a turn the provider had already accepted is continued with a short nudge from BB.

- **When it is used.** Only for a re-prompt decision on a BB target in error whose class is `network`, `overloaded` or `unknown`. A rate limit without a reported reset is still re-prompted with the prompt, an auth error is still held for a person, and wakes, nudges and handoff briefs are unchanged. The choice is a pure rule, `decide.RecoverBy`.
- **Same bounds as a re-prompt.** One attempt per `errors.backoff`, at most `errors.max_reprompts` per error episode, and one unit of `loop.limits.max_sends`. The attempt is counted when BB acted on it, refused it, or gave no readable answer. Two answers say BB did nothing for this request, and those are not keepgoing's attempt: a retry BB already has queued, and a thread that is no longer in error. Neither spends the cap or starts the backoff, and the reserved send is returned; this is the one case where a reservation is refunded. A session that never recovers ends in the same `await_user` hold as before, now without a single extra prompt.
- **What BB answers, and what keepgoing does.** Only the JSON result on stdout is read; BB's message text is never read or stored.

| BB result | Recorded as | keepgoing then |
| --- | --- | --- |
| `ok: true`, `delivery: "sent"` | `retried` | nothing more; reports `reprompt` |
| `ok: true`, `delivery: "queued"` | `queued` | nothing more; BB runs it when the thread is free or the retry is due. The queued row counts in `queuedMessageCount`, which already stops further recovery. |
| error code `no_failed_turn`, and a fresh `bb thread show` still reports `error` with nothing queued | `nothing_to_retry` | sends the prompt, as a re-prompt always did, under the same attempt. The thread failed before it dispatched a turn. |
| error code `no_failed_turn`, and the thread is no longer in error, has something queued, or its status cannot be read | `not_in_error` | sends nothing and counts nothing. BB's own retry or a person restarted it after it was observed; a prompt in auto mode would steer that live turn. |
| error code `unknown_command` | `unsupported` | sends the prompt: a BB release without `thread retry` behaves exactly as before |
| error code `retry_already_queued` | `already_queued` | sends nothing and counts nothing: the retry that is waiting is not keepgoing's |
| `retry_already_queued` on more than three consecutive checks (the prompt goes on the fourth), and a fresh `bb thread show` still reports `error` with nothing queued | `queue_unconfirmed` | sends the prompt, counted as a re-prompt. Any check between them that ends otherwise, including one that finds the retry in the queue count, starts the count again. A retry that is waiting is a queued message, and an errored thread with queued messages is not re-prompted at all, so this pair contradicts itself. It is treated as unknown and the ordinary error rules apply, which ends in the hold instead of asking BB on every check for ever. |
| any other code, an unreadable result, a timeout, or `ok: true` without a known `delivery` | `refused` | sends nothing, counts the attempt and records the check as failed. An unexplained refusal is not evidence that the turn is gone. |

- **Children in error.** A turn retry has no text to carry the notice about errored children. Where the rules give a re-prompt that notice, the retry is followed in the same check by the short notice-only message that the extra wake for errored children uses. It never contains the task, it is one more send against the allowance, and it is recorded as announced or rejected exactly as when a prompt carries it. Nothing is announced when nothing was retried.
- **Time.** The retry is given 12 seconds and the status re-read 10, so that a retry, a re-read and the fallback prompt still fit the 60 seconds reserved for a send.
- **Where it shows.** The check's JSON has `recovery: turn_retry` or `prompt`. `status` prints the last recorded turn retry (`turnRetry` in JSON), `timeline --kind turn_retry` shows each one, and `runs` lists it among the sends. The `reprompt` report carries `recovery`, `delivery` and BB's attempt number. A dry run previews the method and calls nothing.
- **Stop and holds.** Unchanged and first: a stopped, paused, disabled, completed or awaiting-user loop is not observed and nothing is retried.
- **After an outage of any length.** Nothing in this path depends on how long the thread sat failed. BB applies no age limit to a retry: it needs only the thread in `error` and its last turn request stored. Fixtures run the first check 20 minutes, 4 hours, 3 days and 3 weeks after the failure, with no check in between, and require one recovery attempt, no hold and nothing else spent, for each answer BB can give. If the provider session itself is gone after a long gap, the retried turn fails again, each attempt is counted, and the loop ends in the ordinary hold with its one `await_user` report; it does not stay silent.
- **An unknown error that is really a limit.** A provider failure that carries no recognised code is `unknown`. If it is in fact a usage limit the provider did not label, the retry runs into the same limit and fails again, as a re-prompt did, until the cap is spent and the loop holds.
- **Run graph.** A turn retry is recorded as a `reprompt` send with mode `turn_retry` and no goal reference, since no prompt was composed. A build without this change treats a graph containing that mode as unreadable.
- **What this does not do.** It does not itself know whether the network is back. The [connectivity check](#network-outages) decides that first: while it fails, nothing is retried and no attempt is spent. With `network: {check: "off"}`, a retry made while the connection is still down is accepted by BB, fails again and spends an attempt, exactly as a re-prompt did, so checks that run during an outage can use up `max_reprompts`. It also does not restart failed child threads; that is [lane recovery](#lane-recovery), which is opt-in.

### Rejected takeover briefs

A fallback can pass its exact probe and still not take the loop: its adapter cannot be built, its model cannot be applied, or the brief send fails or is unsupported. The same can happen to the primary on switch-back. v0.2.0 counts those rejections so the same target is not probed and sent to on every check.

**Handoff.** Each fallback has its own count and spacing within one error episode:

- After a rejection, that fallback is skipped until `errors.backoff` has passed. Skipped means not probed and not sent to.
- After `errors.max_reprompts` rejections it is skipped for the rest of the episode, and the next healthy fallback is tried.
- The episode ends on evidence that the session recovered: a turn that finished without an error (the session is seen idle), or verified Git progress while it is active. It also ends when a handoff or switch-back succeeds, on `retarget`, on a BB transfer and on `resume`. The counts then start over.
- Seeing the session active does not end the episode. A re-prompt from keepgoing, or a provider retry, makes it active; if that turn errors again the fallbacks stay capped. Without `progress.repositories` there is no Git evidence, so only a finished turn ends it.
- Every brief send is still reserved against `max_sends`. A failed adapter build or activation happens before the send, so it counts toward the cap but not toward `max_sends`.

When no fallback can be offered a brief on a check, the loop does what it already did when no fallback could take over: it waits for a reported reset, or applies the re-prompt rules to the current target and holds once those are spent. The reason, hold note and report then say that every confirmed fallback is capped or backing off after rejecting its handoff brief. The tick's `handoff.skipped` lists each skipped fallback as `backing_off` or `capped`.

**Switch-back.** Attempts were already spaced by `switch_back.retry_every`. After `errors.max_reprompts` rejected switch-back briefs, keepgoing stops trying and keeps the fallback working. No hold is raised, because the loop is still running on the fallback. When the cap is reached it sends one `switch_back` report whose data has `stopped: true`, so a subscriber must not read every `switch_back` report as a completed move. Each later check carries a warning, and `status` prints a `switch-back: stopped` line and sets `takeoverBriefs.switchBackStopped`. There is no time-based retry: it starts again only after `resume`, `retarget` or the next handoff.

**Trying a repaired target again.** `keepgoing resume` [starts a new episode](#what-resume-starts-over): it clears all rejected-brief counts, for fallbacks and for switch-back, as well as the holds and the re-prompt and nudge counts. Use it after repairing a fallback that was capped while the primary is still in error, or after repairing the primary when switch-back has stopped. `keepgoing retarget <id>` clears them too and moves the loop without waiting for a brief. Pause, enable and the other controls leave the counts alone. The registered `client resume` does what `resume` does. `status` lists capped fallbacks on a `handoff briefs:` line and in `takeoverBriefs.capped`.

**A brief that arrived anyway.** A send reported as failed may still have been delivered. keepgoing then counts a rejection and keeps the loop pointed at the current target while that fallback starts working. It can be sent up to `errors.max_reprompts` briefs in total, and a later fallback may also be handed the loop, so two sessions can work on the task at once. This is the same uncertainty as a failed wake or re-prompt; check the fallback's session when a handoff brief is reported as failed.

**Dry runs.** A dry run previews the first fallback that would be offered a brief. When none would be, it previews the wait or hold a real check would reach. It changes no counts, but, like any check, it records that it ran.

**Why per fallback, and what it costs.** The count belongs to one fallback so that a single broken fallback cannot use up the attempts of a healthy one that is listed after it. The cost is more total attempts: with N fallbacks that all reject, one error episode can make up to N times `max_reprompts` probes and brief sends before the loop falls through. A single count for the whole episode would cap that total at `max_reprompts`, but one fallback's failures would then stop the others from being tried. The rule is one pure function, `decide.BriefGate`, applied per fallback in the handoff loop, so changing to a per-episode count is a small change. Both limits reuse `errors.max_reprompts` and `errors.backoff`; there is no separate setting.

Evidence is offline: a decision table for the gate, and fake-adapter fixtures with a rate-limited primary and two fallbacks that pass the probe and reject the brief, with and without a reported reset. In those, each fallback is probed and sent to twice, ten minutes apart, over forty one-minute checks, where the earlier code did so on every check. Further fixtures cover an error, active, error sequence that keeps the caps, recovery that clears them, a fallback whose adapter cannot be built, a restart mid-episode, older state files, `resume`, `retarget` and transfer. No live handoff was run.

## No-progress timeout

In v0.1.3 or newer, set `loop.limits.no_progress_timeout: 2h` or use `init --no-progress-timeout 2h`. It requires at least one `progress.repositories` entry and a duration of at least one minute; zero/omission disables it. There is no default timeout. This measures elapsed host-clock time without a change in the existing Git metadata fingerprint, not useful work, goal completion, tokens or spend. Research, discussion and untracked files may leave no fingerprint change: use a deadline or send allowance when Git is not an appropriate progress signal.

The first enabled ordinary tick saves a baseline in private `progress.json` before any automatic provider observation, yield command or probe. Subsequent ticks verify Git again. A changed fingerprint for the same repository list resets the timer; an unchanged fingerprint at or beyond the timeout persists/reports an awaiting-user hold. Progress is checked even outside the operating window or while the agent is busy. No running or queued turn is cancelled. Stop, existing holds, the absolute deadline and exhausted total-send allowance take precedence. A failed read, fingerprint or ledger write prevents automatic provider work with a diagnostic error; unknown evidence never grants more time.

The ledger is independent of diagnostic history, target identity and per-turn retry/nudge counts. Repeated idle turns, errors, handoffs, switch-back, restart and resume do not reset it. Elapsed time includes operating-window closures while checks keep running. Elapsed time still includes pauses and disabled or held periods while checks keep running. v0.2.0 no longer counts time in which no check ran at all (a host that slept, a stopped scheduler) beyond one ordinary interval, or time in which the connectivity check found the network down; see [a long time offline](#a-long-time-offline). It is still not active execution time. Reordering or duplicating repository entries does not alter the source identity. Changing the source list rebases the fingerprint while preserving elapsed time, so a configuration edit alone is not progress. Dry runs preview the result without changing this ledger or controls. Child-completion polling skips provider queries when the saved timer is due, unavailable or lacks a baseline, leaving fresh Git verification to the next ordinary tick.

Once held, new Git changes or a configuration edit alone do not reopen supervision. Inspect the work and tracking, then explicitly `resume` after verified progress, increasing the timeout, or disabling it under the task's authorization. Resume alone with unchanged Git and an expired timer immediately holds again. Re-enabling a disabled timeout uses the retained ledger. A fresh state directory starts a fresh baseline; deleting/rolling back the ledger loses the bound and is not a recovery method.

`status` reports `progressAllowance` with `timeout`, historical `changedAt` and `observedAt`, and `due`; unavailable evidence instead has `error`, and a new allowance has `baselinePending`. Status does not query Git or change the ledger. `due` means the saved timestamp has reached the interval: a future tick may verify new progress, so it does not prove that a hold has been applied. The allowance summary adds no repository paths or fingerprint hashes; the existing diagnostic `state` fields are unchanged. Host-clock rollback before the last observation fails closed until corrected or caught up; forward jumps can cause an earlier hold. Persisted holds survive clock changes.

The tick lock and synced replacement preserve accounting across process restarts; power loss, storage corruption, manual deletion/rollback, external writers ignoring the lock and older binaries are outside this guarantee. Manual commands remain outside the automatic bound. Verification uses offline state/decision/supervisor and CLI fixtures, including real Git metadata in a temporary fixture repository. No live model or installed service was used.

## Total send allowance

In v0.1.3 or newer, set `loop.limits.max_sends: 20` or use `init --max-sends 20` to allow at most 20 automatic send attempts while accounting is enabled for that state directory. Zero or omission disables accounting; there is no default cap. Setup previews the limit. `status` exposes `sendAllowance` with `max`, `used`, `remaining`, and `reached`; an unreadable ledger instead has `error` and omits unknown counts. These are local accounting facts, not proof of delivery or agent completion.

Wakes, stall nudges, error re-prompts, handoffs and switch-backs share the allowance. Each attempt is reserved in private `sends.json` before calling the adapter; in v0.2.0 [every send is recorded there first](#a-send-recorded-before-it-is-made), with or without a limit. Failed, unsupported or uncertain sends consume an attempt; a process exit after reservation can consume one without delivery. In v0.2.0 a [turn retry](#recovering-a-failed-bb-turn-by-retry) is reserved the same way, and is the only attempt that can be returned: when BB answers, in its structured result, that it did nothing for the request. Multiple fallback attempts in one tick each count. Probes, activation, manual commands and prompts sent outside keepgoing are not sends under this limit. It is not a token, monetary or agent-turn budget, and it does not stop work already running or queued.

The next ordinary tick after exhaustion persists/reports an awaiting-user hold before automatic provider queries, probes, yield or fingerprints. Exhaustion during failed recovery prevents further sends and holds in that tick. Stop and existing holds take precedence. Child polling does not query providers or consume notices when exhausted or accounting is unavailable. Dry runs reserve nothing and persist no hold. Repeated checks retain the hold without repeating its report.

Restart, progress, turn completion, target changes, ownership takeover and resume do not reset the count. To continue, increase the total cap under the task's authorization and explicitly `resume`; changing configuration alone retains the hold. Disabling the cap permits uncounted sends after resume but preserves the previous count, which applies again if re-enabled. The allowance starts at zero when first enabled in an existing state directory; earlier activity cannot be reconstructed. A fresh state directory has a fresh allowance. Never delete or roll back the ledger to recover from exhaustion. There is no reset command in this version.

Malformed, unreadable or unwritable accounting fails closed with a diagnostic error; no unverified allowance is assumed. Repair runtime access or restore the last trustworthy ledger before continuing. The tick lock serializes reservations, and synced temporary-file replacement preserves them across process restarts independently of `state.json`. This does not guarantee survival of power loss, storage corruption, manual deletion/rollback, external writers ignoring the lock, or an older binary that does not implement this limit. Verification uses offline CLI, decision and supervisor fixtures, including simulated exit before recording a check; no live provider was used. A separate [no-progress timeout](#no-progress-timeout) is available in v0.1.3 or newer.

## A send recorded before it is made

Released in v0.2.0; **fixture-tested only**. A check used to save what it did only at its end, in `state.json`. A send it made and could not then record was unknown to the next check, which made it again: with a read-only or full state directory a session in error was re-prompted at every check and never held, and a supervisor killed between a send and that save repeated the send on restart.

**The rule.**

1. **Record before sending.** Every automatic send gets a numbered record in private `sends.json` before the adapter is asked to make it, with or without `loop.limits.max_sends`: a wake, nudge or re-prompt, a [turn retry](#recovering-a-failed-bb-turn-by-retry), a handoff or switch-back brief, a new conversation's first prompt, a child-error notice, a stop, and the one-off reports (the supervised thread waiting on a person, `degraded` and `recovered`, switch-back stopped, `hung_turn`). The record holds when, what and to which target, never the text. With `max_sends` set the same write counts the attempt against it; a stop or a report never counts. **If the record cannot be saved, nothing is sent**: the check records action `none` with `could not save the record of the send before making it, so nothing was sent`, exits 1 and names the cause. A stop is the one exception: it is made anyway, with a warning, because stopping again is harmless and not stopping when asked is worse.
2. **A record is settled only by a check that read it.** A check settles a record by recording its outcome: its own sends when it saves `state.json` at its end, and earlier checks' records when it has read and handled them (rule 3) and then saved. A check that does not read the records settles none of them, so they are still there for the next check that does: a held check (paused, awaiting a person, completed, disabled), the deadline's hold, a check that cannot read `sends.json`, and a dry run. Nothing is settled by time, and an older binary that rewrites `state.json` cannot make a settled record look unsettled again (see rolling back, below).
3. **An unsettled record is counted as made, unless it may have put the task on a second conversation.** The next check that reads it cannot tell whether the check that made it was killed before or after the send, or only failed to save. So:
   - **Sends into the conversation the loop is already on are counted and spaced**, as a send whose result is unknown: a re-prompt or turn retry spends `max_reprompts` and starts `errors.backoff`; a nudge spends `max_nudges`; each sets the time of the last send, which spaces the next nudge by `min_wake_interval` (an idle wake is not spaced, as before); a child-error notice counts as an attempt of its announcement. A one-off report is not sent again. If unconfirmed re-prompts are what reach the cap, the hold says `error persisted after re-prompts; N of them were recorded but could not be confirmed as sent`. The check warns `a <kind> to <target> was recorded at <time> but that check could not save what happened, so it may have been sent; it is counted as sent`.
   - **Sends that may have put the task on a second conversation hold for a person** instead: a handoff brief and a switch-back brief. The hold names every such brief and says what to do: `a handoff brief to <route> may have been delivered. Check that conversation: if it took the task, run keepgoing retarget <id> and then keepgoing resume, so the loop follows it; if not, run keepgoing resume, and the loop stays on <current route> and briefs no route on the next check`. The briefs are settled only once that hold is saved; if it cannot be saved, the check fails, settles nothing, and the next check finds them again. A new conversation's first prompt is settled by its own record, saved in `state.json` before the conversation is created: an outcome that is still unknown holds the same way, and a conversation found by its title is taken as created, with nothing sent again (see [hand off to a new conversation](fallbacks.md#hand-off-to-a-new-conversation)).
   - **A stop with such a brief unsettled, or requested while its hold is in force, stops every conversation that may have the task**: the loop's current target and each briefed one (a second stop is harmless; each is recorded first), once per stop request, then holds as above if it had not yet. Each of those stops follows the [session claim](#one-loop-per-session) rule of any stop: it waits only while another loop's live check holds that session (the next check makes it), goes ahead past a holder past its own time limit, and goes ahead without the claim when the claim directory cannot be determined or used. A briefed route that is no longer configured cannot be stopped by keepgoing; the check says so, and that conversation must be stopped by hand. With a stop requested, the hold points to `keepgoing resume --keep-stop`, which settles the brief and keeps the stop; a plain `keepgoing resume` would cancel it.
   - **A stop is never taken as made.** One recorded and then not sent must still be sent, so the next check that finds the stop requested sends it, once more at most; a second stop is harmless.
   - **A lane stop is looked at again.** A `stop:lane` record of a [stop that covers the lanes](#stopping-the-lanes-too) is not taken as made either: the next check reads the lane again, counts it as stopped if it is no longer running, and stops it if it is.
4. **An unreadable `sends.json` stops every send.** A check that is not held and cannot read it sends nothing and fails with `the send record sends.json cannot be read, so nothing is sent`; its `error` report is sent once, when this begins, not at every check. `status` prints a `send record:` line (`sendRecord` in JSON) and `doctor` a `supervisor.send_record` error. Restore `sends.json` from a copy. A copy older than the last check lacks the records made since, so those sends are not detected as interrupted and may be repeated; the count against `max_sends` goes back to the copy's. Deleting the file lets checks send again, but turns off the detection of interrupted sends for the records it held, which may then be repeated, and resets the count against `max_sends` to zero. Numbering continues from the settled point, so later records are still detected.

**Resume.** A `resume` of the hold for an unsettled brief settles it: `resume` prints which brief, and that the loop continues on its current route. A brief to another route counts as delivered and not taken, so that route is spaced like a rejected brief (by `errors.backoff`, and never capped by the resume, so with `max_reprompts: 1` it is not spaced) and a switch-back is spaced by `switch_back.retry_every`; no route is briefed on the next check. If the check that raised the hold was killed before it could save that it had settled the record, the resume still settles it: the next check takes the record as settled. To follow the brief instead, `keepgoing retarget <id>` first; `resume` then says the loop is on that route. A `resume` that starts a new error episode first settles the records no check has read yet, in the episode that is ending, so a re-prompt recorded and not confirmed does not count against the new episode; it stops at an unsettled handoff or switch-back brief, which the next check still holds for.

**Dry runs.** A dry run reads the records but changes nothing: it previews the hold or the count a real check would apply, and settles nothing.

**Rolling back to an older binary.** An older binary does not record a send before making it. It drops `sendsRecorded` from `state.json` when it saves, and it keeps `sends.json` as it is unless `max_sends` is set, in which case it rewrites it with only `version` and `used`, dropping the records, the numbering and the settled point. After upgrading again: if `sends.json` kept its `settled` value, records the older binary's checks could not have settled are judged by it; if the older binary rewrote the file, there are no records left and nothing is counted twice or held. While the older binary runs, an interrupted send is treated as before this change: it may be retried or a brief sent again, including a second brief to another fallback.

Covered by `TestUnwritableStateDirectorySendsNothing`, `TestSendWithoutARecordedOutcomeIsCountedByTheNextCheck`, `TestASendRecordedWithoutAnOutcomeAtEachKillPoint`, `TestBriefsAreRecordedWithoutASendLimit`, `TestARefusedSendIsReportedAsNoAction`, `TestUnreadableSendRecordIsReportedOnce`, the `internal/state` ledger tests, and in the scenario suite `TestScenarioUnwritableStateDirectory`, `TestScenarioNoRoomToWrite` and `TestFaultKilledCheck`.

## Loop deadline

Set `loop.limits.deadline` to a timestamp with a timezone, or pass `--deadline "2030-01-01T18:00:00Z"` to `init`. There is no default deadline. Setup previews it in text and JSON; `status` exposes `deadline` and `deadlineReached`. These status fields describe the configured cutoff and host-clock comparison, not proof that a supervisor has run or that an agent stopped. Status itself changes no controls.

Each ordinary tick compares its start time with the deadline. At equality or later, it records `await_user`, persists the reason in the existing control hold, and sends the subscribed awaiting-user report. This happens before automatic provider queries, yield, fingerprinting and all automatic probes/recovery. Repeated checks or supervisor restarts retain the hold and do not repeat that report. Child-outcome polling also skips providers after the cutoff and leaves hold persistence to the next ordinary tick. External schedulers retain their own cadence. Dry runs preview the decision and record diagnostic history without setting a hold, sending reports or calling providers.

An in-flight check may finish past the deadline, and an already-running or queued agent turn is not cancelled. This is a cutoff for future supervision checks, not a real-time execution timeout, total-turn cap or monetary budget. It relies on the host clock; clock changes can move an unreached cutoff. After a hold is persisted, a clock rollback or deadline edit does not clear it. Stop retains precedence and can still cancel a running turn through its adapter.

To continue, revise or remove the deadline under the task's existing authorization and explicitly `resume`. Resume alone with an expired deadline causes another hold on the next check. Enable, restart, retarget and ownership takeover do not extend the configured deadline. Existing disabled/pause/stop/completion/awaiting-user holds retain precedence. Manual operations, including `fallbacks check`, `retarget` activation and read-only `doctor` queries, remain explicit operations outside this automatic cutoff. Existing config-snapshot and ownership checks still apply.

Available in v0.1.3 or newer. Verification uses decision tables, CLI and supervisor fixtures; no live provider or service deadline was exercised.

## Upgrading and rolling back

**Before every upgrade, stop supervision and copy the loop's state directory.** That copy is the only supported way back. Stop the daemon, service or scheduler first, so nothing writes while you copy, and copy the whole directory named by `loop.state_dir`. The files that matter in it:

| File | Why it matters |
| --- | --- |
| `control.json` | the holds (paused, stop, awaiting a person, completed), their note, and who owns the loop |
| `state.json` | the active target, the re-prompt and nudge counts, the last send and the last check |
| `sends.json`, `progress.json` | the total send allowance used and the no-progress evidence, when those limits are on |
| `health.json` | fallback probe evidence |
| `targets/` | each target's saved session ID, the BB log cursor and headless turn files |
| `incidents.json`, `deliveries.json`, `runs.jsonl`, `graph.json` | history and run references; diagnostic, but an older build stops on the journal (below) |
| `goal.json` | the private goal record, when one was set |

The configuration (`keepgoing.yaml`, `fallbacks.yaml`, the prompt file) lives outside the state directory; keep a copy of those too if the upgrade changes them.

**Upgrading keeps the loop where it was.** A newer build reads the state directory of every released version, v0.1.0 to v0.1.5. A loop held for a person stays held with its note, the first check sends nothing and runs no agent command, the saved re-prompt count and last send time are kept, and after `resume` the loop carries on from the saved session without repeating a send. Records are upgraded in place the first time the new build writes them: an incident journal from v0.1.3 to v0.1.5 keeps its earlier records, and a state directory from before the journal or the run graph gets them from the first check and control command on. This is fixture evidence, from each release's own binary and the scenario suite (see [testing](testing.md#scenario-suite-t2)); no live loop was upgraded for it.

**Rolling back by restoring only the older binary is not supported.** Once a newer build has written to the state directory, an older build does not read it and does not fail safely. What v0.1.5 does with a state directory today's source has written to:

| Command | What happens | Exit |
| --- | --- | --- |
| `tick` | The check still observes and acts (it sent a re-prompt), then prints `tick: incident history unavailable; check private state storage`. Its line carries the warning `incident history write failed; diagnostic evidence is incomplete`. | 1, on every check |
| `resume`, `pause` and the other control commands | The control change is saved, with `warning: control saved; incident history write failed; diagnostic evidence is incomplete`. | 1 |
| `status` | Works, from `state.json` and `control.json`. | 0 |
| `timeline` | `source incidents.json: unavailable; schema 0; retained 0; dropped 0`. | 1 |

So:

- A scheduler that disables a job after a few failing exits stops calling the older build, although every one of those checks ran and may have sent.
- The older build rewrites `state.json` without the fields it does not know. What the newer build saved there is lost: the count of failed checks, the last turn retry, the child-error episode and the like.
- Nothing is recorded in the journal while the older build runs.
- An older build refuses a configuration that names something newer than itself, before doing anything: v0.1.2 answers `loop.report.events: unknown event "complete"` and exits 2.

The run graph (v0.2.0) differs from the journal. A build that meets a graph holding a record kind it does not know carries on: the check does the same work, exits 0, and has the warning `run reference record unavailable; discovery evidence is incomplete`. But `keepgoing runs` exits 1 and shows `graph: corrupt`, with nothing read from it. The build cannot tell a record kind it does not know from damage, so after a rollback "corrupt" may only mean "written by a newer build". Neither file is rewritten or reset by the older build.

**To go back:** stop supervision, restore the loop's state directory from the copy taken before the upgrade, then restore the older binary, and start supervision again. Work the newer build did after the copy is not in it: sends it made are not counted, and holds set since then have to be set again. Without a copy there is no supported way back: the older build can only be started on a new, empty state directory, which starts the loop's counters and history again.

## Yielding to other work

```yaml
yield:
  busy_command: ["./busy-check.sh"]
```

When the command exits 0, the tick does nothing and exits 75. Any other exit means the loop may run. A command that cannot run is a warning, and the tick goes ahead. This lets heavy scheduled jobs on the same machine take priority.

## Webhook reports

```yaml
report:
  secret_file: ~/.config/agent-loops/example.env
  events: [handoff, degraded, recovered, await_user, stop, error]
```

The URL and secret come from `LOOPTENDER_WEBHOOK_URL` and `LOOPTENDER_WEBHOOK_SECRET`, each also read under its [earlier name](configuration.md#environment-variables) (`KEEPGOING_WEBHOOK_URL`, `KEEPGOING_WEBHOOK_SECRET`). Rename them with `url_env` and `secret_env`. Values are read from the environment first, then from `secret_file`, a `KEY=value` file. Secrets never appear in logs, errors, or reports. The URL must use https. Plain http is allowed only for localhost.

- **`scheme: standard-webhooks`** is the default. It signs each body with HMAC-SHA256 and sends `webhook-id`, `webhook-timestamp`, and `webhook-signature`. The secret is base64, optionally prefixed `whsec_`.
- **`scheme: bearer`** sends the secret as a bearer token instead.
- **`format: standard`** is the default. It sends `{"type": "keepgoing.<event>", "timestamp": ..., "data": {...}}`.
- **`format: text`** sends `{"source", "sent_at", "text"}` for receivers that expect a plain message.

A failed delivery is retried once on a network error or a 5xx response. A report that cannot be delivered is a warning on the tick, never a failure. Check delivery with:

```sh
keepgoing report test --dry-run   # print the body
keepgoing report test             # deliver it
```

Events: `wake`, `nudge`, `reprompt`, `handoff`, `switch_back`, `degraded`, `recovered`, `await_user`, `limit_wait` (v0.2.0), `network_wait` (v0.2.0), `child_error` (v0.2.0), `check_gap` (v0.2.0), `hung_turn` (v0.2.0), `complete` (v0.1.3+), `stop`, `error`, `probe_failed`, `test`, or `all`. `complete`, and in v0.2.0 `limit_wait`, `network_wait` and `child_error`, are included in the default event list on `main`; an explicit event list must include them or `all`. `check_gap` and `hung_turn` are not: name them, or `all`, to receive them. `complete`, `limit_wait`, `network_wait`, `child_error`, `check_gap` and `hung_turn` make a single attempt without following redirects. Other events retain their existing one-retry policy. `keepgoing report test` sends a `test` event, whatever events are subscribed.

## Situations that need a person

- **The agent is waiting on a person.** A pending interaction is reported once as `await_user`, and nothing is sent until it is answered. `keepgoing await-user --note` reports at once and holds the loop until `keepgoing resume`.
- **The session stays stalled.** After `progress.max_nudges` nudges without visible progress, the loop is marked awaiting user and reports `await_user`.
- **The turn was restricted, or refused again and again.** A provider that denied permission holds the loop at once with its own note, one `await_user` report and a question; a `resume` asks for exactly one more try. A refused turn is continued in the same session with growing spacing, and holds with a question only after `refusal.ask_after` refusals in a row. Neither is handed off. See [a refused or restricted turn](#a-refused-or-restricted-turn).
- **The target is gone.** An archived, deleted, or missing target marks the loop awaiting user and reports `await_user`.
- **A headless turn was stopped.** Stopping a headless turn ends its process without an exit code, so it reads as an `unknown` error. After `keepgoing resume`, it is re-prompted under the ordinary error rules.
- **Only `resume` clears a stop.** `enable` does not.

### A refused or restricted turn

Unreleased; **fixture-tested only**. Two error classes mean that someone decided against the request, which is different from a limit or a fault:

- `restricted`: the provider denied permission for the request or the account. Signals: HTTP 403, the codes `permission_denied`, `permission_error`, `forbidden` and `oauth_org_not_allowed`.
- `refused`: the model or the provider declined the turn itself. Signals: a headless Claude Code result whose `stop_reason` is `refusal`, BB's error category `policy`, and Codex's `cyberPolicy` and `misalignmentPolicyViolation` codes.

When an error carries several structured fields, one of these in any field wins over every other class. The [capability matrix](adapters.md#refusals-continue-restrictions-hold) says what each adapter can and cannot detect. A refusal that no structured field reports is still `unknown`, or looks like a finished turn.

Neither class ever moves the work. keepgoing does not hand off, switch model, account or conversation, or retry the turn by reference, whatever `errors.failover_on` lists, and neither class can be listed there. If the connectivity check is failing, it waits for the network first, as for every session in error.

#### A refused turn is continued

**What changed, and why.** The first version of this change, never released, held the loop at the first refusal. Refusals turn out to be false flags often: a continue in the same session usually clears them. Holding at once would stop the loop many times for nothing. So a refused turn is now continued, and a gauge shows how often refusals happen and how often a continue cleared them, so you can see whether the loop is being declined for a real reason.

What keepgoing does:

- **A plain continue, in the same session.** It sends the loop's ordinary continue prompt to the same session, and never a different prompt. The check is recorded with the note `the model or provider declined this turn; continuing in the same session` (cause `refused_continue`), and the send is recorded before it is made, like every send.
- **Spacing that grows with the streak.** The first continue goes 1 minute after the refused turn was seen, then 2 minutes, then 5 minutes, then every 10 minutes for as long as the turns keep being refused. A check that is too early records `the model or provider declined this turn; waiting before continuing` (cause `refused_wait`) and sends nothing.
- **No per-episode cap.** The continues do not spend `errors.max_reprompts` or its backoff. The loop-wide limits still apply: every continue counts against `loop.limits.max_sends`, and `deadline` and `no_progress_timeout` still end the loop. `pause` and `stop` win over a continue, as over everything else.
- **A streak report.** When the streak reaches 3, and again at 10 and every 10 after, keepgoing sends one `refusal_streak` report, in the default `report.events`. It is a report only: it says how many turns in a row were declined, how many were declined and how many recovered in the last 24 hours, that false flags are common, and that `keepgoing pause` or `keepgoing stop` stops the continues.
- **A question after a long streak.** At `refusal.ask_after` refusals in a row with no turn that recovered (default 10; `0` never asks), keepgoing stops continuing and raises a question for a person, below. It holds only this loop, with one `await_user` report.

**The gauge.** Each loop keeps, in `state.json`: how many turns were refused; how many of those were recovered by a continue, meaning the next turn ended without a refusal; the current streak; the longest streak; and the time of the last refusal. A refused turn is counted once, however many checks see it. `status` prints a line such as `refusals: 7 in the last 24h, 6 recovered by continue; current streak 1`, `status --json` carries it as `refusals`, the panel shows it as **Refusals**, and `timeline --kind refusal` shows each refusal and each recovery. All of it is counts and times; nothing the session said is kept.

#### A restricted turn holds

A restriction is not a false flag: the provider has said the account or request may not go ahead, and a continue would only ask again. keepgoing holds the loop for a person on that check, with the note `provider denied permission for this request or account; not a limit, so no handoff`, one `await_user` report and a question of kind `restricted`.

The way out is a person's decision:

1. Read why. The provider's own message is in the session, not in keepgoing's records.
2. Fix the cause where you can: the account's access or plan.
3. Run `resume`. A resume of a loop held for this reason is your request for one more try: the next check sends exactly one re-prompt to the same session, outside `errors.max_reprompts` and its backoff. The loop-wide limits still apply and that send counts against `max_sends`. The one try belongs to the target that was held and to the turn that was declined: a check that sees that turn and does not use the try spends it, and a move to another target drops it.
4. If that turn is restricted again, the loop holds again and reports again. keepgoing never tries twice for one resume.

Starting a turn in the session by hand also works: once the target no longer shows the restricted turn, the loop continues after `resume` with nothing extra sent. `retarget` to a different fallback is a move you make yourself; keepgoing does not make it.

When the loop is on a fallback and the primary's switch-back probe is refused or restricted, switch-back stops after that one probe, with one `switch_back` report, until `resume`, `retarget` or the next handoff. It is not probed again every `retry_every`.

#### The question

A question is the loop's record that it needs a person's decision. It is saved in `control.json` as `question` (version 1), one per loop at most, and holds only that loop. It stores no words: an ID (`q_` and 32 hex digits), a fixed `kind`, when it was raised and by which build, what it holds (`loop`), a `basis` (a SHA-256 over the kind, the evidence and the control fields it depends on, including the target and the stop and pause flags), the `evidence` as typed facts, the `options` in order, and who may answer (`person`; a thread or an automatic answer is never allowed for these kinds). The panel renders the words.

| Kind | Raised | Evidence | Options, in order |
| --- | --- | --- | --- |
| `refused` | at `refusal.ask_after` refusals in a row | `declined_turns`, `first_at`, `last_at`, `route`, `error_class`, `current_streak`, `recovered_by_continue_24h` | `continue` (primary: clears the streak and goes back to continuing with spacing), `fresh_session` (needs review; sends), `pause` |
| `restricted` | at once | `route`, `error_class`, `last_at` | `resume` (one re-prompt once access is fixed; needs review), `pause`, `stop` |

`status` prints a `question:` line while one is open. The incident journal records `question_raised` and `question_withdrawn` control records, by ID only; `question_answered` is kept for the answer commands. A new question replaces an open one, which is recorded as withdrawn. A question whose situation has cleared, because the loop is running again, is withdrawn. Answering from the panel or with `client review|apply answer` is not built yet. Until it is, `keepgoing resume` withdraws the question and goes on: for `refused` the streak starts over and continuing starts again at 1 minute, and for `restricted` it is the one more try above.

### A long limit wait with no way out

Released in v0.2.0; **offline fixtures only**. A provider limit with a reported reset is waited out without prompts when no handoff can happen: failover is off for that error class, or no fallback is confirmed. That wait can last days. When the reported reset is further away than `errors.report_wait_after` (default `6h`), keepgoing sends one `limit_wait` report for that wait, saying which target is waiting, when the limit resets and why no handoff is possible.

- **It does not hold the loop or change a decision.** Checks keep observing. If the limit lifts early, the next check acts exactly as it would have without the report. Nothing needs to be resumed.
- **The check at the reset.** A check that waits on a provider limit records the limit's structured reset (`limitResetsAt` in `state.json`). Under the daemon or a service, when that reset comes before the end of `daemon.interval`, the next check runs at the reset itself, with no margin guessed, instead of at the end of the interval. A reset further away is reached by the ordinary checks. Under an external scheduler nothing changes. Noticing a limit that was lifted before its reset would need a real request to the provider before then, which spends one; that is the owner's decision and is not done.
- **One report per wait.** The wait is recorded in `state.json`, so repeated checks and a restarted supervisor stay quiet. The wait ends only on positive evidence: the loop moved to another target, the session is idle or working without a provider retry, or it is in error with no reset still ahead. A check that merely decided something else (outside the time window, queued messages, a pending interaction, child work, a provider retry, an unknown or pending state) does not end it, so a loop with a daily window reports a multi-day wait once. After the wait has ended, a later long wait is reported again.
- **A reset that moves later.** Within one wait, a second report is sent only if the reported reset moves more than one hour later than the reset last reported, and a third only if it then moves more than two hours later again. Three is the most any single wait sends, so a provider whose reset keeps sliding cannot produce a stream. A reset that moves earlier is never re-reported.
- **At most once, never retried.** The wait is saved before the request is made, the same order as holds and completions. A report makes a single request without following redirects. If the supervisor is killed mid-request, or the request fails, that report is lost: it is not sent again by later checks, held or not, and a failure stays visible in `status` and the notification records. If `state.json` cannot be written, nothing is sent.
- **Subscription.** `limit_wait` is in the default `report.events` because, like `await_user`, it says a person may be needed. An explicit `report.events` list receives it only if it names `limit_wait` or `all`: existing explicit lists are unchanged and get nothing new. With no subscription the wait is still recorded and shown, marked as not sent; subscribing during the wait sends its one report on the next check.
- **Holds win.** A paused, disabled, completed, awaiting-user or stopped loop does not observe its target, so it neither sends this report nor forgets one already recorded. Dry runs send and record nothing.
- **Turning it off.** There is no off value: `report_wait_after: 0` means the default. To receive nothing, give `report.events` an explicit list without `limit_wait`. The wait is then still recorded and shown as not sent.
- **When it does not apply.** No report is sent when a handoff is possible. That includes a long wait you chose with a large `wait_if_reset_within` while a fallback is confirmed. The same setting with no confirmed fallback leaves no way out and is reported. With no reported reset time the supervisor does not wait at all: it re-prompts within `errors.max_reprompts` and then holds for a person, which reports `await_user`. So a limit without a reset time is never waited out silently.
- **Where it shows.** `status` prints the recorded wait, its reset time and whether the report was requested, failed or not subscribed (`limitWait` in JSON). `timeline --kind limit_wait_report` shows the check that detected it, and the delivery appears as a `limit_wait` notification.

- **Older builds.** Once a `limit_wait` delivery or a marked check is recorded, v0.1.5 and earlier refuse `deliveries.json` (unknown event label) and `incidents.json` (newer schema) rather than rewrite them. Do not run an older build against the same state directory.

The payload carries the loop name, the target alias, the reset time, the reason the threshold and the report's number within the wait. It carries no task text, transcript or thread ID. This is the same content class as the existing `handoff` report.

## ci-wait

```sh
keepgoing ci-wait --repo example-org/example-app --pr 42
keepgoing ci-wait --repo example-org/example-app --sha <40-char sha> --branch cb/example --json
```

This waits until the newest run of every workflow on the exact commit has finished. It looks at the 50 most recent runs on the branch, and it pins the pull request's head commit when it starts. A failed run makes it exit 1. When a run is replaced, for example cancelled by a pull request edit, the newer run of the same workflow is followed. Then it prints each run's jobs. It uses the `gh` CLI, so authentication stays with `gh`. Every `gh` call goes through the network retry below.

## Network outages

Released in v0.2.0; **fixture-tested only**. A re-prompt, a handoff brief or a fallback probe sent while the network is down fails and still spends its allowance. In one observed outage two of three allowed re-prompts went into a dead network; a third failure would have ended in a hold with the network back minutes later. keepgoing now checks connectivity first.

**What keepgoing sends, by default.** One HTTP `GET https://api.github.com/zen`, with Go's standard `User-Agent` and no loop name, host name, thread ID, token or other identifier. keepgoing contacted no host by itself before this change. It is sent only when one of the following is about to happen, at most once per check, and never in a dry run:

- an error **re-prompt**, a **handoff**, or an **awaiting-user hold for a session in error** (a spent re-prompt cap, an auth error, or a [refused or restricted turn](#a-refused-or-restricted-turn)). While the check fails, that hold is not raised either: the loop waits for connectivity and holds on the first check after it returns;
- a **stall nudge**, or an **awaiting-user hold for a stalled session** (`no progress after N nudges`, or a provider retry that went silent);
- any check of an **active session while the last check found the network down**, so the outage is not forgotten and the stall clock stays paused;
- the first **scheduled fallback probe** that is due;
- the exact probe of a **switch-back**;
- a **`no_progress_timeout` hold** that is about to be raised, so that time offline can be credited first;
- a **`limit_wait` or `child_error` report** that is about to be sent.

Idle wakes, stop, pause and the other holds do not trigger it. To change it, set `loop.network`: `url` for another address, `command` for an argv whose exit 0 means online, or `check: "off"` for no check at all. With neither `url` nor `command`, the `net-retry` variables apply first: `LOOPTENDER_NET_PROBE`, a command line run by the platform's shell (`/bin/sh -c`, or `cmd /C` on Windows), or `LOOPTENDER_NET_PROBE_URL`. Both are also read under their [earlier name](configuration.md#environment-variables)s. Only `network.command` is run without a shell. Any HTTP response other than a redirect or a `511` means online (see captive portals below); a transport error means offline. No response body, error text or provider output is read. The check has `network.timeout` (8s), reserved inside the [check's hard limit](#check-time-budget).

**While it fails.**

- An errored session is not re-prompted, not handed off and not held. The check records action `none` with the reason `network down; waiting for connectivity` (incident stage and cause `network_down`), outcome `succeeded`, exit 0. The re-prompt count, the backoff clock, the handoff-brief counts and the send allowance are untouched. A hold that has nothing to do with the session's error (a child waiting on a person, a loop deadline, the send limit, a missing target) is raised as usual.
- Due scheduled probes and a due switch-back probe are not run. They appear in the check's `probes` with `"skipped":"network_down"`, are not recorded as failures, do not count against the daily cap, and stay due.
- An active session that looks stalled is not nudged and not held. A turn whose host slept in the middle of a request never fails: BB keeps showing it as active with no Git change, which is exactly what a stall looks like. The nudge count is untouched, and the stall clock and the silent-retry clock start again when the network is seen back, so the turn then has a full `stall_after` before its first nudge.
- A check that has already found the network down, because a probe was due, does not go on to send an idle wake or a switch-back brief either. A check that had no reason to test the network still sends them.
- The tick line has `"network":"down"`, a warning names `loop.network`, and `status` prints `network: down at the last connectivity check, failing since <time>`.

**When it returns.** The first check whose connectivity check passes acts as usual: it recovers the session if it is still in error (subject to `errors.backoff` from any earlier attempt) and runs the probes that were left due. Nothing is retried faster than the ordinary check interval.

For a BB thread, a recovery after an outage is therefore one [turn retry](#recovering-a-failed-bb-turn-by-retry), with no new prompt, plus one notice-only message when direct children are still in error: a retry has no text to carry the [child-error notice](#children-in-error), so the count is sent on its own. The notice never contains the task, is sent once per newly failed child, and is one more send against the allowance. With no child in error the retry is the only thing the session receives. Other adapters receive one re-prompt, which carries the notice itself. With [lane recovery](#lane-recovery) switched on, the children that were working when the network dropped are retried on that same check or the next ones, and a child keepgoing is recovering is not announced, so the session receives the turn retry alone.

**A long outage, and a check that is wrong.** Two cases look the same from the check: a real outage, which may last weeks, and a check target that this machine cannot reach while the provider works (a DNS filter or blocked host, a scheduler environment without its proxy settings, a proxy that refuses the connection, a TLS-inspecting gateway whose certificate is not trusted). The first must be waited out; the second must not hold a loop in silence. So after `network.verify_after` (default `1h`) of failed checks keepgoing looks more closely: it asks the provider directly, with the one exact probe a switch-back would use for the current target. It looks again after twice as long each time (2h, 4h, 8h and so on, up to a week), so a three-week outage costs about nine probes.

- **Positive evidence that the provider was reached** sets the check aside for this outage: the tick line has `"network":"down_untrusted"`, a warning and `status` say so, and the ordinary error rules apply again. The check is believed again once it has itself passed, or once the session has been seen active or idle, which ends the episode: a later outage is judged afresh, so a target that is still blocked costs one `verify_after` per error episode. What counts, by probe result:

  | Probe result | Evidence of connectivity? | Why |
  | --- | --- | --- |
  | passes | yes | The provider answered the request. |
  | `rate_limit` | yes | A limit is the provider's own answer to a request that reached it; no CLI reports one without a response. |
  | `overloaded` | yes | As for a rate limit: the provider answered, with a refusal. |
  | `restricted`, `refused` | yes | A permission or policy decision is the provider's answer to a request that reached it. Counting it keeps a restriction from being mistaken for an outage. |
  | `auth` | no | A CLI can find its stored login expired or missing without making a request, so this says nothing about the network. Treating it as an answer would re-prompt into a dead network. |
  | `network`, `unknown`, a timeout | no | Nothing shows the provider was reached. |

  An expired login with a working network is not held up by this rule: the connectivity check passes then, so the gate is not involved and the `auth error` hold and its report are reached as usual. Only an expired login together with a check target this machine cannot reach keeps waiting, and the `network_wait` report says what to do.
- **No such evidence.** It is treated as a real outage. Nothing is spent and no hold is raised, however long it lasts: the fixture runs three weeks. A `network_wait` report is attempted at each look until one is accepted; in a real outage it usually cannot be delivered, and nothing depends on it.
- **No probe is configured for the target** (`loop.probe`, set by default for the `claude-code` and `codex` providers). keepgoing cannot tell the two cases apart and keeps waiting. The report says so, and it is repeated at every look (1h, 3h, 7h, 15h after the outage began, and so on), so a loop held up by a blocked check target does not go silent.

The probe is the only thing sent during an outage, and it is a real request when the network in fact works. Into a dead network it fails without reaching the provider. `keepgoing doctor` runs the connectivity check once and reports it as `network.check`, so an unreachable target is found before it matters; `doctor --offline` does not run it.

**What counts as online, and captive portals.** Online means the target answered the request itself: a response that is not a redirect and not `511 Network Authentication Required`. Any other status counts, because a server that answers shows the network works. A network that needs a sign-in answers requests itself, with a redirect to its sign-in page (on another host or on the target's own name), a `511`, or, for `https`, a certificate this machine does not trust; all of these read as offline. keepgoing does not follow redirects, so a `network.url` must answer directly: `doctor` names a redirect or a `511` when that is what the target returned. The `net-retry` command uses the same rule for `LOOPTENDER_NET_PROBE_URL`: a target that redirects now reads as offline there too. A portal that answers a plain `http` request in place, with its own page and an ordinary status, cannot be told from the target; use `https`.

**Recorded outage and status.** The `network:` line reflects the last connectivity check. It is cleared when a check passes, and also when a later check needs no connectivity check and finds the session active or idle, since nothing is waiting for the network then. The check that finds the network back has `"network":"restored"` and `networkDownFor` in its tick line and a `network back` warning with the duration, which `runs.jsonl` keeps. The outage starts at the first check that found it, not at the moment the network dropped. `timeline` shows the waiting checks as one retained entry with its first and last time and a count, whatever its length; it does not tell a portal from no network.

**Reports that make one attempt.** `limit_wait` and `child_error` reports are not attempted while the connectivity check is failing, because a failed attempt is not repeated. They are sent by the first check after it passes.

**Limits.**

- The check says the network is reachable, not that the provider is. A provider outage with a working network is still re-prompted into, as before.
- With `tick_timeout` at its minimum there is no room for the check in the time accounting. It is then not made, and `validate`, `status` and `doctor` say so; raise `tick_timeout` to `2m48s` or more to have it.
- `doctor` tests the target from the environment `doctor` runs in, which may differ from a scheduler's.
- **When recovery starts.** Recovery starts at the first check after connectivity returns. Under the daemon or a [service](services.md), that is within one minute of the network coming back: while the last check found the network down, the daemon makes the same connectivity check, at most once a minute (a fixed bound, and never more often than `daemon.control_poll`), and starts the next check as soon as it passes. That connectivity check is made under the tick lock, so it never runs beside a check; nothing is sent from it, and the check that follows decides everything. While it runs, the daemon holds the tick lock for up to the network check timeout, so a manual `keepgoing tick` at that moment is turned away (exit 75) and should simply be run again. Under an external scheduler, such as a BB automation, it is still up to one scheduler interval after a portal is cleared: nothing runs between its checks.

### A turn that hung through an outage

Released in v0.2.0; **fixture-tested only**; BB threads only. A host that sleeps in the middle of a model request leaves the turn active and silent for good: BB still shows it running, it never fails, and nothing ends it. Before, the stall rule queued three nudges behind it, which would all arrive later if the turn ever resumed, and then held with `no progress after 3 nudges`, which did not say what happened.

keepgoing now watches an active turn through an outage. It applies only to loops that track Git progress (`progress.repositories`), and only inside the loop's operating window: without tracking the stall rule never nudges or holds an active turn, and neither does this. It treats the turn as possibly hung while all of these hold:

1. An outage happened while this turn was active: a connectivity check found the network down, or this is the first check after a gap that the [missed-time rule](#time-in-which-no-check-ran) judges missed (the computer slept or the scheduler was down; more than three usual intervals, once the loop has shown three gaps).
2. It is still the same turn (BB's latest `turn/started` in that thread).
3. It has logged nothing since the outage began: since the failed check, or, after a gap, since the computer woke, taken as one usual interval before the first check after the gap. So a last log after the last check before the gap counts, as when a lid is closed a minute after it. A turn that has logged since is not watched. It has also logged nothing for `stall_after`, and the stall clock has reached `stall_after`.
4. It is waiting on the model, not on a tool: every tool item it started (`commandExecution`, `fileRead`, `fileChange`, `toolCall`, `backgroundTask`, `webSearch`, `mcpToolCall`) has completed. An item without an ID or type, an item type keepgoing does not know, or more than 64 open items, makes the bookkeeping uncertain, and the turn is then treated as slow, not hung. Items the model itself produces (`reasoning`, `agentMessage`, `userMessage`) do not count: an open one is where a hung request stops.
5. Nothing else explains the silence: nothing queued, no background agents, no child running or unverified, no person asked, no provider retry, no Git change.

**What it changes: the nudges are held back.** The stall rule decides exactly as it would without the watch. On every check where it would nudge, the nudge is *held back*: it is recorded as a nudge is (the nudge count goes up, the time of the last wake is set, and connectivity is checked first, exactly as before a nudge), and it is not sent (`nudge held back, not sent: …`). On the other checks the loop records `turn silent since before an outage or the computer sleeping; it may be hung; keepgoing has not stopped it`. Since the nudges are counted, the stall rule's own hold after `max_nudges` nudges comes at the same check as it would have. It carries the stall rule's reason, with how many nudges were held back and why (`no progress after 3 nudges (3 held back, not sent, because the turn looked hung); the turn has been silent since before an outage or the computer sleeping; …`), and the two ways out: `keepgoing stop` then `keepgoing resume`, or retry the turn in BB. At the defaults, with the network back and no nudge sent before, that is 3h30m later: nudges held back at 30m, 1h30m and 2h30m, the hold at 3h30m.

**Telling a held-back nudge from a sent one.**
- `status` prints `last sent:` from the last time something was actually sent (`lastSentAt` in `state.json`). It adds `last nudge held back: <time> (the turn looked hung; 2 of 3 nudges held back, not sent)` while any are counted. A held-back nudge still sets the time of the last wake (`lastWakeAt`), which keeps the stall rule's spacing.
- The timeline gives the checks their own causes: `nudge_held` for a held-back nudge, `hung_wait` for a check that waits on the turn, and `stall_limit_held` for the stall rule's hold after nudges that were held back.
- The panel's hold says `No progress after 3 nudges, all held back because the turn looked hung.`, or how many of them were.
- The count of held-back nudges (`heldNudges`) is kept with the nudge count. So if the turn logs again and is handed back, the stall rule's hold still says how many of its nudges were held back.

When the wait begins, one `hung_turn` report says when a person will be asked, at about the time the stall rule would hold if every check came on time, or that no time is set if that is more than a year away. It is recorded in `sends.json` before it is sent, like every [one-off report](#a-send-recorded-before-it-is-made), and makes a single attempt. `hung_turn` is **not** in the default event list: a loop receives it only by naming it, or `all`, in `report.events`.

The watch ends when the turn ends (an ordinary wake, or recovery of a failed turn) or Git changes. A watched turn that logs anything again is handed back to the stall rule completely. While something else explains the silence (a tool, a queued message, a child), the stall rule's decisions are its own. Held-back nudges stay counted in each case, as sent ones would have been. A check that cannot read the turn's log decides nothing and keeps the watch as it was. A held-back nudge is not a send: it does not count toward `loop.limits.max_sends` or the no-progress flag's count of messages sent. Unspent sends stay available for later.
- **Where the stall rule alone reaches `max_sends` first.** By spending sends on those nudges, the stall rule alone can reach the `max_sends` hold before the hold after its nudges. The watch does not; it holds at the nudge hold instead.
- **Examples,** at the defaults with a 15-minute-to-2-hour outage: with `max_sends: 1` the stall rule alone holds at 2h40m and the watch at 5h30m; with `max_sends: 2`, 3h40m and 5h30m.
- **The general bound.** The difference is about (`max_nudges` − sends left + 1) × `min_wake_interval`, less the check interval.
- **Why.** A limit on sends is not what should hold a turn nothing is being sent to.

The no-progress flag is likewise raised later, or not at all, for the same reason. `keepgoing resume` alone, without `stop` or a retry in BB, leaves the same turn hung and silent, and the stall rule holds again when it next would.

A check killed after it held a nudge back, before `state.json` was saved, has not recorded it. The next check holds the same nudge back again, so the stall rule's hold comes one check later than it would have (5h40m instead of 5h30m with checks every 10 minutes). Held-back nudges are not recorded in `sends.json` first, as sends are: nothing is sent, so a repeat sends nothing either.

**Compared with the stall rule alone.** Because the watch only turns the stall rule's nudges into held-back ones, its hold is the stall rule's hold, and it checks connectivity only where the stall rule would. The tests show it by running each journey twice, with the watch on and off. They assert:
- the same action at every check, except a held-back nudge where the stall rule sends a nudge;
- the same hold, at the same check;
- the same connectivity checks, provider probes and `network_wait` reports;
- the same sends, less the held-back nudges, with nothing sent on a check that holds one back.

The journeys (`TestHungTurnActsAsTheStallRuleExceptForTheNudges` and the tests named below):
- an outage, the network back, then a second outage;
- an outage, then one failed check later;
- a lid close, then a second sleep;
- checks every 25 minutes with one failed check, with and without fallbacks to probe;
- checks every 9m59s with one failed check;
- a tool opening, or a message queued, 2 hours after the network is back;
- a parent waiting on a child for 6 hours, and through a 2-hour outage;
- a long tool through an outage; a silent turn 24 hours offline;
- the scheduler down with the turn logging;
- a lid close a minute after the last log, and one earlier;
- a nudge behind one turn starting another that hangs;
- a turn that logs once during the wait; a turn that logs every 29 minutes.

Stop, pause, the other holds and the loop-wide limits come first, as for every rule; nothing is evaluated while the network is known to be down. Covered by:
- `TestHungTurnIsWaitedOnThenHeldAtAnyOutageLength`, `TestHungTurnWaitEndsWhenTheTurnResumesOrFails` (20 minutes, 4 hours, 3 days and 3 weeks), `TestHungTurnNeedsEverySign`;
- `TestHungTurnActsAsTheStallRuleExceptForTheNudges`, `TestHungTurnNeverChecksConnectivityMoreThanTheStallRule`, `TestHungTurnLeavesATurnThatKeptLoggingToTheStallRule`, `TestHungTurnAfterASleepWithNoFailedCheck`, `TestHungTurnPatienceCountsNudgesAlreadySent`, `TestHungTurnThatLogsAgainIsHandedBack`, `TestHungTurnIsSilentOnlyAfterStallAfterWithoutALog`, `TestHungTurnDoesNothingOutsideTheWindow`;

#### Upgrading and going back

- **Older binaries reject `hung_turn`.** v0.1.5 and earlier, and `main` before this change, refuse a configuration whose `report.events` names `hung_turn` (exit 2, unknown event). Remove it from `report.events` before running an older binary.
- **Older binaries cannot read the delivery record.** Once a `hung_turn` report has been recorded in `deliveries.json`, an older binary cannot load that file, because of the unknown event label (as for `limit_wait` and `child_error`). The consequences:
  - `status`, `timeline` and `doctor` show the delivery history as unavailable;
  - reports are still delivered, but each returns an error;
  - the history stays frozen;
  - `network_wait` is reported again at every verification look while deliveries error;
  - the session-claim `degraded`, `recovered` and stuck reports, which go by that history, count as undelivered and repeat, up to three times each.
  To recover, move `deliveries.json` aside (the older binary starts a new one), or upgrade again.
- **Older binaries count the report record as a send.** An older binary that finds an unsettled `report:hung_turn` record in `sends.json` (one whose check could not save its outcome) counts it as a send to the agent. It warns, and sets the time of the last wake, which delays its next nudge by up to `min_wake_interval`.
- **Older binaries drop the watch.** They do not know `hungTurn`, `heldNudges`, `lastHeldNudgeAt` and `lastSentAt` in `state.json`, or `turnStartSeq`, `openTools` and `toolsUncertain` in `bb-cursor.json`, and drop them the next time they rewrite those files. An older binary run during a wait sends the nudges still due from then on, by the nudge count it finds, which includes the held-back ones. After going forward again, the watch for that turn does not resume, because the outage and the turn's start are no longer on record. The nudge count, held-back nudges included, carries over, so the hold comes when it would have.
- **Before going back:**
  - remove `hung_turn` from `report.events`;
  - check `keepgoing status`: if the reason says the turn has been silent since before an outage, settle the turn first (retry it in BB, or `keepgoing stop` then `keepgoing resume`), or pause the loop until you have;
  - if a `hung_turn` report was ever recorded, move `deliveries.json` aside, or expect the delivery errors above.
  Going forward again needs no step.

### A long time offline

Released in v0.2.0; **fixture-tested only**. `TestOfflineWithAHungTurnForAnyLength` runs the same outage with a turn that never fails and stays active throughout: it is not nudged or held at any length, and gets a full `stall_after` once the network is back. `TestOfflineForAnyLengthThenRecoversOnce` runs one scenario at 20 minutes, 4 hours, 3 days and 3 weeks offline: a turn with two working children fails as the network drops, checks run only now and then with a long stretch of none, the machine wakes behind a captive portal, and the portal is cleared. At every length nothing is sent while offline or behind the portal, no hold is raised, and the first check after connectivity returns takes exactly one recovery action: the failed turn is retried once, with no new prompt, and one notice-only message tells the parent that two children are in error.

What each time-driven or counted mechanism does across such a gap:

| Mechanism | Across a long gap | Right? |
| --- | --- | --- |
| Retry-notice expiry (`bb.retry_signal_ttl`) | The notice is dead after 15 minutes and is not waited on again. | yes |
| `errors.backoff` | Has long passed; the first re-prompt after the outage is not delayed by it. | yes |
| `stall_after`, `min_wake_interval`, nudge count | Apply only to an active session, and wait for connectivity like a re-prompt. The stall clock restarts when the session is seen active again after an error or after a connectivity check found the network down, and is paused for [time in which no check ran](#time-in-which-no-check-ran), so a turn that works again after a long outage is not nudged for the time it could not work. Before, it was nudged at once (`no progress for 72h`). The nudge count restarts whenever the session is seen not active. | changed here |
| Re-prompt count | Kept across the gap: attempts made before it still count, and nothing is spent or held during it. If the cap was already spent before the outage, the hold is raised by the first check that finds the network up. | yes; see follow-ups |
| Handoff-deferral and rejected-brief counts | Kept until the error episode ends. Their backoff has long passed. | yes |
| Probe `every`, `ttl`, daily cap | No probe is run or recorded while offline. After a gap longer than `ttl` every fallback's result has expired: the first check back runs the due probes (as many as fit its time), `degraded` may be reported once, and a handoff is refused until enough have passed again. The daily cap is per calendar day. | acceptable; a handoff can lag by a check or two |
| Limit-wait episode and its report | A reset that passed while offline ends the wait; the session is then handled as an ordinary error. The report is not attempted while offline. | yes |
| Child-error episode, its report and the notice | Children that failed stay failed. The report waits for connectivity and is sent once; the parent is told on its first re-prompt or wake, or after a BB turn retry by one notice-only message. | yes |
| `network.verify_after` | One provider probe and one report attempt at each look: after `verify_after`, then after twice as long each time, up to a week. | yes |
| Provider limit reset recorded for switch-back | A reset that passed makes switch-back due; its probe waits for connectivity. | yes |
| Usage readings and credential expiry recorded by probes | Not examined in this change. They are refreshed only by probes, so they are as old as the last probe. | follow-up |
| Incident history retention | Identical consecutive checks are folded into one entry with a first time, a last time and a count, so the offline period stays one explainable span. | yes |
| Run graph staleness labels | Not examined in this change. | follow-up |
| `loop.limits.deadline` | An absolute time. One that passed while offline holds the loop at the next check with `loop deadline reached`, whatever the network is doing. This is the owner's choice and is not softened. | yes |
| `loop.limits.no_progress_timeout` | Counts only time in which progress was possible: see below. | changed here |

**`no_progress_timeout` across a gap.** It used to count all host-clock time, so a machine that slept past it was held on waking although nothing could have run. It now counts time in which supervised work was possible:

- [Time in which no check ran](#time-in-which-no-check-ran) is not counted. Checks that run while the loop is paused, held or disabled are checks, so that time counts as before.
- Time in which the connectivity check found the network down is not counted, including the interval in which it came back, and the limit does not hold while it is down.
- Everything else counts as before, including time outside the operating window while checks run.

The limit keeps its meaning as "this long with no Git change while the loop could work", and `status` shows the adjusted `changedAt`. If you relied on it as a wall-clock cutoff, use `loop.limits.deadline`, which is absolute.

#### Time in which no check ran

A host that slept, or a scheduler that was stopped, leaves a gap between two checks in which nothing was supervised. A scheduler that is simply slow leaves gaps too, and those are ordinary time. keepgoing tells them apart from the loop's own record, not from a fixed number:

- **The usual interval** is the longest of the loop's last five gaps between checks of any kind, or `daemon.interval` if that is longer. It is kept in `state.json` as `recentCheckGapsNs`.
- **A gap is ordinary** when it is no more than three usual intervals. All of it counts, toward the stall clock and toward `no_progress_timeout`. A loop checked every ten minutes, every thirty-one minutes or every hour is nudged, held and stopped by `no_progress_timeout` at the first check on or after the configured time in each case (`TestStalledSessionIsNudgedAndHeldOnScheduleAtAnyCadence`).
- **A longer gap** holds time in which no check ran. One usual interval of it counts and the rest does not: the stall clock and `no_progress_timeout` are paused for the excess, not restarted, so active time before the gap still counts.
- **Before the loop has shown three gaps** (its fourth check) no gap is judged, so the first intervals always count in full.
- **Learning a slower scheduler.** A gap that is judged too long is recorded as three usual intervals, so an outage does not pass for the loop's cadence, while a scheduler changed from every ten minutes to every hour is learned within two checks; until then part of each gap goes uncounted.

Positive evidence is preferred over a gap: an error state, or a connectivity check that found the network down, restarts the stall clock outright. Limits of the gap rule: a check run by hand does not shorten the usual interval; several long sleeps within five checks of each other raise it, after which a later sleep of similar length counts in full, as all of them did before this rule existed.

## net-retry

```sh
keepgoing net-retry --max-wait 2h --attempts 6 -- git push origin cb/example
```

This reruns the command only when it failed while the network was down. When `--attempts` runs out while still offline, it returns the command's own exit code. A failure while the network is reachable is returned at once, so a rejected push or merge is never repeated blindly. Connectivity is an HTTP GET to `LOOPTENDER_NET_PROBE_URL`, which defaults to `https://api.github.com/zen`. Set `LOOPTENDER_NET_PROBE` to a shell command to check connectivity your own way. Both are also read under their [earlier name](configuration.md#environment-variables)s.

### Saved headless resume IDs

For a configured Claude Code or Codex target, `status --json` includes `targetSession` with the saved `id` when recognized, its `state` (`saved`, `missing`, or `unavailable`), `source: "runner_session_file"`, `liveVerified: false`, and an explanatory `message`. Text status shows the same identity as saved history. After retargeting, status reads the selected target's record; missing or disabled targets do not fall back to another target's ID. BB and custom process targets omit `targetSession`.

The record is read without executing a provider or inspecting turn output. Missing metadata does not mean no turn is running, and saved metadata does not verify live identity or resumability. Unrecognized/non-UUID, oversized, or inaccessible records are withheld without modifying the runner's existing resume behavior. See [saved session diagnostics](diagnostics.md#saved-headless-sessions).

### Inspecting a running daemon

`status` and `doctor` query the built-in daemon's private local endpoint for this state directory. The `daemon` object identifies a responsive instance, its phase, next normal check time while waiting, dry-run mode, and build comparison against the inspecting CLI. This is separate from historical `runtime` fields. Agent activity and successful future checks are not established by an endpoint response. `doctor --offline` skips the query.

The endpoint starts with the daemon and is removed on clean exit; stale or unavailable endpoints remain unverified. Endpoint records are private state and must not be shared. A missing endpoint does not rule out an older daemon or external scheduler. See [live daemon diagnostics](diagnostics.md#live-daemon-diagnostics) for fields and limits.

## BB retry and stall handling

Available in v0.1.3 or newer; **fixture-tested only**. A BB `provider/error` with `willRetry: true` suppresses wakes, stall nudges, re-prompts and target moves while BB reports an active or errored thread and the notice is fresh (see [stale retry notices](#stale-retry-notices)). These checks record `provider is retrying the turn`; repeated checks do not spend the active turn's nudge allowance. Stop, pause, existing holds, child-input escalation and configured loop-wide deadline/send/no-progress limits still win. Scheduled fallback probes keep their existing policy.

Queued `client/turn/requested` input is not recovery. The retry summary clears on a new `turn/started`, or on matching `providerThreadId` metadata for an agent-message delta, a started item of any kind the model produced (not a `userMessage` item, which is input), or a successful turn completion. A started item is the model answering again: a provider that recovers straight into a tool call starts a tool item and may write no message for a long time, and before (v0.2.0) only an agent message cleared the notice, so such a turn kept it and later fell under the stall rules as if it had never recovered. Failed/interrupted completion ends retry intent while retaining the error classification. Output from a tool that was already running, a finished item, transcript prose, unknown statuses and mismatched/missing provider identity do not establish recovery. What remains: a provider that resumes an interrupted tool call without starting a new item logs nothing that clears the notice, and whether BB or a provider ever logs a started item while still reconnecting has not been checked against a live thread. A failed or incomplete log scan suppresses prompts and target moves with `provider retry state unverified`, while preserving the active state so an explicit stop can still execute. An active provider error with missing retry intent is also unverified until later structured evidence resolves it. An idle thread with a complete scan follows normal idle rules.

When a tick observes retrying and a later tick observes verified active recovery on the same target, private `state.json` remembers a recovery timestamp across restarts. Ordinary stall detection waits up to one `progress.stall_after` interval from that observation; a real Git change can provide a newer baseline. Already-spent nudges, Git fingerprints/timestamps and independent loop-wide allowances are unchanged. Recorded `unchangedFor` continues to mean elapsed Git time, including the retry; it is not the shortened ordinary stall timer. Later genuine stalls can still nudge or exhaust the remaining nudge allowance. Dry runs do not consume recovery grace. A retry and recovery occurring entirely between observations do not create grace.

Old BB cursors rebuild their summary from structured events once, without replaying previously consumed child notices. Failed scans do not commit retry recovery. This needs readable BB log history; unavailable evidence remains unverified. The cursor stores metadata only, never message content. Recovery never clears a saved hold, and this change neither diagnoses an internet root cause nor adds a unified incident timeline or automatic alert replay. Offline fixtures cover repeated active retries, same-turn recovery, later stalls, restart, partial reads, queued input, migration and controls. No live outage was induced or installed loop changed for verification.

### Stale retry notices

Released in v0.2.0; **fixture-tested only**. A provider can announce a retry and then stop without saying so, for example when the network is lost. Two shapes were observed: a turn ends `failed`, further `willRetry: true` events arrive after that completion, and the errored thread goes silent; or a re-prompted turn logs a notice while BB still reports the thread `active`, and then logs nothing more. Honoring the last notice forever left both unattended, so a notice now counts as a live retry only while there is fresh evidence behind it. The rules use structured data alone: BB's thread status, each event's `createdAt`, turn events, rate-limit windows and the check time. The interval is `bb.retry_signal_ttl` (default `15m`, minimum `1m`).

- **Thread status `error`:** nothing is running, so only notices count. The notice is honored while the newest `willRetry: true` event is at most the interval old. After that the observation stops reporting a retry and the ordinary error handling applies: re-prompts spaced by `errors.backoff` up to `max_reprompts`, then an awaiting-user hold. An `unknown` error still never triggers a handoff.
- **Thread status `active`:** any newer provider or system event in the thread log (tool output, another notice, a started item) shows the turn is alive, and the notice keeps suppressing nudges exactly as before, for as long as such events continue. Requested input (`client/...` events: a person's message, a child notice, keepgoing's own nudge) is not thread activity and does not keep the notice alive. Neither is what BB logs in answer to it: on a real thread every `client/turn/requested` is followed within milliseconds by a `turn/input/accepted` and a `provider/unhandled`, which are not client events and which BB logs even into a dead turn, so they used to re-arm an expired notice. Only that one `provider/unhandled`, the first to follow a request with no thread activity in between, is set aside. Any other `provider/unhandled` still counts as thread activity, as before: an event BB could not interpret is still the thread doing something, and treating a live turn as silent would queue a nudge into it. It never clears a notice, because it is not evidence that the turn recovered. Once the log has been silent for the interval, the notice stops suppressing the ordinary stall handling described under [a silent active thread](#a-silent-active-thread). It never becomes a re-prompt or a handoff, and it earns no recovery grace.
- **A notice after the failed completion**, with no new turn started, is aged the same way. A failed or interrupted completion with no later notice ends retry intent at once, as before.
- **Rate limit with a structured reset:** for a notice that is itself classified `rate_limit`, the interval starts at the reset time, so the notice can stand until the reset and one interval after it. A notice of any other class never borrows the reset of an earlier blocked window. On an errored thread with a reset still ahead the notice is honored only while a retry is actually queued; with nothing queued the ordinary limit rules decide (a recorded limit wait when the reset is within `errors.wait_if_reset_within`, otherwise a handoff when a fallback is confirmed and a recorded limit wait when none is), so a notice cannot keep the loop on a limited account past a healthy fallback. A reset inside `wait_if_reset_within` is therefore recorded as `limit resets in …; waiting` with its reset time, where it used to read `provider is retrying the turn`. Nothing is sent in either case. A rate-limit notice with no structured reset expires like any other.
- **A retry BB has queued:** BB's retry plugin schedules its retry of a failed turn as a queued message, and BB counts it in the thread's `queuedMessageCount`. An errored thread with anything queued is left alone under the existing rule (`messages already queued after error`), ahead of any handoff or re-prompt and whether or not a notice has expired. This is what protects a retry that is genuinely scheduled, including one for a rate limit with no reset keepgoing can see (a pooled route). It was established by reading the installed BB 0.48.1 server and plugin code, not by observing a live retry.

#### A notice BB has already declined

Released in v0.2.0; **offline fixtures only**, not verified against a live BB thread.

When a turn fails, BB's `provider-retry` plugin decides whether it will retry it and records that decision. For an error it does not consider retryable it declines, and nothing in BB will retry the turn. keepgoing used to wait out the provider's last retry notice anyway, up to `bb.retry_signal_ttl` (15 minutes by default) after the newest notice, before recovering.

On an errored thread whose notice is still fresh, keepgoing now asks the plugin and drops the notice at once when all of these are certain:

- `bb provider-retry explain <thread> --json` returns a decision of kind `decline`;
- that decision's `observedAt` is not earlier than BB's time of the thread's latest `turn/started` event and not later than this check, so it is about this failure and not an earlier turn's. Both times are stamped by BB and neither is compared with an earlier check on this host. Whether one BB process stamps both has not been verified: with a remote BB host whose clock runs behind the server's, a decline for an earlier turn could look current. The thread is in error either way, so the cost would be recovering it before its notice aged out;
- `bb provider-retry status <thread> --json` lists nothing pending.

The check then records `retry signal: declined` and applies the ordinary error rules on the same check, which for a network, overloaded or unknown error is a [retry of the failed turn](#recovering-a-failed-bb-turn-by-retry).

- **A pending retry is waited for.** A decision of kind `retry`, or anything in the pending list, keeps the notice. BB's scheduled retry is a queued message, which already stops recovery on its own.
- **The plugin is optional.** A BB without it, a failed call, an answer for another thread, a missing field or any shape not listed here is "unknown". Unknown changes nothing: the notice is honoured until it ages out, exactly as before.
- **Only kinds and times are read.** The decision's reason text is never read, stored or printed.
- **Cost.** At most two extra `bb` calls on a check, each limited to 5 seconds, and only while a fresh notice sits on an errored thread. The second is made only when the first would drop the notice. An active thread, an idle thread, a thread with no notice and a notice that has already aged out ask nothing.
- **After an outage of any length.** The plugin matters only while the notice is fresh. A fixture runs the first check 1 minute, 10 minutes, 20 minutes, 4 hours, 3 days and 3 weeks after the last notice: a declined notice is dropped at 1 and 10 minutes, and from 20 minutes on the notice has aged out, the plugin is not asked, and the result is the same recovery.
- **Limits.** The decision is tied to the failure by time, not by request ID, and relies on BB logging a `turn/started` event when a retried turn begins. Plugin output over 256 KiB is not parsed and counts as unknown. A cursor written by an older build has no turn-start time, so the plugin's answer is ignored until the next turn starts. A held or stopped loop is not observed and asks nothing.

#### A silent active thread

An active thread whose retry notice has expired is handled by progress evidence, and what happens depends on whether the loop tracks Git.

*With `progress.repositories`.* The ordinary stall rules apply. At the defaults (`stall_after: 30m`, `min_wake_interval: 60m`, `max_nudges: 3`), for a re-prompt sent into a dead network at 0:00 whose turn logs one notice and then nothing:

| Time after the re-prompt | What keepgoing records |
| --- | --- |
| up to about 0:16 | `provider is retrying the turn` |
| 0:16 to 1:00 | `active`, `retry signal: expired`; `min_wake_interval` since the re-prompt has not passed |
| about 1:00, 2:00, 3:00 | nudge 1, 2 and 3 |
| about 4:00 | awaiting-user hold, `no progress after 3 nudges`, one report |

The nudges queue behind the stuck turn and are not delivered while it is stuck; here they act only as a countdown to the hold. Nothing is recovered automatically in those four hours.

*Without `progress.repositories`.* There is no stall evidence and no nudge is sent. Instead, once the thread has been observed active with an expired notice for `stall_after` plus `max_nudges` times `min_wake_interval` without a break (3h30m at the defaults, counted from the first check that saw the notice expired), the loop is held for a person with reason `provider retry went silent on an active session` and one report. Any check that sees the thread retrying, logging provider events, or not active starts that period over. This bound applies only to a thread with an expired retry notice; an untracked active thread with no notice is still never nudged or held.

**To recover sooner**, do not wait for the hold: `keepgoing stop` asks the next check to stop the stuck turn, and once the thread is idle `keepgoing resume` clears the stop so the following check wakes it. Shorter `min_wake_interval` and `stall_after` shorten both timelines for every stall, not only this one.

**Why the interval does not cut off a slow, genuine retry.** It bounds silence, not the length of a retry: each failed attempt logs a newer notice, which restarts it. The notices come from the provider. BB's retry plugin is a separate mechanism that acts only after a turn has failed: in BB 0.48.1 it retries an unavailable provider up to four times, waiting one to two minutes before the first and doubling each time (up to eight to sixteen minutes before the last), and a subscription limit shortly after its reset. Each of those waits is a queued message, so the queued rule above covers it however long it is, and the interval does not need to. If the interval is still too short for a provider's own retries, the cost is bounded: on an errored thread at most `max_reprompts` extra recovery attempts (turn retries, which add no prompt, or re-prompts) and then a hold, on an active thread at most `max_nudges` queued nudges or the hold above. Raise `retry_signal_ttl` for a provider known to pause longer between attempts. None of this has been checked against a live slow retry.

**Worked example and the default.** In one observed outage a provider logged ten notices over about 145 seconds (gaps of 1 to 37 seconds), gave up and failed the turn; a second turn failed the same way and ten more notices followed its failed completion, the last at 00:28:30, then nothing. With checks every ten minutes from 00:30 and the default interval, the notice expires at 00:43:30: the 00:30 and 00:40 checks record `provider is retrying the turn` and the 00:50 check sends the first re-prompt (fixture `TestIncidentRetrySeriesAfterFailedCompletion`). Before this change every check waited. Raising the provider's attempt count lengthens the series, not the gaps, so it does not affect expiry. Fifteen minutes is far longer than the 37-second gaps seen here. It was kept when nothing checked connectivity before sending, because a re-prompt sent while the network is still down spends one of `max_reprompts`. With the [network check](#network-outages) on, a shorter interval no longer risks that. Set `retry_signal_ttl` as low as `1m` to re-prompt sooner.

**Clocks.** Event times are bounded by what keepgoing knows locally. An event is never treated as later than the scan that read it, so a source clock running ahead cannot keep a notice fresh. An event that was not in the previous complete scan is never treated as older than that scan, so a BB host whose clock runs behind cannot expire a notice early; on the first scan of a log there is no earlier scan and old events keep their own time. A missing or malformed `createdAt` uses the scan time. A summary saved by an older build is aged from the first scan after the upgrade. A local clock that moves backwards delays expiry rather than causing it. The adapter uses the check's own time, including `tick --now`.

**Where it shows.** `status` prints `retry signal: expired` for the last check (`state.lastCheck.retrySignal` in `status --json`, `retrySignal` in tick output), and `timeline` and `incidents.json` record the observation's retry state as `expired`. A build older than this change that rewrites the journal records that value as `unavailable`.

## BB child awareness

For a BB target, each observation discovers existing direct children with `bb thread list --parent-thread <id> --include-hidden --json`. It then verifies each child's ID, `parentThreadId`, and status using `bb thread show <child-id> --json`. A matching child with status `active` prevents wakes, stall nudges and switch-back of a parent that is not in error. The recorded reason is `child work running`; the parent's own status is preserved. This does not start, stop, message, or re-parent any child.

**A parent in error is recovered whatever its children are doing** (v0.2.0; offline fixtures only). Child work holds a parent because the parent may be waiting for its children. A parent in error is not waiting: it cannot take their results, so the loop would stall until a person acted. Before this change an active child, or a child listing that could not be read, suppressed every error rule, including a handoff to a confirmed fallback after a usage limit. Now, when the supervised session is in error, the error rules apply as if it had no children: the wait while the network is down, handoff, the limit wait and its report, the hold for an authentication error, turn retry, and re-prompts with their cap and backoff. The same holds when the child listing failed (`child status unverified`), because a failing listing is not evidence that the parent is waiting, and it would otherwise stall an errored loop for as long as it kept failing. What stays the same:

- A child waiting on a permission prompt or question still holds the loop first, whenever a listing shows it. This is intended even for a parent at its usage limit with a confirmed fallback: the loop takes the hold and does not hand off until a person has answered the child and resumed. A listing that failed cannot show it; holding back recovery would not show it either.
- Stop, pause, the other holds, the time window, a provider retry in progress and a message already queued still come before the error rules.
- Recovery never messages or answers a child. It retries one only with [lane recovery](#lane-recovery) switched on, and stops one only when a person asks with [`stop --lanes`](#stopping-the-lanes-too). After a handoff to a different conversation the children belong to the conversation that was left, and keepgoing no longer lists or supervises them. They may still be working in the same repositories, so the handoff brief says so in one fixed sentence: how many were working at that check (`1`, `4`, `more than 200`), `at least N` when the listing was incomplete, or that the number is unknown when it failed, and that they are not supervised and were not moved. It carries a count only: no child ID, title or text. The sentence follows a `handoff_file` text too, and is left out when a complete listing showed no child working or the fallback is the same BB thread.
- Known limit: what was announced about children in error is forgotten whenever the loop's target changes, as before this change. After a handoff and a later switch-back, children of the primary that are still in error are announced to it, and reported to the owner, once more.
- A parent that is idle, working, pending or of unknown status is treated exactly as before.

A child that has finished and is now idle no longer blocks its parent. An idle parent is eligible for its ordinary wake on the next supervisor check, subject to controls and pending interactions. Waiting for children does not spend the nudge budget. A plain stop applies to the supervised parent, not its children; [`stop --lanes`](#stopping-the-lanes-too) also stops the running ones. Pause, completion, disabled, and awaiting-user holds remain authoritative.

Discovery requires a complete parent-filtered inventory, including hidden children. The inspected BB 0.48.1 CLI/server implementation passes the parent filter to the database and does not apply a default pagination limit. This complete-list contract is required; versions that silently truncate this query are not supported or verified. CLIs with unsupported flags, incompatible response shapes, failed queries, missing relationship fields, or unknown child states produce `child status unverified`: a parent that is not in error gets no prompt and no switch-back, and a parent in error is recovered as described above. A scan has one adapter timeout budget and accepts at most 200 listed children; larger inventories remain unverified. Duplicate IDs are inspected once. Confirmed missing, archived, deleted, or re-parented children do not count as active. This is a snapshot; a child starting after observation is seen on a subsequent check.

Offline fixtures verify discovery, identity matching, hidden children, conservative failures, controls, and repeated checks across the nudge limit, followed by an immediate next-check wake once the child finishes. No live child turn or model request was started for these tests. Child permission/question escalation is described below; ownership enforcement remains planned. Direct children only are inspected; idle children with active grandchildren do not establish direct active child work.

### Early checks after child outcomes

The built-in daemon also polls the active BB target's new log events at `daemon.control_poll`. A structured `client/turn/requested` system notice with `child-completed`, `child-failed`, `child-interrupted`, or `child-outcome-batch` metadata can bring the next check forward. The notice must contain matching, valid child IDs and terminal statuses in `systemMessageSubject.outcomes`; message text and child output are ignored. This schema was inspected in BB 0.48.1 and exercised with offline fixtures. Older schemas or absent notifications cannot trigger early checks. keepgoing does not change BB's child notification settings.

The parent is observed again before scheduling an early wake check. It must be idle, with no queued messages, background workers, pending parent interaction, active direct children, or incomplete child discovery. BB may already have activated the parent while delivering the notice; that needs no additional wake. A later parent turn start supersedes an earlier notice, and retry requests do not count as new outcomes. Normal tick rules, including controls, windows, yield checks, and current target state, still apply before any prompt is sent.

The existing per-target log cursor consumes each event sequence once, including across restarts, and must save successfully before an early check is authorized. Ordinary observations consume the same events. A crash, failed observation, or exhausted control-poll budget after consumption can lose that early opportunity; it is not retried from the notification. The normal interval remains the backstop. Restarting the daemon still performs its ordinary initial tick; notification deduplication does not disable ordinary idle wakes. Removing runtime state removes the cursor too.

Each notification poll shares the tick lock with normal ticks and retargets and has a total timeout of one `control_poll`. Held loops and loops outside their window do not query providers; lock contention, failed queries, and timeouts do not authorize an early check. With an available CLI and lock, a new eligible notice advances the next check within a control cycle plus query time. Host downtime and slow/unavailable commands have no delivery guarantee. Status continues to show the next **normal** check time; an eligible notice may bring it forward.

This acceleration applies to `keepgoing daemon` only. Cron, BB automations, and other external schedulers invoke `tick` on their own cadence; their timers are not changed. Fixtures cover completed/failed/interrupted notices, batching, deduplication, saved-cursor restart, control holds, other active children, pending parent interactions, lock contention, and bounded slow queries. No live child turns or paid calls were started for this verification. Confirmed pending child input discovered during an early completion check advances an escalation tick instead of a wake; the same hold rules apply.

### Child permission prompts and questions

After verifying each direct child's identity and parent relationship, keepgoing runs `bb thread interactions list <child-id> --json`. An interaction with that child's `threadId` and `status: pending` means human input is needed. Permission prompts, questions, and other pending interaction forms all count; their text, commands, answers, and payloads are never used or included in reports. Only verified child IDs are retained in the reason and report metadata.

Confirmed child input takes precedence over idle wakes, active siblings, stall handling, recovery, and switch-back. The next tick records `await_user`, persists the hold, and emits the configured `await_user` report with `children` and `pendingInteraction` metadata. It does this before scheduled probes, health checks, or repository fingerprinting. Stop and existing control holds still win. No message is sent to the parent or child, no interaction is answered, and no child is stopped or re-parented. An explicit stop continues to apply to the supervised parent only.

The hold survives supervisor restarts and remains after the child interaction is answered elsewhere. Inspect the named child, resolve its interaction, then explicitly `keepgoing resume -c /path/to/keepgoing.yaml`. Resuming while input is still pending creates the hold again on the next tick. Dry runs show the proposed escalation without changing control or sending reports. A failed webhook delivery does not remove the persisted hold; the reason remains available locally.

Child interaction queries share the existing child-discovery timeout and accept at most 500 records per child. Failed queries, missing/mismatched identities, missing or unknown statuses, and incompatible JSON make child status unverified and suppress parent wakes. `resolving` also suppresses wakes while a response is in flight, without asking the person to answer again. `resolved` and `interrupted` are terminal. If one verified child is pending while another child's status is unknown, the confirmed pending child still triggers a hold. Archived, deleted, missing, or re-parented children are excluded. Discovery is a snapshot of direct children, not their descendants.

Offline fixtures cover permissions/questions, identity verification, stale relationships, terminal/resolving/unknown states, cancellation, control precedence, one report per hold, restart persistence, explicit resume, privacy, and a pending interaction concurrent with a completion wake signal. The field/status contract was inspected in BB 0.48.1; live child permission and question flows remain unverified. Pending child input is checked on ordinary ticks and during completion-driven early observations, not by a separate continuous interaction watcher.

### Children in error

A direct child whose status is `error` is not running work. It does not keep the parent classified as `child work running`, and it does not make discovery unverified. Through v0.1.5 nothing else happened: an idle parent got its ordinary wake with the ordinary prompt, and no tick output, `status`, `timeline` or message mentioned that a child had failed. After an outage that failed every child, the parent could carry on without knowing, and the children stayed failed until a person retried each one.

v0.2.0 tells the session that owns the children, and records the count:

- Each BB check lists the verified direct children in error, from the status field alone. keepgoing never sends a message to a child or creates one, and stops one only when a person asks with [`stop --lanes`](#stopping-the-lanes-too). Unless [lane recovery](#lane-recovery) is switched on, it also never retries a child and never reads a child's log; with it on, it may ask BB to retry a failed child's turn, and to decide that it reads the typed fields of that child's log, never its message text.
- When the parent is woken, or re-prompted after an error of its own, and a child has newly entered error, that message ends with a fixed notice: a `[keepgoing:child-errors count=N]` line, then one sentence saying N direct child threads were in error, that keepgoing has not touched them, and that the session should decide whether to retry or replace that work. The notice holds the count only: no child ID, title, task text or error detail.
- Only growth is announced. keepgoing keeps a short hash of each child it has announced, never the IDs. A child not in that record triggers the notice; a set that only shrinks does not, so retrying one child, or archiving or deleting an errored one, says nothing.
- A recovered child is forgotten slowly. A child stays in the record until it has been out of error for `progress.min_wake_interval` (default `60m`). Failing again before that is the same failure and says nothing, so a child that flaps between error and a provider retry is announced once, not on every re-failure, and does not cause a wake each time. A child that has been out of error that long and fails again is announced again. This is the same rule, in the same code, as the owner report below; the two keep separate records only because they are told at different times.
- N is every child in error at that check, including ones announced earlier that the parent may have chosen to abandon. keepgoing cannot tell an abandoned child from one still waiting for a decision.
- With one exception, the notice adds no wake. It rides on a wake the idle parent would have received anyway, so the idle-wake rules, `max_sends`, the deadline, the no-progress timeout and every hold apply unchanged. Stop, pause, awaiting-user and completed send nothing. A child with a pending interaction still raises its hold first.
- The exception is the one case where the notice causes a wake that would not otherwise happen. When a child newly fails while at least one other is still `active`, the parent would be left alone as `child work running` until the last one finished, which can be hours. Instead an idle parent is woken once, with the reason `children in error while other children run`, and is then left alone again. That message is the notice alone, with no task prompt and no goal context, because the parent is waiting on purpose: its first line is `[keepgoing:child-errors count=N running=M]`, and it says M other children are still running and that it is not an instruction to continue the task. This wake is counted against `max_sends`, obeys every hold and limit, needs the same conditions as an idle wake (idle, inside the window, nothing queued or running in the background, complete discovery, no provider retry pending), and is sent no sooner than `min_wake_interval` after the previous send.
- A send the adapter reports as failed or unsupported does not count as announced, and may still have been delivered. After `errors.max_reprompts` such attempts for one announcement, keepgoing gives it up: later wakes go without the notice and the extra wake stops. `status` prints a `child notice:` line and the tick output sets `childErrorNoticeStopped`. Another child failing starts a new announcement with its own attempts, and `keepgoing resume` lets a given-up one be tried again.
- The notice is not added to stall nudges or handoff briefs. A parent that is itself in error hears on its next re-prompt (after a BB [turn retry](#recovering-a-failed-bb-turn-by-retry), in the notice-only message that follows it); an active parent is not woken for errored children and hears on its next wake.
- Incomplete discovery withholds the wake. It forgets nothing about a child it does not show, and a child it shows with a known status other than `error` counts as out of error. A count taken from an incomplete listing is a lower bound: the tick output sets `erroredChildrenPartial`, and `status` and `timeline` print "at least N (child discovery was incomplete)".

The tick output has `erroredChildren` (the count) and `childErrorNote` (true when this check's wake or re-prompt carried the notice). `status` prints a `children:` line with the count from the last recorded check and exposes `state.lastCheck.erroredChildren`; like the rest of that record it is historical and makes no provider call. `timeline` shows the count on each check that saw errored children, and a change in the count is never folded into the previous check. The incident journal stores the count only, under an optional field. Children belong to one thread, so a handoff, a switch-back, `retarget` and BB transfer all forget what was announced.

keepgoing does not decide whether failed child work should be redone. Whether it is depends on the parent agent acting on the notice. No hold is raised for errored children alone. The owner is told separately, by the `child_error` report described next.

#### Reporting children in error to the owner

Released in v0.2.0; **offline fixtures only**. The notice above reaches the parent session, and only when it is next woken or re-prompted. The owner had no signal: the count was in `status`, `timeline` and tick output for anyone who looked. keepgoing now sends a `child_error` report when child threads of the supervised thread are first seen in error.

- **When.** On the check that first sees a child in error, whatever the parent is doing: idle, working, in error, waiting on a person, or waiting on other children. It does not wait for the parent to be woken.
- **Only growth.** One rule decides what counts as a new failure for both this report and the parent notice, using the same per-child hashes: a report is sent when a child newly fails, never because the set shrank. The two records are separate, because the report is sent on first sight and the notice on the next wake, so one can be ahead of the other.
- **A recovered child is forgotten slowly.** A child covered by a report is forgotten only after it has been out of error for `progress.min_wake_interval` (default `60m`). Until then, failing again is the same failure and sends nothing. A child that flaps between error and a provider retry is therefore reported once, not on every flap, and does not use up the reports other children may need. A child that stays recovered for that long and fails later is reported again.
- **Capped per episode.** An episode starts with the first report and ends when every covered child has been forgotten. It sends at most three reports. Children that fail after the third are recorded without a report, and `status` says so. A later failure after the episode has ended starts a new one. Children that keep failing one after another, each before the previous has been forgotten, are one long episode: after its three reports nothing more is sent until they have all stayed recovered, so check `status` for a loop in that state.
- **It does not hold the loop or change a decision.** The check acts exactly as it would have without the report. Nothing needs to be resumed.
- **At most once, never retried.** The episode is saved to `state.json` before the request is made. A report makes a single request without following redirects. If the supervisor is killed mid-request, or the request fails, that report is lost: it is not sent again, the check only carries a warning, and the failure stays visible in `status` and the notification records. If `state.json` cannot be written, nothing is sent.
- **Incomplete listings.** A report is still sent when the child listing was incomplete, marked as such, with both counts as lower bounds. An incomplete listing proves nothing about a child it does not show, so that child is kept. A child the listing does show with a known status other than `error` is treated as recovered, so an episode can still end when the listing never completes, for example because one child has a status this build does not know. Two cases remain. A covered child that a never-complete listing stops showing at all (it was archived or deleted) is kept until a complete listing or a target change; the record is bounded at 200 children, dropping those seen in error longest ago. And when a thread has more than 200 children the adapter inspects none of them, so no child is seen in error and no report is sent.
- **A parent that is gone.** An archived or deleted parent is not scanned for children. That is not evidence of recovery, so the episode is kept; if the thread comes back with the same children in error, nothing is sent again.
- **Holds win.** A paused, disabled, completed, awaiting-user or stopped loop does not observe its target for this purpose, so it neither sends this report nor forgets one already recorded. A failure that happens during such a hold is reported by the first check that observes the target after the hold is cleared, if the child is still in error then. A loop that stays completed or stopped never sends it. Dry runs send and record nothing. A check that raises a hold for a child waiting on a person sends `await_user` and not this report. After a handoff or switch-back in the same check, nothing is reported for the thread just left.
- **Subscription.** `child_error` is in the default `report.events`, because a parent left behind failed children is a loop that has silently stopped making progress. For existing loops this means: a loop whose `report` section has no `events` list starts receiving this event after upgrading; a loop with an explicit `events` list receives nothing new until it names `child_error` or `all`; a loop with no `report` section sends nothing, as before. With no subscription the failure is still recorded and shown as not sent, and subscribing while children are still in error sends the report on the next check. To receive nothing, give `report.events` an explicit list without `child_error`.
- **Where it shows.** `status` prints a `child errors:` block with the counts seen by the detecting check and whether the report was requested, failed, not subscribed or capped (`childErrorReport` in JSON). It says when the loop has no report section, and when earlier reports of the same episode were sent before the event was unsubscribed. The delivery appears as a `child_error` notification.
- **Older builds.** Once a `child_error` delivery is recorded, v0.1.5 and earlier refuse `deliveries.json` because of the unknown event label. An older build that rewrites `state.json` also drops the episode record, so returning to a newer build while the same children are still in error sends one duplicate report. Do not run an older build against the same state directory.

The payload carries the loop name, the number of children in error, the number still running, whether the listing was complete, and the report's number within the episode. It carries no child ID, title, task text or transcript.

Evidence is offline: adapter fixtures for listing errored children and for asking a child nothing but its status and pending interactions; a decision table over every enumerated input, with and without enough time since the last send, showing errored children change the chosen action only in the one case above and the notice follows only a wake or an error re-prompt; tables for growth-only announcement; supervisor fixtures for a shrinking set, a child that fails again, the notice-only wake and its spacing, the cap on rejected sends, blocked wakes, the send limit, dry runs, restart, partial scans and target moves; and a CLI journey against a fake `bb`. No live child thread failed or was retried for these tests.

### Stopping the lanes too

Released in v0.2.0; **offline fixtures and a stand-in bb only**, no live thread has been stopped this way. A plain `keepgoing stop` stops the supervised conversation only. To stop its lanes as well, the conversations it started and theirs, ask for it:

```sh
keepgoing stop --lanes --immediately -c /private/example-loop/keepgoing.yaml
keepgoing client stop --lanes --immediately --id loop_0123456789abcdef0123456789abcdef --json
keepgoing stop --lanes --drop-queued --immediately -c /private/example-loop/keepgoing.yaml
```

`--lanes` saves the request in `control.json` (`stopLanesAt`) with the stop. The check that carries out the stop also stops the lanes. `--immediately` carries the stop out in the command itself instead of waiting for the next check: see [carrying a stop out now](#carrying-a-stop-out-now). Each `stop --lanes` is a new request, so asking again looks at the lanes again; a `resume` ends the stop and the request with it. Plain `stop` is unchanged.

**Which threads.** For a BB target, a lane is a direct child of the supervised thread, found by the listing that child discovery already uses (`bb thread list --parent-thread <thread> --include-hidden`) and verified on its own with `bb thread show`: it must name itself and its parent and be neither archived nor deleted. Its children are found and verified the same way, down to three levels below the supervised thread and fifty threads in all.

| A verified thread that is | What the stop does |
| --- | --- |
| active or starting | stops it with `bb thread stop`, the command the supervised thread's own stop uses |
| in error with a message queued (a retry waiting its turn) | cancels a waiting provider retry with `bb provider-retry cancel <thread> --json`, then stops it. A queued row that is not a provider retry (a retry asked for by keepgoing or a person) is not cancelled, and the report counts it |
| pending, or idle with messages queued | nothing by default: it is counted as not started, with its queued messages kept, and BB may run them. A pending lane has no session yet: no message has cleared dispatch, and `bb thread stop` has no transition from pending. With `--drop-queued` (only with `--lanes`), its queued messages are deleted with `bb thread queue delete`, each lane recorded first, reading only each queued row's ID and thread. Their text is not kept anywhere, which is why this needs its own consent. The supervised thread's own queue is never touched |
| idle with nothing queued, stopping, or in error with nothing queued | nothing: a lane that is not working and has nothing waiting to run needs no stop. Its children are still looked at |
| supervised by another keepgoing loop | nothing, and nothing below it is looked at: that loop's own stop is the way to stop it. "Another loop's" means another loop's session record names it, or another loop's check holds its session claim now ([one loop per session](#one-loop-per-session)) |
| one whose ownership cannot be established (the session directory cannot be used, or the lane's session record cannot be read, is too large or is of another schema) | nothing, and nothing below it: it might be another loop's. Counted as failed, `ownership_unconfirmed` |
| not verifiable, or in a status this build does not know | nothing; counted as failed (`unverified`, `unknown_status`) |
| gone: not found, archived, deleted, or now another thread's child | left out, as child discovery leaves it out. It uses none of the fifty and is not counted |

Another loop's BB fallback thread is in no session record until that loop has been on it, so a lane that is such a fallback, and has never been active as one, is not recognised as another loop's.

A lane is sent nothing but these: a stop, a `bb provider-retry cancel` when a provider retry waits in it, and, only with `--drop-queued`, `bb thread queue delete` for each message queued in a lane that has not started or is idle. No message, no retry. `starting` and `pending` have the meanings BB gives them, which differ from child discovery's: discovery counts neither as active work, while a stop stops a starting lane (its session is starting) and leaves a pending one alone unless `--drop-queued` asks for its queue to be deleted; the supervised thread's own stop stops it when it is pending. Stop wins: lanes are stopped whether the loop is paused, held, completed or disabled, and whether or not the supervised thread itself was running. A dry run looks at nothing and says so.

**Past the bounds.** Nothing past three levels or fifty threads is stopped. The threads there are counted as not checked; the count says "at least" when some were never listed, which is so below anything past a bound. Running `stop --lanes` again after the first lanes are stopped reaches no further: the bounds are counted from the supervised thread each time.

**Recorded first.** Each lane stop is recorded in `sends.json` before it is made, as `stop:lane` under a hash of the lane's ID keyed with a secret kept in the loop's own state (`lanes.key`), and under the request. No lane ID is stored. A check killed in the middle of the stop is followed by one that reads those records ([a send recorded before it is made](#a-send-recorded-before-it-is-made)): a recorded lane that is no longer running was stopped, is counted as stopped and is not stopped again; one still running was not, and is stopped now. A stop made just before the kill that BB has not yet shown as stopping would be made a second time; a second stop is harmless. If a record cannot be saved the stop is still made, as for the supervised thread: not stopping when asked is the worse failure. Lane stops do not count against `loop.limits.max_sends`. The deletion of a lane's queued messages is recorded the same way. `sends.json` keeps at most 64 records waiting to be settled; past that, lane stops are dropped first, since stopping a lane again is harmless, and a brief to another conversation (`handoff`, `switch_back`) is never dropped, so the hold for it is not lost.

**Time.** The walk uses the check's own time budget, checked before each lane. With less than three seconds left it ends, the check says so, and the next check goes on with the same request; the report waits for the end. The lanes an earlier pass of the request stopped or emptied are kept with it (`laneStop` in `state.json`, under their keyed hashes) and counted as stopped or emptied, whatever they are doing now: a person may have restarted one, and it is not stopped again. A lane whose stop failed is not tried again. Only a record left by a check that was killed is looked at again (above).

**A listing that cannot be read.** A listing at any level that fails or times out (BB briefly offline, `bb` not found) does not use up the request. The check says so and the next check tries again, up to three checks. If it still cannot be read then, the report counts it under `listingsUnread`, and what is below it is not checked. Only that case is tried again: one lane's failed stop is not.

**From inside a lane.** If the command that carries the stop out runs in a thread the stop covers (`BB_THREAD_ID` is the supervised thread or one of its lanes), that thread is stopped last, after every other target and only once the walk has finished or been given up (not by a pass that a listing or the time leaves incomplete), and the command says so before it stops anything. `keepgoing stop --immediately` and `keepgoing client stop --immediately` both say it. If BB ending that thread ends the command too, everything else has already been stopped.

**One report.** When the walk is finished, and after the supervised thread's own stop has been made or not, one `stop` report is sent, for the supervised thread and its lanes together, recorded before it is sent so that it is sent once: what is known of the supervised thread itself (`parent`: `stopped`, `stop_failed`, `stopped_earlier` by an earlier check for this stop, `not_running`, or `not_observed` when the check could not observe it), and the lanes stopped, already idle, left to another loop, failed (by error class, for example `thread_host_offline` or `timeout`), and not checked, with queued retries cancelled and not cancelled. It names no thread. A lane stop that fails is reported and not retried by later checks; running `stop --lanes` again makes a new request, which walks the lanes again. The check's JSON has the same counts as `laneStop`, and `state.json` keeps the latest as `laneStop`. It also counts the lanes not started and the queued messages kept in them (`notStarted`, `queuedKept`; "BB may run them"), and, with `--drop-queued`, the messages deleted and from how many lanes (`queuedDeleted`, `dequeued`), saying that their text was not kept. A stop of the supervised thread made by a later check, after that report went out (the first check could not observe it, or its first stop failed and a later one worked), sends its own short `stop` report, as a plain stop does.

**Other adapters.** Headless agents, defined agents and process loops have no child conversations keepgoing can see. A stop with `--lanes` stops the session as before, and its output and report say lanes are not applicable.

### Carrying a stop out now

`keepgoing stop --immediately` and `keepgoing client stop --immediately` save the stop and then carry it out in the command, through the same stop path a check uses, so the stop does not wait for the next scheduled check (with an external scheduler, up to its interval). The command takes the loop's check lock, runs one check that does nothing but the stop (a resume that lifts the stop first leaves it nothing to do), and records it as a check: `status`, `timeline` and the run graph show it like any other. Session claims apply as in any check: the stop waits only while another loop's live check holds the session.

If another check holds the lock, the command waits at most five seconds for it. If it is still running then, the stop is left to the checks, and the command says so: a check that read `control.json` before the stop was saved does not carry it out; the next one does, and a daemon starts that one at its next control poll.

Loop ownership follows the rules of `keepgoing stop`: anyone who may ask for a stop may have it carried out, and a different BB thread does not need to take the loop over. The check does only what the next check would do for the saved stop; if a resume has lifted the stop, it records a check that did nothing and leaves the counts of failed checks as they were. The panel and the menu act as no BB thread. Their stops are offered as options and carried out at once ([stop options](local-clients.md#reviewed-pause-stop-and-resume-client-review-client-apply)); a change there is given 20 seconds, which the stop check takes as its hard limit, so what it cannot reach in that time the next check finishes.

The command exits 0 when the stop was carried out and recorded, even if the check could not observe the target, and when it was left to a running check or to another loop's live check on the session; it exits 1 when the stop was saved but could neither be carried out nor left to a check (the configuration changed on disk, the lock could not be taken, or the check could not be recorded). `keepgoing stop` and `keepgoing client stop` agree on this. The stop check's warnings are printed.

**Finding bb.** The panel and the menu run with the system's PATH (`/usr/bin:/bin:/usr/sbin:/sbin` on macOS), and a loop whose configuration names a bare `bb` finds it only with the PATH its checks run with. So every check records, in `state.json` (`bbPath`), the absolute path of the `bb` executable it actually started: a fact about this machine, nothing read from bb's output. When a stop is carried out from a command, or a review counts the lanes, and the configured command is a bare name not on that command's PATH, the recorded path is used, if it is still an executable regular file, owned by this user or root and not writable by everyone (its link followed). If no such path is recorded, the command says so plainly: "bb could not be found from here", and the stop is saved and left to the next check, which stops the lanes. The page's and the menu's review then offer the options without `immediately`. A configuration that names a path is used as it is.

**Rollback.** A build without this change reads an unsettled `stop:lane` or `report:stop_lanes` record as a send to the agent: it warns with the lane's hash and moves the time of the last send. It also drops `laneStop` from `state.json`, so going forward again with the stop still in force walks the lanes again and sends a second stop report. `control.json`'s `stopLanesAt` is ignored by it.

## One loop per session

Released in v0.2.0; offline fixtures and the two-loop scenario only. Two loops configured on one session, a BB thread or a headless agent's working directory, would each prompt it: one prompt from each loop into one conversation is the duplicate work keepgoing exists to prevent. Each loop has its own state directory, locks, send allowance and re-prompt count, so nothing inside a loop can see the other. Two things outside them do.

**The session claim.** Before a check first observes its session, it takes a claim on that session, and it holds it until the check ends. Before a handoff sends a brief to a fallback, or a switch-back sends to the primary, that session is claimed too.

- A session is identified by the adapter and its identity: the BB thread; a headless agent's working directory, absolute, with links resolved and, on a case-insensitive disk such as the macOS default, spelled as the disk stores it, so `~/Lab/project` and `~/lab/PROJECT` are one session; or a generic process's resume command. The claim's file name is a hash of that, never the thread ID or the path.
- Claims live in one private directory under the user's state directory, `looptender/sessions` (`~/.local/state/looptender/sessions`, or under `$XDG_STATE_HOME`, on Linux; `~/Library/Application Support/looptender/sessions` on macOS). On a computer where the tool already keeps its files in a `keepgoing` directory from before the rename it is `keepgoing/sessions` in the same place, so loops run by builds from before and after the rename use the same claims. Where both directories exist, a check run by this release or later is refused its claim while the same session is claimed in either; see [per-user directories](configuration.md#per-user-directories). It is mode `0700` and its files `0600`. Every loop the user runs uses it, registered or not. What happens when it cannot be used is below.
- A check that finds its session claimed by another loop observes nothing, sends nothing, records nothing in `state.json`, and exits 75 like any busy check: `BB thread thr_… is being checked by loop example-loop-b (pid 4242) since 14:03:07; skipping, nothing sent`. Its next check tries again.
- A fallback whose session is claimed is skipped for that handoff ("another loop is acting on its session"), and the next fallback is tried. A switch-back waits for a later check.
- A claim is an operating-system lock, released by the system when its holder exits, however it exits. It cannot be left behind by a crash; the file that remains is reused.
- The one lasting case is a holder that is stuck: suspended, or hung past its own time limit, which it records with the claim. Every loop's check of that session then exits 75, records the outcome, and says so: `… is still claimed by loop example-loop-b (pid 4242), which passed its own time limit at 14:08 and is stuck; skipping, nothing sent. Find process 4242 and stop it; keepgoing does not break the claim`. One `error` report is sent for each stuck holder (`sessionClaim: stuck`, with the holder's loop and pid), not one per check. `status` prints the same on a `session:` line. To recover, find that process by its pid and stop it; the claim ends with it. keepgoing never breaks a claim, because a claim it could break would not prevent the double send.
- A requested stop wins. It waits only while another loop's check is live and holds the session, and a daemon whose stop met such a claim tries again at its next `control_poll`, not after a whole `interval`. A stop goes ahead past a holder that is past its own time limit (that process is stuck, and a second stop is harmless), and it is reported once as above. Pause, disable and the other holds send nothing and take no claim.

**When the claim directory cannot be used.** There are three cases, and `doctor` (a `session.directory` check) and `status` (its `session:` line) name the real one with its own fix.

- *It cannot be determined*: keepgoing runs with no `HOME` and no `XDG_STATE_HOME`, as under some schedulers. The check goes ahead without the claim and exits as it otherwise would. It warns: `session claim unavailable (<reason>); this check is not protected against another loop acting on the same session at the same moment`. One `degraded` report is sent when this begins and one `recovered` when it ends, with `sessionClaim: unavailable` or `available`; a report whose delivery fails is tried again at the next check, up to 3 attempts for each, and is not marked sent until it is delivered. A handoff or switch-back goes ahead unprotected the same way. The fix: set `HOME`, or `LOOPTENDER_SESSION_DIR` to a private directory. Failing every check instead would get an external scheduler to switch itself off after a few failing exits, and supervision would stop altogether; the refusal below still keeps a second loop from being turned on.
- *It is this user's directory and merely too open* (group or other may read it): the check makes it `0700`, says so once in a warning, and goes ahead protected. `doctor` reports a warning until then.
- *It cannot be repaired safely*: the directory is owned by another user, the path is a file or a symlink, a non-file or another user's file is planted where a claim file belongs, or it cannot be created. The owner is checked, not only the mode. The check then acts on nothing: it observes and sends nothing, and exits as a failed check naming the path and the fix (`remove <path> if it is not keepgoing's, or set LOOPTENDER_SESSION_DIR to a private directory of your own`). The same happens when `LOOPTENDER_SESSION_DIR` and its [earlier name](configuration.md#environment-variables), `KEEPGOING_SESSION_DIR`, are set to different directories; the fix is to unset one. A handoff to that session is skipped and a switch-back waits. A requested stop still goes ahead, with the warning `stop proceeds without the session claim`.

**Turning on a second loop.** `enable`, `start` and `init` (and so the BB plugin's setup, which runs `init` and then `start`) refuse to turn on a loop whose primary session is already the primary of another enabled loop. The message names that loop and its configuration, and says to disable it first or pass `--allow-second-loop`. With the flag, the loop is turned on and the other is named in a warning. What still protects the session then depends on its kind:

- A BB thread: each check holds the claim from observing the thread until its prompt is sent, and the thread's own status is shared, so a check sees the other loop's prompt as the thread being busy and sends nothing. The two loops can still each prompt the thread in turn, once it is idle again.
- A headless agent or a generic process: the claim covers only a check, up to the moment it starts a turn. The turn then runs detached, after the claim is released, and each loop sees only the turns it started itself. So the two loops never start a turn at the same instant, but a turn one loop starts can run alongside a turn the other started, in the same directory or conversation. Nothing prevents that overlap; use the flag for headless loops only when that is acceptable.

Other loops are found two ways: the [registry](local-clients.md), and a supervisors record in the same private directory that every `enable`, `start` and check writes, so loops that were never registered are found once they have been enabled or checked by a build with this change. A loop counts only while its configuration still loads and names its state directory, its control record says enabled, and its configuration still names that session.

**Warnings.** `status` (a `shared:` line, and `sharedWith` in JSON), `validate`, `enable` and `start` say when another enabled loop shares any of this loop's sessions, a fallback's included, or when its current agent works in the same directory, or it tracks the same progress repository. The repository warning is about shared work, two loops whose progress counts the same commits, and not a conflict: two loops on different threads in one checkout always get it. Two headless agents of different kinds in one checkout, a Claude Code loop and a Codex loop, are two conversations, so they are warned about and not refused or claimed against each other: the hazard there is two agents editing one checkout. Lanes a loop starts are not loops and are not affected.

**What this does not cover.** Loops run by different operating-system users, or with different `HOME` or `XDG_STATE_HOME`, have different claim directories and do not see each other. `LOOPTENDER_SESSION_DIR` (or its [earlier name](configuration.md#environment-variables), `KEEPGOING_SESSION_DIR`) sets the claim directory explicitly; loops given different values do not see each other either. `doctor` names the directory whenever it is set.

### Lane recovery

Released in v0.2.0; **offline fixtures only**, and **off by default**. No live lane has been retried by keepgoing. This is the only thing keepgoing ever does to a lane (a direct child conversation of the supervised BB thread), and it does it only when the loop's BB target sets:

```yaml
bb:
  thread: thr_example123
  children:
    retry_errored: true
    max_per_check: 5      # default; 1 to 20
    max_per_episode: 20   # default; 1 to 100
```

With the option on, a lane that a check saw working and a later check finds in error has its failed turn retried with `bb thread retry <lane> --reason "keepgoing: recover the failed turn" --json`: BB runs the same turn again by reference. No message is composed or sent.

**What it can do to a lane.** Ask BB to retry the lane's failed turn, and read the lane's status, pending interactions and the typed fields of its event log to decide whether to.

**What it cannot do to a lane.** Lane recovery never messages a lane (`thread tell`), stops one, creates one, moves, renames, archives or deletes one, or changes its model or settings. (A lane is stopped only by an explicit [`stop --lanes`](#stopping-the-lanes-too), which also forgets what lane recovery knew of the lanes, so after a resume a lane is retried only once a check has seen it working again.) It never falls back to a prompt when BB says there is nothing to retry. It never acts on the lanes of a lane: only direct children of the supervised thread, verified by ID and parent on every attempt.

**Which lanes.**

- **Seen working first.** A lane is retried only if an earlier check, made with the option on, saw it `active`. This excludes a lane that had already failed before the loop first saw it active. In particular it excludes every lane that was already in error when the option was switched on, including when it is switched on in the middle of an outage: those lanes stay as they are until something else makes them work again, after which a later failure is recoverable. The rule exists so that opting in cannot restart work the session had abandoned.
- **Every fact established, on a fresh inspection.** Just before a retry, keepgoing reads the lane again: it must still be a direct child of the supervised thread, not archived or deleted, in `error`, with nothing queued, with no pending interaction, and with a failure that reads as `network`, `overloaded` or `unknown`. Anything that cannot be read leaves the lane alone.
- **Never a lane waiting on a person.** A pending permission or question on a lane raises the loop's hold before any lane work, as before. A lane whose interactions cannot be read is treated as waiting on a person.
- **Never a rate-limited lane or one that needs a login.** A retry would run into the same limit or the same sign-in. These lanes are left alone, announced to the session as before, and counted in the owner report below.
- **Never a lane the provider restricted** (unreleased source). A [restricted turn](#a-restricted-turn-holds) is the provider's decision, not a fault, so a retry would only press it again. Such a lane is left alone, announced to the session, and counted in the owner report as `declined`. A refused lane is treated like a refused turn: false flags are common, so it is retried like a failed lane, within the same per-lane and per-day caps. With lane recovery off it is announced to the session, as before.
- **Not while BB is still retrying it.** A fresh provider retry notice on the lane is honoured, with the same expiry and the same question to BB's `provider-retry` plugin as for the supervised thread.

**How the failure is read.** The lane's status alone does not say why it failed, so keepgoing reads the lane's event log with the same reader it uses for the supervised thread. It decodes typed fields only: event type, sequence and time, the error category, HTTP status and provider code, the will-retry flag, rate-limit windows and reset times. It never decodes message text, titles, tool input or output, and a test fails if any of those reaches what keepgoing stores, reports or prints. `bb thread log --json` does return those fields to the process; they are discarded by the decoder and never kept. This replaces the earlier statement that a child's log is never read: with the option off it still is not.

**What is kept.** Per lane, under a keyed hash of its ID and never the ID: when it was last seen working, the number of retries, their times, the last outcome, and the position reached in its log (in `bb-lanes.json` in the target's state directory, with the provider reference hashed the same way). The hash is keyed with the loop's lane key, `lanes.key` in its state directory, made once and shared with [`stop --lanes`](#stopping-the-lanes-too); `bb-lanes.json` keeps its own. The same lane therefore has a different name in every loop, and a hash cannot be looked up in a table made elsewhere. It is not protection from someone who can read those files. `status`, including `status --json`, shows counts and never the record, its hashes or the key. The child-error notice and report records and the run graph's `child:<key>` references, which existed before this change, still use an unkeyed hash of the child's ID; lane recovery adds no new use of it. A log longer than 2,000 events is read over several checks, and the lane is not retried until its end has been read. Switching the option off removes the record and the active target's `bb-lanes.json` on the next check.

**Bounds.**

| Bound | Default | Set by |
| --- | --- | --- |
| Lanes worked on per check | 5 | `bb.children.max_per_check` |
| Retries per lane for one failure | 3 | `errors.max_reprompts` |
| Retries per lane in 24 hours, across failures | 6 | twice `errors.max_reprompts` |
| Spacing between retries, and between inspections, of one lane | 10m | `errors.backoff` |
| Retries for one failure (an episode), across all lanes | 20 | `bb.children.max_per_episode` |
| Answers of "nothing to retry" or "already queued" in a row before a lane is given up | 3 | fixed |
| Sends kept back for the supervised session | 4 | `errors.max_reprompts` + 1 |
| Time for one lane | 40s | fixed |
| Time left in the check below which no further lane is started | 30s | fixed |

- **Sends.** Each retry uses one send from `limits.max_sends`. The supervised session comes first: lane retries never use the last `errors.max_reprompts` + 1 sends, which is a whole recovery of the session and one notice. When only those are left, lane work stops, the lanes are announced to the session as its own, and no hold is raised by lanes. Without `max_sends` there is nothing to keep back.
- **One failure.** A lane's count is kept until it has stayed out of error for `progress.min_wake_interval`, so a lane that fails again straight after a retry spends the same three attempts: it is retried at 0, 10 and 20 minutes, given up at 30 and reported once.
- **One day.** A lane that works for longer than `min_wake_interval` after each retry and then fails again is a new failure each time. Its retries are still counted over 24 hours from the first: after six it is given up and reported, and it stays given up until that day has passed and it has been out of error for `min_wake_interval`.
- **An episode** is one failure being recovered, across lanes. It ends when no lane is still being recovered: each has been forgotten or given up. A lane that stays given up and in error does not keep it open, so the 20 retries and the three reports apply to each failure, not to the life of the loop.
- **Time.** When too little of the check's time is left, the remaining lanes are recorded as deferred and taken first on the next check. A `bb thread retry` that is still running when the lane's 40 seconds end is cut off; BB may have acted on it, so it is counted as an attempt.

**Giving up.** A lane is given up when it has used its retries for the failure or for the day and is still in error after the spacing, when it is still due once the episode's retries are spent, or when BB has answered three times in a row that there is nothing to retry or that a retry is already queued. A given-up lane is not retried again, is announced to the session and is counted in the owner report.

**Order in a check.** Lane work happens after the session is observed and **before the check's decision**, so that the decision and the notice already know which lanes are being recovered. It is gated on what the engine would decide at that point. A stopped, paused, disabled, completed or awaiting-user loop is not observed, so nothing is retried. A check that would raise a hold, stop the session, hand off or switch back, falls outside the window, finds the session itself waiting on a person, stopping or in a state that could not be read, or is a dry run leaves every lane alone. The control file is read again before each lane, so a stop, pause or hold requested while a check is working through its lanes ends lane work before the next one. A hold raised later in the same check for another reason, for example a failed handoff, does not undo retries already asked for. A handoff, switch-back, `retarget` or transfer forgets the record: no lane of the conversation that was left is retried afterwards.

**The network.** A lane retry needs the network, so the [connectivity check](#network-outages) is made first. While it fails nothing is asked of BB, nothing is counted and no send is used, however long the outage lasts; fixtures run 20 minutes, 4 hours, 3 days and 3 weeks. The first check after it passes retries each eligible lane once, within the bounds. BB applies no age limit to a retry. If BB answers that there is nothing to retry, or that a retry is already queued, no attempt or send is counted, nothing is recorded as sent, and the lane is asked again after the spacing; the third such answer in a row gives it up.

**What the session is told.** Only about lanes keepgoing will not act on. A lane keepgoing is recovering, or will recover on a coming check (it is over the per-check limit, was put off for lack of time, or its log has not been read to the end yet), is not announced: it is not the session's to restart. A lane is announced, by the [notice](#children-in-error), when it is given up, and at once when keepgoing will not retry it at all: never seen working, rate limited, needing a login, restricted by the provider, waiting on a person, or not verifiable as a direct child. When the provider has no turn retry, or the sends left are kept for the session, every lane is announced. A notice that goes out while other lanes are being recovered says so: its first line is `[keepgoing:child-errors count=N recovering=M]`, and it says keepgoing is recovering M of them itself and will say if it gives one up, that the other N−M are the session's, and that the session should check a child's current state before retrying or replacing it. It never says which lanes.

**What the owner is told.** A `child_recovery` report, once per lane, when lanes are given up or are left alone because they are rate limited, need a login, or were restricted by the provider. It carries counts only (`givenUp`, `rateLimited`, `authFailed`, `declined` in unreleased source, `retried`), never an ID. At most three are sent per episode, each makes one attempt, and the record is saved before the request. A report that could not be sent, because the network was down, no time was left or the loop was not subscribed, is sent by a later check. `child_recovery` is in the default `report.events`; a loop with an explicit list receives it only after naming it or `all`. The `child_error` report is unchanged. Because that record is saved in the middle of the check, a supervisor killed after it and before the check's end leaves the lane retries of that check unsettled; the next check counts them again as made. That can spend an attempt twice, never retry a lane twice; it errs on the safe side.

**Where it shows.** The check's JSON has a `lanes` object with `retried`, `givenUp`, `deferred`, `notRetried` (a count per reason) and `waiting` (`network`, or `control` when stop, pause or a hold ended lane work during the check). `status` prints a `lane recovery:` block (`laneRecovery` in JSON), `timeline --kind child_retry` shows each check that did lane work, `incidents.json` stores the three counts, and `runs` lists each retry BB was asked for as a `child_retry` send against the loop's target, except those BB answered with nothing to do. All of it is counts: no lane is named anywhere.

**Another loop's lane.** A lane another keepgoing loop supervises (its session record names it) or holds the session claim of now is that loop's: it is never inspected or retried here, and it is counted as `other_loop`. One whose ownership cannot be established (the session directory cannot be used, or the lane's session record cannot be read) is left alone the same way, as `ownership_unconfirmed`. Both are announced to the session like any lane keepgoing will not act on. The same check is the one [`stop --lanes`](#stopping-the-lanes-too) uses.

**What this does not establish.** That a retried lane's turn succeeded: BB accepting a retry is not proof of that. Whether the work a given-up lane was doing should be redone is still for the session or a person to decide.

**Upgrade and rollback.** Upgrading needs nothing: older state loads, and a loop without `bb.children` behaves as before. Going back to a build without this change is not clean, in three ways:

- **Every loop, option on or off.** A check by this build writes `incidents.json` at schema 10. An older build cannot read it: its `tick` still makes and acts on its decision, but exits 1 with `incident history unavailable; check private state storage` and records no history, and its `timeline` has none. Before running the older build, move `incidents.json` out of the state directory; it starts a new journal.
- **Only a loop that opted in and had a lane retried.** `graph.json` then holds a `child_retry` send, which an older build does not accept: its `runs` reports `graph: corrupt`. Move `graph.json` aside as well. A loop that never opted in, or whose lanes were never retried, has no such record: nothing is written to the run graph unless BB was asked to retry a lane and did not answer that there was nothing to do.
- **The configuration.** An older build rejects the `bb.children` key. Remove it.
- **An unsettled lane retry.** If a check by this build recorded a lane retry (`child_retry` in `sends.json`) and could not save what happened, an older build counts that record as a send to the supervised session: it warns, and moves the time of the last send.

`state.json` needs no change: an older build ignores the `lanes` record and drops it on its next save. `bb-lanes.json` is ignored by an older build and can be deleted. Moving the two files aside was not run against an older binary here.

## One owner per loop

When `keepgoing enable` runs inside BB, it records `BB_THREAD_ID` in `control.ownership`, with a generation number. The owner is the thread operating the loop; it is separate from the configured agent target. Claiming or transferring ownership never retargets the loop or changes a BB parent/child relationship. `status` shows the owner and latest handoff, and `status --json` includes the ownership metadata.

A different BB thread is refused by `validate`, `enable`, `start`, and `daemon`, as well as direct ticks, resume, retarget, and executing manual probes. Read-only status/doctor and probe previews remain available. Disable, pause, stop, complete, and await-user remain available from any thread. Missing `BB_THREAD_ID` identifies an external scheduler or ordinary terminal: commands use the existing claim without changing it. Legacy loops without ownership metadata continue working; their first enable from a BB thread records the claim. This relies on cooperative callers and private runtime files, not an authentication boundary.

From the BB thread that should become the new owner:

```sh
keepgoing validate -c /path/to/keepgoing.yaml --take-over
keepgoing enable -c /path/to/keepgoing.yaml --take-over
keepgoing status -c /path/to/keepgoing.yaml
```

Validation only previews eligibility; it never claims ownership or enables a loop. Validation against an existing runtime directory may create its private control lock; it creates no missing runtime directory. When replacing an existing owner, `enable --take-over` transfers only the claim, preserving disabled, pause, stop, awaiting-user, completion, and the existing note unless a new note is supplied. If the loop was disabled, a subsequent `enable` from the new owner is required; use `resume` separately to clear other holds. First claims and same-owner enables set `enabled` as usual. The previous owner is recorded as `handed_off` with a timestamp; only the latest handoff is retained. A same-owner enable leaves the generation unchanged. Takeover requires a valid `BB_THREAD_ID` and is never inferred from inactivity or a failed status lookup. No owner-status provider query is made: even an idle, archived, or missing owner retains its claim until an explicit transfer. Malformed ownership metadata is refused rather than silently discarded.

`enable --take-over` needs the loop's check lock, which the old owner's supervisor holds during each check and control poll. It waits up to 5 seconds for it. If a check holds the lock for all of that, it changes nothing, says the old owner's supervisor is busy and to run it again, and exits 75. Plain `enable` and `resume` do not wait: they exit 75 at once while a check holds the lock.

A running daemon is bound to its starting ownership generation. After a successful transfer it exits before further provider work, normally at its next control check, and releases its daemon lock. This also applies to a daemon started by an identity-free scheduler and to a previously unowned daemon when the loop is first claimed. `enable --take-over` does not start a replacement daemon; after the old daemon exits, start `daemon` from the new owner or scheduler. `daemon --take-over` can claim and start when no daemon already holds the process lock, preserving disabled and other held state. It cannot evict an existing daemon. `daemon --take-over --dry-run` is rejected; use validation to preview a transfer.

Ownership and transfers use the runtime state directory, so multiple config paths or directory symlinks sharing that directory share the same owner and locks. A `control.json` file symlink is refused: use the original state directory instead. Distinct runtime directories are distinct loops; moving a config to another state directory is not an ownership transfer. Do not alias individual runtime files with hard links or mix old binaries that discard ownership metadata. Removing or replacing runtime state also removes its ownership history and safeguards.

Claims and transfers serialize with ticks and early polls. If a tick is in flight, takeover exits 75 and must be retried; it never interrupts or rolls back that tick's work. Control updates have a separate short lock, preserving concurrent pause/stop requests without waiting for long provider calls. Control-lock contention also exits 75. No thread is created, stopped, re-parented, or messaged by ownership operations.

Offline fixtures verify conflicting identities, preview and explicit takeover, shared-state config paths, simultaneous claiming processes, directory aliases, control-file symlink refusal, hold preservation, scheduler access, and old-daemon exit including a transfer back to its original owner. Live transfers between real threads remain unverified; the tests make no live model calls.


## Owned headless cancellation

New headless Claude Code and Codex turns run through a detached keepgoing wrapper on macOS, Linux and Windows. Each turn gets a random private `stopKey` in `run.json`; it is passed to the wrapper only and removed from the agent environment. The saved PID never authorizes a signal, and it does not decide whether a turn is running: a turn is running while its wrapper holds `turn.lock`, which the operating system releases when the wrapper ends.

**Turn liveness.** Starting a turn waits up to ten seconds for the lock, so a turn that is still running is never started over; if the lock stays held, the start is refused and nothing is changed. It is also refused when any of the previous turn's files cannot be cleared, for example because the directory has become read-only. One exception: on Windows, the prompt and output files of an agent that outlived its wrapper can still be open, and an open file cannot be moved there; those stay in place and the new turn overwrites them, as before this change. Such an agent can still write into them while the new turn runs, so that turn's output can contain the earlier agent's writes. The exit code, the turn keys and the markers are never left. The files are moved aside together (as `<name>.old`) and deleted only once the new turn's record is saved; a start that fails before that, for any reason, puts them back, so the previous turn still reads as it did and the new turn can never read as finished with the old exit code. If a file cannot be put back, the start's error names it, the exit code is left aside, and the previous turn reads as failed with its result marked incomplete; it is never shown as finished with output missing. The next start that succeeds removes what was left aside. It then waits up to ten seconds for the new wrapper to take the lock. A wrapper that does not is shut out: the record is marked abandoned, a wrapper that arrives later finds the mark and runs nothing, and the turn reads as crashed, which the next check treats like any turn that died. Starting and reading a turn happen under the loop's check lock; starting is not safe to do twice at once outside it.

**Upgrading and rolling back.** Stop the daemon before you replace the binary on disk or restore an older one, then start it again. A daemon starts each turn by running the binary at its own path as the turn's wrapper, and the two have to keep the same contract: what the wrapper locks, checks and writes. That contract has a label (`keepgoing-turn-wrapper 2` in this build), which changes only when the contract does, not with every release. Before a start, the daemon asks the binary on disk for its label: one short run of the binary that starts no turn, repeated only when the file is replaced or changes.

When the binary answers with another label or does not know the question, or cannot be run or does not answer within ten seconds, no turn is started. The two cases are reported with different reasons. Nothing was sent, so nothing is counted: no send against `max_sends`, no re-prompt, no nudge, and so no hold however long it lasts. The check is recorded as succeeded with the reason, an `error` report with `cause: start_refused` is sent once when the refusal begins, `status` shows a `turns:` line with the reason and since when, and `doctor` reports it as `runner.wrapper`. The first start that is accepted ends it. A handoff or switch-back to a headless target that is refused this way still fails that check as before.

So a daemon from this build with an older binary restored under it sends nothing until it is restarted; it does not run turns it cannot see. The check cannot protect the reverse order of a rollback: an older daemon does not ask, so stopping it first is what keeps it from running a newer wrapper.

A turn started by an older build holds no lock and is still judged by its PID until it ends. If the machine has restarted since that turn began, it is read as crashed whatever now has that PID, so a loop that was stuck on a reused PID before the upgrade recovers at its next check. The start of the machine is read from the operating system (in a container, the host's), and a record from within a minute of it is still judged by its PID. Two cases are not covered: a PID reused without a restart of the machine, and a platform where the start time cannot be read. One case can go wrong the other way: if the clock is stepped forward by more than a minute past the true start of the machine while an older build's turn is still running (a virtual machine resumed after a long pause can do this where the start time is worked out from the clock), that live turn reads as crashed and is re-prompted. Let turns started by an older build finish before upgrading where that matters. There, pause the loop, confirm with the operating system's own tools that the PID in `targets/<id>/run.json` is not a keepgoing wrapper or its agent, delete that `run.json`, and resume; the next check starts a turn on the saved session.

A stop writes `stop-request.json` atomically with that key and a fresh request ID, then waits up to three seconds for matching `stop-ack.json`. The wrapper checks requests every 100 milliseconds and accepts only its own key. Old requests cannot cancel a new turn; old acknowledgements cannot confirm a new request. A timeout reports an unconfirmed stop and leaves the request pending. A matching receipt means the wrapper accepted cancellation, not proof that the operating system has completed termination. Later observations still determine liveness.

The live Unix wrapper verifies that it leads its own process group, then signals that group itself. While it is alive, its own PID/group cannot be recycled. Windows uses an unnamed native job containing the wrapper and descendants, terminated through the wrapper's retained job handle; no `taskkill` PID lookup occurs. Job setup failure prevents the agent from starting. Windows job membership/termination follows the [native job-object contract](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects).

This is a cooperative channel in private runtime storage, not a security boundary against writers who can replace those files. Never share the stop key or raw runner records in diagnostics. A crashed wrapper cannot acknowledge a new request, even if its old PID belongs to another process. Descendants that outlive an abrupt wrapper death, or detach from a Unix process group, are not recovered or tracked by this change: a wrapper killed alone leaves its agent running, the turn reads as crashed, and the next turn can start beside it. Inspect them manually; do not signal PIDs merely because a stale record names them.

Legacy turns without the key remain observable but automatic stop refuses them. Let an existing turn finish before upgrading, or inspect it manually using native process identity evidence. Do not use an older binary to stop new turns: old versions ignore the key and retain the unsafe saved-PID path. Supervisor restart does not change an existing wrapper/key. This implementation is covered by local subprocess and synthetic stale-record tests; it does not establish live provider resume/cancellation or installed-service acceptance.
