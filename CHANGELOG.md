# Changelog

## Unreleased

- **The BB plugin says looptender.** keepgoing is being renamed to looptender, and the plugin (v0.3.1) is the first part to show it: BB lists it as looptender, and its labels and messages read `looptender: enabled`, `looptender: watching …`, `looptender: checks have stopped` and so on. Nothing you type changes: the plugin id (`keepgoing`), the `bb keepgoing` command, the `keepgoingPath` setting, the `keepgoing` executable and `keepgoing.yaml` keep their names, so updating keeps the plugin's settings, secrets and schedules. It still runs whichever executable the setting names. Plugin unit tests only; not yet reinstalled into a running BB.

- **Environment variables are also read as `LOOPTENDER_…`.** The next step of renaming the tool to looptender. Every `KEEPGOING_X` variable now has the name `LOOPTENDER_X` as well, and the earlier names keep working: nothing in an existing setup needs to change. This covers `SESSION_DIR`, `REGISTRY_DIR`, `ROUTES_FILE`, `PANEL_OPENER`, `NET_PROBE`, `NET_PROBE_URL`, and the default report names `WEBHOOK_URL` and `WEBHOOK_SECRET` (the default `report.url_env` and `report.secret_env` are now the `LOOPTENDER_` names, read first, then the `KEEPGOING_` ones; names you configured are read as written). Resume and probe commands receive `MODE`, `PROBE_TIER`, `PROBE_MODEL` and `CANDIDATE` under both names. When both names of one variable are set to different values, the `LOOPTENDER_` one is used and `doctor` warns, except for the three that name a place (`SESSION_DIR`, `REGISTRY_DIR`, `ROUTES_FILE`): those are refused until one is unset, because commands that each honoured one would work in different places. A check then acts on nothing (a requested stop still goes ahead), registry commands refuse, and the standard route list reads as unusable with the new reason `named_twice`. `doctor` lists the earlier names in use and never prints a value. Messages now name the `LOOPTENDER_` variables. **Going back:** v0.2.0 and earlier read only the `KEEPGOING_` names. Unit and fixture tests only; the whole-binary scenarios and the release smoke keep setting the earlier names. See [environment variables](docs/configuration.md#environment-variables).

## 0.2.0 (2026-11-14)

**The first release under the [Sustainable Use License 1.0](LICENSE).** v0.1.5 and every earlier release stay Apache-2.0 ([#179](https://github.com/connorburgess/keepgoing-agents/pull/179), [LICENSING.md](LICENSING.md)). The [release notes](docs/releases/v0.2.0.md) are the reader's version of this section, and explain why this is 0.2.0 and not 0.1.6. In short:
- the licence changes;
- several behaviours change on upgrade;
- v0.1.5 cannot read the records this version writes without the steps below.

The BB plugin is released from the same tag as **0.3.0**. Its loop card says when checks have stopped, and it is under the same licence.

**What is new.**
- **Recovery that does not spend into a dead network:** a connectivity check before every recovery step.
- **BB recovery:** a failed BB turn retried by reference, and stale or declined retry notices no longer waited on.
- **Hung turns:** a turn that hung through an outage or a sleep has its nudges held back.
- **Stopped schedulers and children:** a stopped scheduler is noticed; failed child threads are reported; failed lanes are recovered (opt-in); `stop --lanes`.
- **Daemon timing:** the daemon checks again within a minute of the network returning, and at a limit's reported reset.
- **Bounds:** one loop per session; every automatic send recorded before it is made; a hard time limit per check; the no-progress flag.
- **The panel** (`keepgoing panel`, `dock`, with controls behind `--allow-changes`) and a rebuilt macOS menu preview, both with pause all and stop all.
- **New commands:** `keepgoing runs`; a navigable `timeline`; usage readings; a standard route list kept once per user (`routes: standard`, `keepgoing routes list`; read-only in this release).
- **Agents and fallbacks:** agents defined in configuration (`adapter: custom`); a primary-only Cursor adapter; handoff into a new BB conversation; `fallbacks` editing commands.

**Behaviour changes.**
- keepgoing makes one outbound request of its own (`GET https://api.github.com/zen`, no identifier) before a recovery step; `loop.network` changes or turns it off.
- Sends are recorded before they are made.
- `resume` of a loop held on a spent cap starts a new episode.
- Three corrections to BB retry notices.
- `no_progress_timeout` and the stall clock skip time in which nothing could run.
- Time windows follow the local clock across daylight-saving changes.
- `tick` exits 0 whenever the check was recorded.
- `enable --take-over` waits up to 5 seconds for the lock.
- The panel's runtime files move to the user state directory.
- Windows needs 10 version 1709 or newer.

**Upgrade.**
1. Copy each loop's state directory.
2. Replace the executable.
3. Restart each daemon or service.

No configuration change is needed. A `client prepare-resume` ticket made before the upgrade is refused after it; prepare it again. External schedulers such as BB automations keep working; the daemon's faster re-checks apply only under `start` or a service.

**Going back to v0.1.5.** A loop that ran on 0.2.0 needs these steps first, each detailed in the [release notes](docs/releases/v0.2.0.md#going-back-to-v015):
- restore or remove `incidents.json` (schema 10);
- move aside a `deliveries.json` that records a new event;
- remove settings and report events v0.1.5 does not know (it reads the configuration strictly);
- do not run it against a run graph that records a new conversation.

It drops the newer fields of `state.json`, `control.json` and `bb-cursor.json`.

**Evidence.** The new reliability behaviour is implemented and fixture-tested only, and the [live outage check](docs/testing.md#live-check-a-long-time-offline) has not been run. Live so far:
- one Cursor walkthrough on macOS (first turn, exact resume, stop);
- the earlier BB, daemon, probe and report checks listed in [integrations](docs/integrations.md).

### Detail

- The release smoke check (`scripts/smoke-release.py`) runs in a home of its own, so running it no longer leaves session claims in the caller's state directory (#223).

- Pull-request checks refuse a change that adds git conflict markers (#224).

- `docs/devices.md` revises the proposed first-version defaults for moving loops between devices. It is a design document; nothing in it is implemented (#218).

- **The daemon checks again as soon as it can tell recovery is possible.** Under `keepgoing start` or a service, while the last check found the network down, the daemon makes the same connectivity check at most once a minute and starts the next check when it passes, instead of waiting out `daemon.interval`. A check that waits on a provider limit records the limit's structured reset (`limitResetsAt` in `state.json`), and the daemon runs the next check at that reset when it comes before the end of the interval. Nothing is sent from the wait. External schedulers, including BB automations, are unchanged. See [network outages](docs/operations.md#network-outages).

- Standard route list (first part). A loop with `routes: standard` follows one ordered list of routes kept once per user in `routes.yaml`, instead of a `fallbacks.yaml` of its own; existing loops are unchanged. `keepgoing routes list` (with `--json`) shows the standard list, which loops follow it and each loop's effective routes. If the list cannot be read, following loops keep being supervised on their current route with no other routes, say so, and report it once when it begins and once when it ends; a loop on a route that is removed from the list stays on it. The commands that edit the lists are not built yet. The private digest of a loop's loaded sources now covers the standard list too, so a `client prepare-resume` ticket made by an older build is refused after the upgrade; prepare it again. Offline fixtures only. See [the standard route list](docs/routes.md).

- **Stop all, from the panel and the macOS menu.** The same one review of every loop as pause all, with each loop's own stop options (#209) behind one line each. It says which stops are carried out when you confirm and which at each loop's next check, and offers **Stop the Conversations** or, when any loop has lanes, **Stop Them and Their Lanes**. Each loop is stopped as its own review offered it: its lanes only if it has them, at once only where it can be, and its expect value binds that, so a single loop's review cannot stand in for it. Deleting queued lane messages is never offered for every loop at once. Every reviewed stop is saved before any is carried out, so running out of time leaves a stop to the next check and never leaves a loop unsaved; run from a BB thread, that conversation's own loop is carried out last. The result names which loops stopped now, with what happened to their lanes, and which wait for their next check. Also, `client apply stop` for one loop now refuses an option its review did not offer, as the page does, and values from a review of every loop and of one loop are no longer each other's. New `client review stop --all` and `client apply stop --all [--lanes]`; `canAll` gains `stop`. Fixtures and unit tests; no live BB loop with lanes was stopped.

- **Behavior change: the nudges to a BB turn that hung through an outage are held back.** For loops that track Git progress, inside their operating window, a turn that has logged nothing since an outage began (a failed connectivity check, or a gap the missed-time rule judges missed, such as the computer sleeping, counted from its waking), and nothing for `stall_after`, with no tool item open and nothing else to explain its silence, may be hung. The stall rule then decides as always, but each nudge it would send is held back: counted and recorded as a nudge, with the same connectivity check first, and not sent. So the stall rule's own hold after its nudges comes at the same check, now with the reason that the nudges were held back. A turn that logs again is handed back to the stall rule. Tests run each journey with the watch on and off and find the same actions, holds, connectivity checks, probes and sends, except the held-back nudges. A held-back nudge is not a send, so it spends nothing of `loop.limits.max_sends`: where the stall rule alone would have reached that limit's hold first (with `max_sends: 1` at the defaults, 2h40m against the nudge hold at 5h30m), the watch holds at the nudge hold. `status` tells held-back nudges from sent ones, and the timeline gives them their own causes (`nudge_held`, `hung_wait`, `stall_limit_held`). Before, the nudges were sent into the hung turn. A new `hung_turn` report event, not in the default list, says once that the nudges are being held back. Older binaries reject `hung_turn` in `report.events` and cannot read a `deliveries.json` that records it; see [upgrading and going back](docs/operations.md#upgrading-and-going-back) and [a turn that hung through an outage](docs/operations.md#a-turn-that-hung-through-an-outage).

- The time an untracked active session may stay silent after its retry notice expired (`stall_after` plus a `min_wake_interval` per nudge) now stops at the longest time instead of overflowing to a negative one with an extreme `min_wake_interval`, so such a session is never held at once.

- **Opt-in: recover failed lanes.** A BB target may set `bb: {children: {retry_errored: true}}`. It is off by default, and with it off nothing changes. With it on, a direct child thread that a check saw working and that then failed with a `network`, `overloaded` or `unknown` error has its failed turn retried with `bb thread retry`, by reference and with no message: at most 5 lanes a check (`children.max_per_check`), `errors.max_reprompts` attempts a lane spaced by `errors.backoff`, and 20 retries a failure (`children.max_per_episode`), within the check's time budget and `limits.max_sends`, and only after the connectivity check passes. Lane recovery never messages, stops or creates a child; another loop's lane is left to that loop; a stop with `--lanes` forgets its records, so after a resume a lane is retried only once it has been seen working again. A child waiting on a person, rate limited or needing a login is left alone, and a child that was already in error when the loop first saw it (including every child in error when the option is switched on) is never retried. To tell what failed, keepgoing now reads the typed fields of such a child's event log (event type, error category and codes, will-retry flag); message text is never decoded or stored. The session is told only about lanes keepgoing will not act on: a lane it is recovering, or will recover on a coming check, is not announced until it is given up, and a notice sent meanwhile says how many are being recovered (`recovering=M`). Further bounds: six retries per lane in 24 hours, three answers of "nothing to retry" or "already queued" before a lane is given up, and the last `errors.max_reprompts` + 1 sends of `limits.max_sends` are kept for the supervised session. Stop, pause or a hold requested during a check ends lane work before the next lane. Lane records use a hash keyed per loop, and `status` never shows them. The owner gets a `child_recovery` report (new, in the default `report.events`, counts only) when lanes are given up or left alone for their failure class. `status`, `timeline --kind child_retry`, the check's `lanes` object and `runs` (a `child_retry` send) show the counts. Incident schema 10 and timeline schema 6. **Rollback:** after any check by this build, option on or off, an older build's `tick` still decides but exits 1 with `incident history unavailable; check private state storage` until `incidents.json` is moved aside; a loop that opted in and had a lane retried also has a `child_retry` send in `graph.json`, which makes an older build's `runs` report `graph: corrupt` (a loop that never opted in has none); and an older build rejects the `bb.children` key. See [upgrade and rollback](docs/operations.md#lane-recovery). Offline fixtures only. See [lane recovery](docs/operations.md#lane-recovery).
- **Pause all, from the panel and the macOS menu.** One review of every registered loop names each with a one-line effect, up to eight then "And N more.", and a total ("Pauses 3 of 4 loops; 1 is already paused."), without repeating each loop's whole review. Confirming pauses each loop on its own, through the same function as a single pause, and only if its control record is still the one reviewed; a loop changed in between is left and the rest are paused. The result names each loop's outcome and never reads a partial result as success ("Paused 2 of 3; 1 needs a new review."). On the page it is **Pause all…** on the overview, with `--allow-changes`; in the menu, **Pause All Loops…**. New `client review pause --all` and `client apply pause --all --expect KEY=VALUE…`; `panel list --json` gains `canAll`. Stop all follows once a stop can be carried out at once. Fixtures, unit tests, the menu's contract smoke and a headless browser run on fictional loops.

- New, off by default: `loop.timing` collects usage readings of a loop's first route. Turned on, it probes the first route every `probe_every` (default 12h), including while the loop runs on it, and once more as each named window in `windows` comes within `near_reset` (default 6h) of its reported reset, within that route's own `probe.daily_cap`. The readings build the history `fallbacks list` and `status` project from. It does not change routes: nothing decides from the readings yet. Each probe is a small paid request, and `validate`, `status`, `doctor` and `fallbacks check --dry-run` say how many a week and on which model, for example "about 14 small paid probes a week for this allowance at a 12h cadence". A window for one model alone is read only on a probe of that model. For a BB loop, they warn that the readings come from this computer's CLI sign-in, which may not be the account BB uses. Timing needs `loop.fallbacks` and a way to probe the first route; `validate` refuses it otherwise. With timing off, probes are exactly as before. Fixtures only. See [timing](docs/configuration.md#timing).

- **The macOS menu says when a loop's checks have stopped.** Run from an app bundle (`integrations/macos/scripts/make-app.sh` builds one into `.build`, and never installs or opens it), the menu posts one notification per gap, named by the loop and its last check, from the reads it already makes. `--no-notifications` turns it off; a menu run as a bare executable posts none. `panel list --json` gives `overdueSince` for such a loop. See [notifications when checks stop](integrations/macos/README.md#notifications-when-checks-stop).

- The macOS menu offers the stop option that also deletes the messages queued in a loop's lanes that have not started, passing `--drop-queued` for that option alone and only with `--lanes`. It now reads stop options so that an addition cannot break Stop: the review is shown whatever the options say, and only the options the menu fully understands are offered; an option with a field it does not know is never offered without it. Unit tests only; no confirmation answered by a person. See [stop options](docs/local-clients.md#reviewed-pause-stop-and-resume-client-review-client-apply).

- New `keepgoing stop --lanes` and `--immediately`, and the same for `keepgoing client stop`. `--lanes` makes the stop cover the lanes too: the check that carries out the stop also stops the supervised BB thread's verified descendants that are running, or in error with a retry queued (a waiting provider retry is cancelled with `bb provider-retry cancel`), at most three levels deep and fifty threads in all, and counts what it did not check. A lane is sent nothing but a stop; one another loop supervises is left to that loop; each stop is recorded in `sends.json` before it is made, under a keyed hash, so a check killed in the middle loses no stop; it may make one a second time, which is harmless. One `stop` report gives the counts. `--immediately` carries the stop out in the command, under the loop's check lock and the session-claim rules, and records it as a check; if a check holds the lock for more than five seconds the stop is left to the checks, and the command says so. For other adapters lanes are not applicable, and the output says so. `client stop --json` gains `carriedOut`, `leftBecause` and `lanes`; `control.json` gains `stopLanesAt`, `state.json` `laneStop`, and the check's JSON `laneStop`. Lanes that have not started (`pending`) or are idle with messages queued are left alone and counted, their messages kept; `--drop-queued` (only with `--lanes`, and its own option in the page and the menu) deletes those messages with `bb thread queue delete`, recorded first. Their text is not kept, and the supervised thread's own queue is never touched. Every check records where it found `bb` (`state.json` `bbPath`), and a stop or lane count run with a shorter PATH (the panel, the menu) uses that path when the configured bare `bb` is not on it, or says plainly that bb could not be found from here and leaves the stop to the next check. A brief to another conversation is never dropped from the pending send records. The page's stop review and `client review stop` (the menu) offer the options as buttons, with the lanes counted from a fresh read (`preview.stop`), and `client apply stop` takes `--lanes` and `--immediately`. Plain `stop` is unchanged. Offline fixtures and a stand-in bb only. See [stopping the lanes too](docs/operations.md#stopping-the-lanes-too).
- **A stopped scheduler is noticed.** An enabled loop that is not paused, waiting for a person, complete or stopped is *overdue* when no check has run, inside its operating window and since its last control change, for more than three times its usual interval (the second longest of its last five gaps, never under 15 minutes), or for 24 hours (of its working hours, with a window) before it has shown three gaps; changing the window starts that record again. Only gaps wholly inside the operating window teach the usual interval. A daemon still running since before the last check, with no pass since and no check turned away, means the computer slept, and is not overdue; a daemon whose completed passes began after the last check and recorded nothing is reported as checks running but not recorded. `status` prints a `schedule:` line and gives `schedule` in JSON; `doctor` gives a `supervisor.schedule` finding; the panel lists an overdue loop under needs you, so the macOS menu badge counts it; the BB plugin's card says checks have stopped. The sentence says the computer may have slept or the scheduler stopped, names a BB automation only when the last check before the gap was started with `tick --routine bb-automation/<id>`, and says a check may be hung when later checks were turned away by its lock. A new opt-in `check_gap` report is sent once by the first check after such a gap, after that check is saved. `init` also prints `keepgoing enable` and `keepgoing service install` as the recommended alternative to `start` on macOS and Linux (`next.service` in `init --json`); nothing else in its output changes. Older binaries reject `check_gap` in `report.events`. See [external schedulers can stop on their own](docs/operations.md#external-schedulers-can-stop-on-their-own).

- **Behavior change: a time window follows the local clock on the days it changes.** A `window` edge was counted in hours from local midnight, so on a daylight-saving day every edge after the change was off by the size of the change: a `22:00`-`06:00` window in New York read 22:30 EDT on Sun 10 Mar 2030 as outside, and a `09:00`-`17:00` window in London read 17:30 BST on Sun 31 Mar 2030 as inside. Each edge is now the local time on its date, so on those days the supervisor acts, and scheduled probes run, at the times the window names. A time the clock skips opens or closes the window when the clock jumps past it, and a time it shows twice means its first occurrence. Windows on days without a change are unaffected. Tested minute by minute against the local clock across both 2030 changes in New York, London and Lord Howe. See [window](docs/configuration.md#window).

- `keepgoing panel` keeps its runtime files (record, locks, socket and launch pages) under the user state directory, beside the session claims, instead of the configuration directory; on Linux that moves them from `~/.config/keepgoing/panel` to `~/.local/state/keepgoing/panel`. After upgrading, `keepgoing panel` or `keepgoing panel stop` stops a panel server the earlier build started there and removes the old directory, which is then never read again; `panel status` and `panel list` only report such a server (`earlierBuildPanel` in JSON) and never stop it. On macOS both are the same place and nothing changes. See [the panel](docs/dock.md#opening-it-with-one-command-keepgoing-panel).

- `enable --take-over` now waits up to 5 seconds for the loop's check lock instead of exiting 75 at once. A takeover that landed while the old owner's supervisor was in a check or control poll used to change nothing and leave the person to guess that running it again would work. If the lock is held for the whole wait, it still exits 75 and now says the old owner's supervisor is busy and to run it again. See [one owner per loop](docs/operations.md#one-owner-per-loop).

- The keepgoing panel says which build serves it, in its footer and as `version` in `api/v1/server`. Each loop's page says which build ran its last check, from that check's own record. A loop whose last check ran a different build is listed under "Worth knowing" (never as a need). Labels are compared whole, so two dev builds of one release are different builds. A `dev` label without a version makes it "unknown". Older or newer is said only between two plain releases. Fixtures only. See [the panel](docs/dock.md).

- **The macOS menu can pause, stop and resume a loop.** Each loop's row opens its choices: Open in Panel, and Pause…, Resume… or Stop… as its control flags allow. Each shows the panel page's own review in a native confirmation, with Cancel as the default and Stop styled as destructive, and confirming acts only on the control record that was reviewed. Today a stop stops the conversation only, at the loop's next check, and the review now says that its lanes keep running; the stop options for lanes and stopping at once, in the CLI's own words, are specified for when the CLI has them. New **Open Panel with Controls…** starts `keepgoing panel --allow-changes` after a confirmation that shows the footer's exposure statement, restarting a read-only panel. Behind it are two new commands, `keepgoing client review pause|stop|resume --loop KEY --json` (read-only: the page's review, built by the same code) and `keepgoing client apply … --expect VALUE --json` (the page's change and outcome wording), recorded as ordinary `pause`, `stop` and `resume`. The expect value is one review for one action on one loop, refused after it expires, and a resume acts as the BB thread in `BB_THREAD_ID` exactly as `keepgoing resume` does, so another conversation cannot resume a loop it does not own (the menu runs with none). Review times are local, with their offset. A reviewed resume is now checked against the record before its ticket is prepared, on the page too, so a stale review no longer replaces a ticket another client prepared. `panel list --json` gains `can` per loop and `panel status --json` gains `exposure`. The menu now runs seven commands, each in its allow-list with a test, with the environment the panel gives its own server. Three review sentences no longer name the page ("this review cannot confirm", "you are asked to review again", "Check its state before doing anything else"), so the menu can show them as they are. Fixtures, unit tests and the menu's contract smoke only; no confirmation was answered by a person. See [the menu](integrations/macos/README.md) and [client review and apply](docs/local-clients.md#reviewed-pause-stop-and-resume-client-review-client-apply).

- New: the no-progress flag. A loop with `progress.repositories` is flagged when it keeps being prompted with no recorded change to its repositories:
  - at `progress.flag_after_sends` messages actually sent (default 6): each send in the run graph by its own result, with turn retries counted only when the provider accepted them, so a re-prompt that sent nothing is not counted;
  - or at `progress.flag_after_errors` checks that found an error or retried the turn (default 4).

  0 turns either off. The window starts at a new uncredited state field, `progressChangedAt`, which supervision sets when the fingerprint changes (or first records it, as a baseline). The flag says which fact raised it, says "at least" where the records are short, reads "Not enough history to tell" rather than "clear" when a lower bound is below its threshold, and adds how long the loop was held for a person in the time its history covers. It is built only from recorded facts, never the transcript. It is shown on the panel (the picker row, "Worth knowing", the loop's page), in `panel list --json` and the macOS menu, as a `progress flag:` line in `status`, and as `noProgress` in `status --json`, all from one function, and only for loops that are on. It only informs: it is never a need, never in a report, and never acts. Lanes are not flagged. **Rollback note:** a binary from before this change drops `progressChangedAt` when it saves state (the flag then starts a new baseline after upgrading again) and refuses a configuration that sets `progress.flag_after_sends` or `progress.flag_after_errors`; remove them before rolling back. `examples/keepgoing.bb.yaml` sets both. Fixtures only. See [the panel](docs/dock.md#the-no-progress-flag).

- A check that cannot observe its session sends one `error` report, not two. It used to send `could not observe <target>` and then `tick failed: …` for the same failure; the one report now names the target and carries the cause.

- **Behavior change: every automatic send is recorded before it is made.** A wake, nudge, re-prompt, turn retry, brief, new conversation's first prompt, child-error notice, stop or one-off waiting-on-a-person report is first saved in `sends.json`, with or without `loop.limits.max_sends`. If that record cannot be saved nothing is sent (a stop is made anyway); if the check's outcome cannot be saved afterwards, the next check counts the send as made instead of making it again, except that a handoff or switch-back brief holds the loop for a person, with what to do next, and a stop is sent again (to every conversation that may have the task, if a brief is unsettled). A record is settled only by a check that read it; held checks and dry runs settle nothing, and a brief only once its hold is saved. Resuming a brief's hold keeps the loop on its route and briefs no route on the next check; `keepgoing resume --keep-stop` does so and keeps a requested stop. Before, with a read-only or full state directory and no `max_sends`, a session in error was re-prompted at every check and never held, and a supervisor killed between a send and the end of its check repeated the send. A loop that is not held and cannot read `sends.json` now sends nothing even without `max_sends`, reports it once, and `status` and `doctor` name the file. See [a send recorded before it is made](docs/operations.md#a-send-recorded-before-it-is-made).

- New `keepgoing panel --allow-changes`: the panel's page can pause, stop and resume a loop. Each change is reviewed before it is confirmed. The review is built from a fresh read and says what the change does: for example, what a resume clears, and that it does not turn supervision on. Changes go through the same functions as `client pause|stop` and `client prepare-resume`/`resume`, and are recorded in the history as `panel_pause`, `panel_stop` and `panel_resume`. Read-only stays the default, and `keepgoing dock` never offers changes. A running panel never switches mode; the footer and `panel status` say which mode is on, for how long, and that `keepgoing panel stop` turns changes off. Change requests are `POST` only, with an exact `Origin`, same-origin fetch metadata, a JSON body and a single-use anti-forgery value bound to the session, the loop and the action. The page acts as no BB thread, as a terminal outside BB does. `client prepare-resume` and `client resume` behave as before. A confirmation acts only on the control record that was reviewed, so a change made in between asks for a new review. **Upgrade note:** a binary from before this change reads `panel_*` operations as "unavailable" and overwrites them that way when it next writes the history, losing that a change came from the panel and whether a resume started a new episode. Restart any daemon or scheduled check on an older binary after upgrading. Fixtures and a browser run only. See [the panel](docs/dock.md#changes-from-the-page-keepgoing-panel---allow-changes).

- **Fix: two loops can no longer prompt one session at the same moment.** Two loops configured on the same BB thread, or the same headless working directory, each kept their own locks and allowance: checked at the same moment, both woke the session. A check now claims its session, in a private directory shared by every loop the user runs, before it observes it, and holds the claim until it ends; a check that finds the session claimed by another loop sends nothing and exits 75 like a busy check, naming the other loop. - **Behavior change: keepgoing now makes an outbound request of its own.** Before an error re-prompt, a handoff, a stall nudge, a hold for a session in error or for a stalled one, or a fallback probe, it checks connectivity, by default with one `GET https://api.github.com/zen` carrying Go's standard `User-Agent` and no loop, host or thread identifier. - On Windows, the records a tick replaces while another command may read them (`state.json`, `sends.json`, `progress.json`, `health.json`, the incident and delivery journals, the loop registry and the daemon endpoint) are now read with delete sharing and replaced with the POSIX-style rename already used for control files. A status reader holding `state.json` open could make a daemon tick fail after it had acted, losing the record of a stop or pause check and leaving the daemon waiting its full interval. A read refused for an instant during a replacement is retried for about thirty milliseconds; saves are not retried. Where Windows reports that rename as unsupported, these records fall back to the ordinary rename, so a reader can still block a save on such a volume; control and goal files still fail there. This narrows the failure and does not remove it: a program outside keepgoing can still hold a file, one unexplained blocked control save was seen in CI, per-target files are unchanged, and after any failed `state.json` save the next tick can repeat a stop or prompt. `state.json` and control files are now synced before replacement.
