# Changelog

## Unreleased

- Add an internal, unregistered Antigravity runner: one owned detached worker per send performs a single checkpointed ACP exchange with the prompt on private stdin, exact conversation resume, per-turn hold records, rollover without replay, owned stop and bounded setup and exit. Failures stay `unknown`. Nothing can select it: there is no configuration, factory or setup entry, because the permission contract is unresolved. Tested only with a stand-in agent; Antigravity is not installed and no version is supported.

- Internal: the headless Claude Code and Codex runners are now each one specification (`runner.Spec`) run by a shared runner, the first step of the runner kit (roadmap K1). No behaviour, command line or state file changes; existing fixtures are unmodified. Cursor is not ported. See [runner contract](docs/architecture.md#runner-contract).

- A failed BB turn is now recovered by retrying it, not by sending the prompt again. For a BB target in a `network`, `overloaded` or `unknown` error, a re-prompt decision runs `bb thread retry`, which re-submits the failed turn by reference with no new text, so a session that fails several times no longer collects a copy of the task for each attempt. It counts against the same `errors.max_reprompts`, `errors.backoff` and send allowance. The prompt is sent only when BB reports no failed turn or has no `thread retry`; an unexplained refusal sends nothing. `status` and `timeline --kind turn_retry` show what was done (incident schema 8, timeline JSON schema 5). Offline fixtures only.

- Add an [adapter capability matrix](docs/adapters.md): what BB threads, headless Claude Code, Codex and Cursor, Antigravity and the generic process adapter each support, with the evidence level for every cell. It is generated from one table that tests compare with the code. The page also records what a network outage does to a headless loop today, the gaps that exposed, and that no IDE documents a way to supervise a chat already open in its window. No behaviour changes.

- Hand off to a new conversation. A BB fallback candidate may set `bb: {new_thread: true}` instead of naming a thread. A handoff to it creates one BB thread with `bb thread spawn`, in the project and environment of the conversation it continues, titled `keepgoing: <loop> (continued, <token>)`, with the brief as its first prompt and a reference to the earlier conversation, and supervision moves to it. This is the only case in which keepgoing creates a thread; it is opt-in per candidate and existing configurations are unchanged. The intent is saved and counted before the spawn. After any failure the thread is looked up by its title. Only a `bb` CLI invocation error from a command that ended on its own, with no such thread listed, is treated as a refusal: it counts as a rejected brief and the next fallback is tried. Otherwise, if it cannot be found the attempt stays counted, the loop is held for a person and nothing is retried or handed elsewhere, so one handoff never creates two threads. `retarget` looks for an unsettled creation first and gives up on one only with `--discard-pending-thread`, after the person has found and stopped or archived any such thread. `loop.limits.max_new_threads` (default 3, at most 10) caps attempts per loop, with a hold when reached, and two are never made less than an hour apart. The new thread gets an explicit `bb.permission_mode` (default `accept-edits`) and works in the same environment as the conversation it continues, which keepgoing leaves untouched and BB may itself retry later. Loop ownership does not change, and the first prompt says so and which commands the new conversation may run. The spawn and lookups fit inside the existing check time limit. `fallbacks add` offers the choice (`--new-thread`). Fake-`bb` fixtures only; nothing live.

- A check now has a tested hard limit of `loop.tick_timeout` plus 90 seconds (4m30s at the defaults). The yield command, the observation, the Git fingerprint, the model switch and send, and three brief essential reports each have a reserved maximum; scheduled probes, exact probes and routine reports run only in time none of those has reserved. Before, a quick observation followed by a hung probe, slow reports, a slow fingerprint and a slow send could run to 4m40s at the defaults and past five minutes with a longer probe timeout. The minimum `tick_timeout` is now `2m40s`, and `status`, `doctor` and `validate` warn above `3m15s`, including when an omitted `tick_timeout` was raised to fit `probe.timeout`. Offline fixtures only. See [check time budget](docs/operations.md#check-time-budget).

- A due handoff now runs its exact probes before any scheduled probe, relying on the other fallbacks' results while they are inside `probe.ttl` (see [fallbacks](docs/fallbacks.md#redundancy)). If no fallback takes over, the held-back probes run before a re-prompt is spent, and the redundancy picture is brought up to date afterwards.

- A report that a check has no time for is no longer attempted. A routine one gets a `not_sent` delivery record; a `limit_wait` or `child_error` report keeps its single attempt for the next check. A build older than this change reads a delivery history containing `not_sent` as unavailable.

- The count of handoffs put off for lack of time now ends with the error episode instead of at any check that sees the session active, which had let a session alternating between error and active be put off without limit. The limit therefore applies within an episode, not to consecutive checks.

- The progress fingerprint no longer fails when Git is configured with `log.showSignature` and HEAD is signed, and it remembers the newest commit time across observations, so a worktree that goes away and returns unchanged is not progress.

- `keepgoing runs` now shows what a loop is waiting on (roadmap D4, partial): the child conversations its last check verified, each working, stuck or failed, and the conversation that owns the loop. When a child or the owner is itself a registered loop, that loop and its run are named so it can be followed with `--registry-id`. A child is said to hold the run only when the last check recorded child work as its reason. Stale, aged or incomplete evidence is reported as unknown, another conversation's thread ID is never printed in the parent's view, and reading a blocker contacts nobody and changes nothing. Who holds a lock is still not identified. The run graph is now schema 2; version 1 files are upgraded on their next write. See [run discovery](docs/run-discovery.md#what-a-loop-is-waiting-on-d4-partial-unreleased).

- `keepgoing tick` now exits 0 whenever the check ran and was recorded, including a check that could not observe the session, could not build its adapter, could not send, or could not read a tracked repository or the fallback health file. Those checks have `"outcome":"failed"` in the tick line (new field) and in `status`, and still print to stderr and send an `error` report. Exit 1 now means the check could not be recorded or could not start. Previously such checks exited 1, and an external scheduler that disables a job after repeated failures switched supervision off during an outage. **Scripts that relied on exit 1 to detect a failed send must read `outcome` instead.** See the [contract for schedulers](docs/operations.md#exit-codes-for-external-schedulers). Offline fixtures only.

- The notice that tells a supervised BB thread its children are in error now uses the same recovery floor as the `child_error` owner report: a child is forgotten only after it has been out of error for `min_wake_interval`, so one that flaps between error and a provider retry is announced once, not on every re-failure, and no longer causes a wake each time. Both follow one shared rule. A notice record written by an earlier unreleased build is carried over. Offline fixtures only.

- Report child threads in error to the owner. A new `child_error` report is sent when children of the supervised BB thread are first seen in error, and again only when a child newly fails, at most three times per episode. A recovered child is forgotten only after `min_wake_interval`, so one that flaps between error and a retry is reported once. It carries counts only, is saved before the single request, never retries, and changes no decision. It is in the default `report.events`: a loop whose report section has no events list starts receiving it; explicit lists are unchanged. `status` shows the record. Once recorded, v0.1.5 and earlier refuse `deliveries.json`. Offline fixtures only.

- New `loop.tick_timeout` (default `3m`): a time budget for one check's optional work. A scheduled fallback probe starts only when its whole timeout fits, so it is never shortened: one that hangs is recorded as failed once and the others are probed on the next check. Exact probes before a handoff use the time that is left, try the next fallback when one is stopped early, and put a fallback that was stopped early last on the next check. A handoff that cannot be confirmed in time is recorded as deferred without spending a re-prompt, for at most `errors.max_reprompts` checks within one error episode. With the network down, sequential 90-second probes and failed reports could make one check last over seven minutes, past a scheduler's timeout, so nothing was recorded. A whole observation is now limited to 90 seconds and a whole Git fingerprint to 60; see the entry above for the measured worst case. Offline fixtures only. See [check time budget](docs/operations.md#check-time-budget).

- A registered Git worktree that Git marks prunable and whose directory is gone (for example one created under a temporary directory before a reboot) is left out of the progress fingerprint and reported in the tick output, instead of failing every check with `could not fingerprint repositories`. A locked worktree on an absent volume, and any worktree or repository that exists but cannot be read, still fail closed. Progress is now compared worktree by worktree: a worktree that disappears or returns, or a fresh checkout of an existing commit, is not progress by itself, while a worktree seen for the first time with uncommitted changes or with a commit newer than any seen before is. The saved fingerprint has a new format; adopting it is not counted as progress. Offline fixtures only.

- `status` and `doctor` show consecutive failed checks (`failed checks: N in a row`, `supervisor.failed_checks`), and `runs.jsonl` tick events carry `outcome`.

- Fix a BB loop waiting indefinitely on a dead thread. A `willRetry` notice now counts as a live retry only while there is fresh evidence within `bb.retry_signal_ttl` (new, default `15m`): the newest notice on an errored thread, including one logged after the turn's failed completion; the newest provider or system log event on an active thread (requested input, including keepgoing's own nudges, does not count); or, for a rate-limit notice, its structured reset. Afterwards an errored thread gets re-prompts with `errors.backoff` up to `max_reprompts` and then an awaiting-user hold. A silent active thread returns to stall nudges up to `max_nudges`; in a loop without `progress.repositories`, which cannot nudge, it is held for a person after `stall_after` plus `max_nudges` times `min_wake_interval` of continued silence (3h30m at the defaults). A rate-limit notice on an errored thread no longer blocks the limit rules when its reset is beyond `wait_if_reset_within` and no retry is queued. Previously the last notice suppressed all of this forever. An active thread that keeps logging provider events is unchanged, and `unknown` errors still never hand off. `status`, tick output, `timeline` and incident history say when a notice was treated as expired. Offline fixtures only; no live outage was replayed. See [stale retry notices](docs/operations.md#stale-retry-notices).

- The re-prompt count for an error now restarts only when a check sees the session idle, or active with a changed Git fingerprint. It used to restart at any active check, so a session whose re-prompted turns kept failing was re-prompted without limit and never reached the hold. This applies to every adapter and uses the same condition as the handoff-brief counts. The count is coarser than one error: it carries over when a session works without a commit and fails again later, and when queued input chains turns so that no check sees the session idle, so unrelated errors can share one allowance. Offline fixtures only.

- On Windows, the records a tick replaces while another command may read them (`state.json`, `sends.json`, `progress.json`, `health.json`, the incident and delivery journals, the loop registry and the daemon endpoint) are now read with delete sharing and replaced with the POSIX-style rename already used for control files. A status reader holding `state.json` open could make a daemon tick fail after it had acted, losing the record of a stop or pause check and leaving the daemon waiting its full interval. A read refused for an instant during a replacement is retried for about thirty milliseconds; saves are not retried. Where Windows reports that rename as unsupported, these records fall back to the ordinary rename, so a reader can still block a save on such a volume; control and goal files still fail there. This narrows the failure and does not remove it: a program outside keepgoing can still hold a file, one unexplained blocked control save was seen in CI, per-target files are unchanged, and after any failed `state.json` save the next tick can repeat a stop or prompt. `state.json` and control files are now synced before replacement. The daemon also no longer polls for wake notices once it has been told to exit.

- Add `keepgoing runs`, a read-only offline view of the run references in `graph.json` (roadmap D3): the current and earlier runs, their sends and chat/session references, for one loop or every registered loop, with `--id` to follow one exact reference and versioned `--json`. It takes no lock, calls no provider and changes no control. Session links and blocker navigation are reported as unavailable. See [CLI navigation](docs/run-discovery.md#cli-navigation-d3-unreleased).

- Add `keepgoing fallbacks handoff on|off`, `fallbacks move ID --to N` and `fallbacks remove ID`, so automatic handoff, the handoff order and the list of fallbacks can be changed without editing YAML. Each previews the result and writes only after confirmation or `--yes`, under the same ownership, transfer and lock guards as `fallbacks add`; comments and file modes are kept. `handoff on` adds `rate_limit` to other error classes already listed. `move` and `remove` cut and paste the entry's own lines, so comments set apart by a blank line and every other byte stay put. `remove` refuses the fallback in use and a loop's only fallback, deletes the removed entry's recorded health and rejected-handoff count, and moves its saved session aside so a reused id starts fresh. `fallbacks add` now points at `fallbacks handoff on` instead of a YAML edit. Offline fixtures only.

- Tell a supervised BB thread when its child threads are in error. Errored direct children are listed from their status alone and were already not counted as running work; now an idle parent's ordinary wake ends with a fixed, count-only notice, sent when a child newly enters error and never because the set shrank, so the agent that owns them can retry or replace the work. Tick output, `status` and `timeline` show the count. keepgoing does not retry, message, stop or read child threads, and all holds and limits apply. The notice causes a wake of its own in one case: an idle parent waiting on other running children is woken once with the notice alone and no task prompt, spaced by `min_wake_interval`. A notice the adapter keeps rejecting is given up after `errors.max_reprompts` attempts and shown in `status`. Offline fixtures against a fake `bb` only.

- A long limit wait with no way out is now reported. When the active target is waiting on a provider limit, no handoff is possible and the reported reset is further away than the new `errors.report_wait_after` (default `6h`), keepgoing sends one `limit_wait` report for that wait and shows it in `status` and `timeline`. The loop is not held and no decision changes; an earlier recovery still takes effect. One report per wait across checks and restarts (at most three if the reset keeps moving later), saved before a single attempt and never retried. `limit_wait` joins the default `report.events`; an explicit list must name it. Incident history schema 7 and timeline JSON schema 4 add the marker. Offline fixtures only.

- Record run references in a private `graph.json` in each loop's state directory (roadmap D1, D2 partial): a durable loop identity, runs opened and closed by explicit control changes, each send intent and its returned call, and links to the chat/session and goal revision known without a provider query. Records are versioned, bounded and written atomically; a graph that cannot be read or written never fails a check or changes its decision, and adds one warning. No command reads the graph yet. See [run discovery](docs/run-discovery.md#persisted-reference-graph-d2-unreleased).

- Guided `fallbacks add` now adds an existing BB thread (`--agent bb`): the loop's own conversation on another model, or a different thread on `claude-code` or `codex`, with model, reasoning level, quota group and probe settings. In the guided mode, after agreement, it offers pick lists from two read-only listings (`bb thread list`, `bb provider models`); flags never run `bb`. Thread IDs stay out of output unless requested. The preview states that BB's account cannot be seen and that a same-thread fallback shares the conversation. No message is sent and no thread is created or changed. Offline fixtures with a fake `bb` only.

- Bound rejected takeover briefs. A fallback that passes its exact probe but rejects the handoff (its model cannot be applied, or the brief send fails or is unsupported) is now skipped for `errors.backoff`, and for the rest of the error episode after `errors.max_reprompts` rejections; it is not probed while skipped, and other fallbacks keep their own counts. Previously it was probed and sent to on every check. When no fallback can be offered a brief the loop waits or holds as before, and the reason says so. Rejected switch-back briefs stop after the same cap, with one `switch_back` report marked `stopped`, a status line and a warning, while the fallback keeps working. `resume` and `retarget` clear the counts so a repaired target is tried again; `status` shows capped fallbacks. Brief sends still count toward `max_sends`. Offline fixtures only.

- Incident history schema 6 keeps the 256-record/512 KiB bound but reserves room separately for key events (target moves, retargets, ownership changes, holds entered and cleared), ongoing conditions (limit waits, failed probes, failed handoff attempts), activity and routine checks, so none can evict another's reserved records. Runs of identical no-op checks, including repeated scheduled-probe failures, collapse into a count and time span between the run's first and latest check; attempted moves and new probe results are never folded. A multi-day limit wait is now a handful of long-lived records instead of being pruned within about 42 hours. `timeline` (JSON schema 3) shows collapsed counts, per-tier pruning and a note when a selected range reaches pruned history. Legacy journals are collapsed on their next append; older binaries refuse the upgraded file. Offline fixtures only.

- Record and show usage readings. When a probe that already runs reports quota windows, keepgoing stores one bounded reading per candidate in `health.json` and shows it, with its age, in `fallbacks list` and `status` (text and JSON); otherwise it shows `unavailable`. A reading is tied to the account it was read from and is marked stale once its window resets. Claude readings come from `rate_limit_event` messages, an observed and undocumented shape, so the Claude probe now requests `stream-json` output and is judged from the same result object. Codex readings come only from the existing app-server read after an unclassified probe failure. No decision uses these values, no provider call is added and no credential is read. Failed-probe captures now keep the end of the output and omit the Claude initialization message. Fictional fixtures, plus one live manual Claude probe on Claude Code 2.1.318 that was judged healthy with a reading recorded; other tiers, failing probes and Codex readings are not live-verified.

- Add guided `keepgoing fallbacks add` for existing loops. It looks up installed agent CLIs without running them, collects a headless Claude Code or Codex account directory, quota group and model, previews the candidate and handoff order, and writes only after confirmation; `--non-interactive`, `--dry-run` and `--json` script it. Handoff stays off unless explicitly enabled, including for loops whose default `errors.failover_on` would otherwise start it with the first fallback. Writes require the owning BB thread and no pending transfer. Unsupported agents, shared quota groups, the same login and model as an existing target, and symlinked sources are refused without writes. `fallbacks list` now names candidates that were never probed. Offline fixtures only: no login, account detection, model lookup or provider call.

- `validate` and `status` now say when a loop has no loop-wide limit. With `deadline`, `max_sends` and `no_progress_timeout` all unset, `validate` prints a warning on stderr and `status` shows it on a new `bounds:` line; otherwise both name the configured limits. `status --json` adds `workBounds`. No default limit is applied, and behavior and exit codes are unchanged. Offline fixtures only.

- `timeline` now works as a navigable event log. Incident history schema 5 records the hashed target after each check, per-check probe results, manual retargets and limit-wait causes, so handoffs, switch-backs and retargets show both ends. New `--kind` (including `moves`), `--target`, `--since` and `--until` filters apply to text and JSON (timeline schema 2); summaries still use all retained evidence. No task text, notes, thread IDs or aliases are stored. Older binaries refuse the upgraded journal. Offline fixtures only; work moved outside keepgoing and reporting a long limit wait remain roadmap items.

- Nudge and re-prompt attempts now count toward `max_nudges` and `max_reprompts` and start `min_wake_interval` and `errors.backoff` even when the adapter reports the send as failed or unsupported. Previously such a send was retried on every check without a cap or a hold. Because a failed send may still have been delivered, an adapter that keeps failing now reaches the awaiting-user hold after the configured number of attempts; a stalled headless turn, which cannot be nudged, does too. `lastWakeAt` records the attempt time. Stop and control holds are unchanged. Failed handoff briefs are not covered. Offline tables and fake-adapter fixtures only.

- Document the [bounds on repeated work](docs/operations.md#bounds-on-repeated-work): per-turn nudge and re-prompt caps versus the optional loop-wide `deadline`, `max_sends` and `no_progress_timeout`, their precedence, and what they do not cover. No behavior change. New exhaustive decision tables and a repeated-turn supervisor fixture back the description with fakes only.

- Windows control loads and daemon polling open read-only snapshots with delete sharing, paired with POSIX-style replacement for control/goal writes. This requires Windows 10 version 1709 or newer and a filesystem supporting that operation; unsupported operations fail without a legacy fallback. Deterministic fixtures retain an open reader across replacement, compare an incompatible legacy handle and preserve originals on failure. Other readers can still block a save; no retry or general write guarantee is added.

- Extend the local recovery smoke with opt-in `--include-cursor` for source builds. A fictional Cursor CLI verifies unknown-error recovery and exact session reuse across actual held-daemon crashes/restarts, without provider calls. Published v0.1.5 remains compatible with the default four-adapter smoke.

- The daemon now checks control-file contents as well as metadata between passes, so same-size pause/stop edits with unchanged modification times request a fresh check. The private digest is never logged; existing ownership, holds and configuration checks still apply. Deterministic native fixtures cover in-place and atomic replacements, changes during polling, and unchanged-file waits.
- Add an internal Antigravity streaming-input encoder and conservative lifecycle parser with fictional offline fixtures. An internal ACP v1 gate and bounded stream exchange additionally test exact session/request correlation, cancellation-only permission handling and required checkpoint ordering before prompt/cancellation writes. A saved interaction hold now implements that checkpoint as synced create-once per-target records, and unadopted evidence of a cancelled permission request becomes an awaiting-user hold that survives supervisor restarts until an explicit resume; fixtures use a stand-in adapter. No adapter or setup option is registered; an owned ACP process, prompt-reservation reconciliation, question handoff and live verification remain open. See the [integration foundation](docs/antigravity.md).
- Add an unreleased primary-only Cursor CLI print adapter with exact session reuse, bounded structured completion parsing and owned cancellation. Offline command journeys cover active holds, stop precedence and bounded unknown-error recovery; a disposable wrapper-crash fixture verifies session recovery after reconstruction. Task input stays on stdin; permissions remain configured in Cursor. Guided setup now discovers the `agent` CLI, creates disabled task/goal setups and discloses unavailable capabilities. Account-directory/fallback options are refused. Supported-version evidence, fallback probes and live acceptance remain unfinished.

## 0.1.5 (2026-11-12)

- CLI v0.1.5 / BB plugin v0.2.0 include version-specific notes and a repository plugin collection for explicit tagged installs. The package smoke check now covers prompt-only and goal-aware setup for all three supported agents, with zero provider calls. See [release verification](docs/release-verification.md) for publication, package and live-acceptance evidence.

- Repeated control writes advance the loaded timestamp even when the wall clock repeats or moves backwards. This prevents a repeated pause from leaving identical evidence for an older registered-resume ticket. Deterministic clock fixtures and the existing resume regressions cover the correction.

- The separately rebuilt BB plugin offers an explicit goal checkbox in setup, binds previews to that choice, and shows recorded goal identity/revision in setup and expanded status without private task text. Goal creation requires CLI v0.1.5; older builds must use the explicitly deselected task-only path. The preview now correctly distinguishes idle checks from stall-nudge spacing. SDK/host/DOM fixtures only; live deployment and first-loop acceptance remain open.

- Guided setup offers an explicit goal choice; scripted setup can use `init --with-goal`. It saves one private task snapshot referenced by the existing goal store and shares the current revision through stable wake instructions. Creation remains disabled; previews write nothing and ordinary output omits task text. Existing noninteractive callers keep prompt-only setup. Offline fixtures only; a live first-loop walkthrough remains unfinished.

- Ordinary status now shows the latest recorded automatic prompt attempt’s goal ID/revision, target alias, mode and adapter return result. Metadata comes from the same composition as the prompt and persists with completed ticks. Offline fixtures cover revisions, queued nudges, failures, holds and restart reads; delivery/execution, crash-complete history and source tracking remain unverified or unfinished.

- Diagnostic records retain BB's generic `thread_command_failed` code, while its decision classification stays `unknown`. Offline CLI fixtures cover unreadable status, interrupted turns, queued work, bounded re-prompts and preserved holds. This does not identify or restart a disconnected host; previously redacted records remain unavailable.

- Goal subcommand help (`create|revise|show --help` or `-h`) now exits successfully without loading configuration or changing state. Invalid arguments still return usage errors. v0.1.4 returns exit code 2 for this help; v0.1.5 includes the correction.

## 0.1.4 (2026-11-12)

- Headless stop now asks a private per-turn wrapper to terminate its own Unix group or Windows job instead of signalling a saved PID. Legacy turns without the key are refused. Native subprocess fixtures cover stale records and descendants; live provider cancellation and abrupt-death descendant cleanup remain unverified.

[v0.1.4 notes](docs/releases/v0.1.4.md) describe the changes and upgrade limits. Publication, package installation and live-provider evidence are tracked separately in [release verification](docs/release-verification.md).

- Incident history now retains numeric release versions with development commit-hash or numeric release-candidate suffixes. Arbitrary suffixes remain redacted; old unavailable build labels cannot be recovered. Offline fixtures only.

- Added opt-in `loop.prompt_goal` to send the latest private goal revision with automatic prompts and handoff briefs, instead of requiring copied goal text in wake policies. Missing or invalid goals refuse sends; existing loops remain unchanged. Offline fixtures only; semantic drift detection and guided goal setup remain planned.

- Added an optional read-only native macOS menu preview for explicitly registered local loops, using the shared CLI contract. It shows holds, timestamped activity, configured targets, optional private goal text and daemon evidence, without starting supervision or a wake timer. Developer build only; controls, installation, signing and live UI verification remain planned.

- Fixed known rate-limit cooldowns with `errors.failover_on: []`: ordinary checks continue without spending recovery retries or entering an automatic user hold before the reported reset. Earlier structured recovery is observed on the next check. Explicit holds and loop-wide bounds remain authoritative. Offline decision/supervisor fixtures only.

- Added `client prepare-resume` and `client resume`: a five-minute, single-use private ticket binds reviewed config/fallback sources, registration, caller/owner, controls, state and goal evidence. Changed evidence rejects resume; consuming before save prevents automatic replay after a crash or lost response. Preparation never clears holds; resume preserves disabled state, ownership, goals and allowances. Offline fixtures only; native UI/live verification remain pending.

- Added registered `client pause|stop` with binding/source checks, short registry/control locking, preserved holds/ownership and versioned save evidence. Diagnostic failures remain distinct from failed or unconfirmed saves. Offline fixtures only; native controls and installation remain planned.

- Added schema-1 read-only `client status` for registered loops: checked config/runtime bindings, explicit holds and declared completion, configured target, historical action/freshness, optional private goal display and bounded daemon evidence. Unknown/corrupt evidence and changed bindings remain explicit. Offline fixtures and a local authenticated daemon test only; the native companion remains planned.

- Added explicit local loop discovery through `registry add|list|remove`, with private versioned references, stable IDs, binding-conflict checks, bounded storage and independent locking. Registration never changes loop controls or runs providers. Offline fixtures only; the client status interface is described above; the menu-bar app is a separate read-only developer preview.

- Expanded the BB banner/card status with declared completion, actual target thread, timestamped daemon/check evidence, and historical action outcomes. Failed refreshes show a warning and hide controls/setup until refreshed. External schedulers remain uninspected. SDK/DOM fixtures, typechecking and bundle builds only; no live deployment.

- Added the BB plugin’s "Move supervision here" flow for plugin-created loops in the same environment/provider: preview source/destination and holds, explicitly apply a held move, and reconcile or recover interrupted requests after reload. Registered-host routing and durable private references keep paths/commands out of browser control; resume/start remain separate. SDK/controller/DOM fixtures and bundle builds only; no live transfer or deployment.

- Added explicit same-environment BB `transfer apply` and roll-forward `transfer recover`, with a durable pending fence, preserved holds/goals/allowances, target-specific observation reset, atomic config replacement and a permanent target binding against stale config copies. Moves stay awaiting-user and advance owner generation. Fixture-tested, including a real subprocess exit with fake BB; no live transfer or model/account verification is claimed.

- Added read-only `transfer preview` for a single BB primary: versioned JSON/text compare thread/provider/environment metadata, display redacted holds/ownership/goal identity and flag unavailable or incompatible inputs. Offline mode skips BB queries. Fixture-tested only; model/account identity remains unverified; the plugin flow is described above.

- `goal create|revise|show` records private goal identity and specification revisions independently of loop controls. Expected ID/revision checks prevent stale edits; ordinary status withholds titles/references, with explicit `show --private` for full history. Offline fixtures cover ownership, locks, holds, corruption, limits and privacy. Goal acceptance, verification and review-stage bindings remain unimplemented.

## 0.1.3 (2026-11-11)

Reliability release collecting the changes after v0.1.2. Publication, package installation and live-provider evidence are tracked separately in [release verification](docs/release-verification.md#v013-reliability-release-evidence). See the [release notes](docs/releases/v0.1.3.md) for the user-facing changes and upgrade limits.

- Native macOS/Linux CI and the unpacked Linux release gate now run a recovery smoke check with stand-in BB/process/Claude/Codex providers, rejected local notifications, held daemon restarts, explicit recovery and completion without replay. This adds offline artifact evidence, not live provider or deployment certification.

- Added `timeline`, an offline text/JSON view combining bounded incident/delivery records with redacted current control flags. It exposes local timestamp/source evidence, historical hold and activity summaries, failed alerts, retention and evidence gaps without provider/scheduler/daemon/CI calls or writes. Diagnostic failures preserve holds and original transport behavior; completion remains single-attempt without redirects or replay. ### Added

- Subscribed `complete` reports now describe a new explicit completion declaration without private notes or claims of independently verified success. Completion delivery uses one attempt without retries/redirects, with notification-loss limitations documented. Covered by offline fixtures only.

The daemon checks structured child outcome notices ahead of its normal interval with persisted deduplication. ## 0.1.0 (2026-11-10)

### Fixed

- The BB adapter read the oldest 60 log events instead of the newest, because `bb thread log --limit` returns events oldest first. On a long thread it missed current errors, rate limits, and interactions. It now keeps a cursor and reads only new events after a one-time full pass.
- A stop request is now honored while the loop is paused, disabled, or awaiting a person, and when state files cannot be read.
- The daemon now acts on a stop or pause written during a pass, instead of waiting a full interval.
- Relative `state_dir` and command paths now resolve against the config file, so headless runners and `./script.sh` commands work from any directory.
- `retarget` now applies the target agent's model and reasoning level.
- A handoff brief that cannot be written no longer leaves a candidate's model switched.

- A gone target now marks the loop awaiting user instead of staying silent.
- Time zones now load on Windows, and the network probe command works there.
